문서를 검토한 뒤, `server/config.mjs`의 비용 추정이 "가장 싼 등급
($15원/건으로 가정)"이라는 학습 기억에 의존한 잘못된 전제였고, 실제
우리 코드가 요청하는 필드(`places.displayName`, `places.location`,
`places.formattedAddress`)는 **Text Search Pro 등급**(가장 싼 등급이
아님)에 해당한다고 지적했다. 공식 첫 유료 등급 단가(ChatGPT 제공,
이 세션이 직접 재확인한 것은 아님 — 5-1절 참고)는 Text Search Pro
$32/1,000, Routes Compute Essentials $5/1,000, Routes Compute Pro
$10/1,000이다. 이번 갱신은 이 단가를 실제로 코드(`server/config.mjs`)
에 반영하고, "공식 등급·달러 단가·계산용 환율·안전 여유"를 서로 다른
변수로 분리해 앞으로 등급이 바뀌어도 계산 전체를 다시 짤 필요가
없게 만들었다. 또한 "월 5만원은 초기 전체 운영 목표이지 전액 Google
예산이 아니다"라는 지적을 반영해 고정비/Google 예산 배분을 다시
확인했고, 무료 체험 사용자의 비용까지 포함해 계산한다.

이 문서는 남은 결정 사항을 정리하는 곳이다. 브랜드·가격·기능 범위는
이미 확정돼 반영했다(아래 1절) — 남은 건 실제 서비스 연결 방식과
사용 한도처럼 아직 안 정해진 것들이다. 숫자를 지어내지 않는다 —
확인 안 된 값은 "모른다/확인 필요"라고 그대로 적는다.

**3차 갱신에서 달라진 것 (요약)**: 사용자가 2차 갱신 검토 후 "무료체험이
서버가 아니라 클라이언트에서 집행되고 있었다"·"운영에서 테스트 기능이
안 막혔다"·"장소 조회가 로그인·한도 없이 열려 있었다" 등 구체적인
문제를 지적했다. 이번 갱신은 그 지적에 대한 실제 코드 수정 결과를
반영한다 — 그리고 **공급자도 확정됐다: 결제는 토스페이먼츠, 로그인
이메일은 Resend, 장소·경로는 Google Places + Routes.** 공급자 확정은
"이 API를 붙이는 코드를 작성한다"는 결정이지, 실제 유료 계약이나
과금을 지금 승인한다는 뜻이 아니다(사용자 지시 원문 그대로). 세
공급자 모두 실제로 그 API를 호출하는 코드를 작성하고 키 없이 통과하는
계약 형태 테스트까지 마쳤지만, **이 세션은 outbound 네트워크가 막혀
있어(EGRESS_BLOCKED) 공식 문서를 다시 열어보거나 실제 키로 검증하지
못했다** — 학습 시점 기억을 바탕으로 작성했고, 실제 키를 넣고 처음
써보기 전까지는 ④(실제 연결 검증 필요)로 분류한다(`docs/RELEASE_STATUS.md`
참고).

## 1. 확정된 사업 방향 (반영 완료)

- 모바일 중심 서버 기반 여행 웹앱, 표시명 **travel hub**.
- 후쿠오카 전용이 아니라 사용자의 저장 장소를 기준으로 여러 도시에서
  사용(도시별 분리, 여러 날짜 일정 정리까지 구현·검증 완료 —
  `docs/DESIGN_INTEGRATION_REPORT.md` 1-B-11).
- 첫 상품: **9,900원·30일 여행 이용권, 결제 승인 시 시작, 자동결제
  없음.** `server/config.mjs`의 기본값을 그대로 확정 상품으로 반영했다
  (여전히 환경변수로만 바꾸는 구조 — 코드에 숫자를 안 박는다는 원칙은
  유지). **구독(정기결제)이 아니다** — 이 문서·마케팅 문서 모두에서
  "구독"이라는 말을 쓰지 않는다. 기간이 끝나면 그냥 끝이고, 다시
  쓰려면 다시 결제해야 한다.
- 무료: 샘플, 장소 가져오기·보관·검색·수동 정리, 개인화 코스 생성
  성공 1회(로그인 필요 — 3차 갱신에서 "첫 코스도 로그인 후에만"으로
  바뀌었다, 2절 참고). 유료: 추가 코스 생성·조건 변경 후 재계산·여러
  날짜 일정 정리. 전부 구현·검증 완료.
- **⚠ 6차 갱신 — 이용권에 실제 사용량 숫자를 못 박았다: 무료체험
  위치 확인 최대 10곳+개인화 코스 성공 1회, 유료 이용권(30일) 위치
  확인 최대 50곳+코스 생성·재계산 최대 30회.** 저장 개수·방문 기록
  열람·수동 정리는 이 한도와 무관하게 계속 무료다(3-3-1절). **이
  숫자는 초기 테스트 상품의 스펙일 뿐, 공개 출시 전 실사용·편의성·
  원가를 검증해 확정한 시장가격이 아니다** — 실제 손님이 30회/50곳
  한도를 불편해하는지, 원가 계산(3-3절)이 실제 계약 단가로도
  맞는지는 초기 체험단 운영 후에 다시 봐야 한다. 새 가격 구간·유료
  부가상품은 만들지 않았다(단일 요금제 원칙 유지).
- 만료 후에도 기존 장소와 코스 열람은 유지된다(서버 게이트를 안 타는
  순수 열람 — `scripts/test-multi-day.mjs`에서 환불 뒤에도 열람되는
  것까지 확인).
- 무제한 사용은 아직 확정 안 됨 — 3-5절에 제안을 정리해 뒀다.
- 결제 **토스페이먼츠**(결제창+서버 승인 연동), 로그인 이메일
  **Resend**, 장소·경로 **Google Places + Routes**로 공급자가
  확정됐다. 이건 "이 API를 호출하는 코드를 만든다"는 결정이고, 실제
  유료 계약·과금을 지금 승인하는 게 아니다.

기존 `src/landing.html`(브랜드 "별표털기", 서버 없음, 한 번 결제)과의
충돌은 위 확정 방향대로 **(A) travel hub로 완전히 전환**하는 것으로
해소된 것으로 보고 진행한다 — `src/landing.html`은 여전히 손대지
않았고(폐기 여부는 실제 공개 배포 시점에 결정), `src/design/`
기준으로만 개발을 이어간다. 옛 마케팅 문서(`가격_판매전략.md` 등,
서버 없는 단일 파일·한 번 결제 전제)는 이제 전제 자체가 안 맞으므로
`MARKETING_LAUNCH_PLAN.md`(이번에 확정 상품 기준으로 갱신됨)를 쓴다.

## 1-2. 9차 재검토 — 확정 사업 방향 갱신(기존 문서 내용보다 이 절 우선)

사용자가 9차에서 사업 방향을 다시 확정했다. 아래 내용이 이 문서
다른 곳의 관련 서술과 다르면 **이 절을 따른다.**

- **목표 시장**: 세계 여러 도시에서 사용자 자신이 저장한 장소로 여행을
  편하게 계획하는 앱이다. 후쿠오카 한정 상품이 아니다(1절과 동일한
  원칙의 재확인). 창업자 본인의 후쿠오카 저장 장소가 160곳 이상이라는
  경험담은 홍보에 쓸 수 있지만, 이걸 "전체 국가 합계 사용자 수"나
  "검증된 시장 규모"처럼 확대해서 쓰지 않는다.
- **초기 사업 목표**: 운영비를 빼고 **월 100만 원이 남는, 관리 부담이
  낮은 반복 수익 자산**을 만드는 것. 이건 목표치이지 세후 순이익이나
  수익을 보장하는 약속이 아니다 — 마케팅 문서·소비자 화면 어디에도
  이 숫자를 성과나 약속처럼 쓰지 않는다(내부 목표로만 취급).
- **기본 수익 모델**: 앱 이용권(현재 코드값 9,900원/30일, 자동결제
  없음)과 **다음 여행 때의 재구매**. 자동 갱신되는 월 구독으로
  바꾸라는 지시가 아니다 — 지금 방식(만료 후 재결제) 그대로 유지한다.
- **추가 수익(보조)**: 필요할 때만 eSIM·교통권·입장권 등 제휴로
  보충한다. 숙박 제휴는 "아직 숙소를 예약하지 않은 사용자"에게만
  자연스럽게 노출한다(이미 숙소를 정한 사용자에게 억지로 들이밀지
  않는다). 6절의 "최소 제휴 준비 구현" 참고 — 이번엔 구조와 클릭
  이벤트만 준비하고 실제 계약·게시는 하지 않는다.
- **가격 재검토**: 4,900원 베타 가격안은 **보류**다(채택도 폐기도
  아님 — 다음 결정을 기다리는 상태). 현재 코드에 있는 9,900원은
  "지금 코드가 이렇게 동작한다"는 사실일 뿐, 검증을 마치고 확정한
  최종 판매가로 홍보하지 않는다. Claude는 가격·사용량 관련 코드
  값을 임의로 바꾸거나, 사용자를 싸게 모집하는 문구·로직을 마음대로
  추가하지 않는다(변경이 필요하면 ChatGPT/사용자의 명시적 결정을
  먼저 받는다).
- **보류(당장 하지 않음)**: 검증 안 된 유료 지역팩, 별도의 대규모
  AI 여행 플래너, 업장 광고·B2B 상품, "도시를 바꿨다"는 이유만으로
  받는 추가 과금. 이 문서에 없는 새 사업 기능을 Claude가 스스로
  만들지 않는다.
- **제휴 운영 원칙**: 제휴 수수료 때문에 추천 동선을 바꾸거나,
  수수료가 높은 업체 순서로 장소를 추천하지 않는다. 이 원칙은 코드
  구조(6절 제휴 스캐폴드)에도 그대로 반영한다 — 제휴 표시 조건이
  "이 지역에 승인된 링크가 있는가"일 뿐, 코스 생성 로직에는 전혀
  관여하지 않는다.
- **수치 사용 규율**: "고객당 추가 매출 15,000~30,000원", "마진
  100%", "제휴 업체 30개 확보" 같은 숫자를 검증된 전망으로 문서나
  마케팅 자료에 쓰지 않는다. 실제 계약·데이터가 생기기 전까지는
  전부 "미정" 또는 "가설"로만 표기한다.

## 2. 확인된 사실 (실제로 코드를 돌려서 검증함)

**4차 갱신에서 새로 고친 것(요약)**: ChatGPT가 실제로 재현·지적한
문제들이다 — 전부 재현 테스트로 확인한 뒤 고쳤다.
- **운영에서 경로 API 키가 없을 때 가짜 "실제 경로"가 나오던 버그**를
  고쳤다. `services.routing !== 'real'`이면 무조건 테스트 시뮬레이터로
  빠지던 조건문이 `'unavailable'`(운영, 키 없음)일 때도 참이 돼,
  ChatGPT가 `APP_ENV=production`+키 없음 상태에서 실제로 `routedReal:true`
  를 받아냈다 — 이제 `'test'`일 때만 시뮬레이터를 부르고, `'unavailable'`
  이면 절대 시뮬레이터로 안 빠지고 정직한 추정만 준다(설정 함수뿐
  아니라 실제 `/api/course/generate` 엔드포인트까지 재현 테스트로
  확인).
- **결제 취소가 계정 소유자를 대조하지 않던 문제**를 고쳤다 — 다른
  계정의 주문을 취소할 수 있었다. 이제 세션의 accountId로 주문
  소유자를 반드시 대조한다.
- **과거 주문 취소가 다른(더 최근) 유효 주문의 이용권을 없앨 수 있던
  구조**를 고쳤다 — 계정이 지금 어느 주문으로 이용권을 받았는지
  (`accounts.active_order_id`)를 기억해, 그 주문이 아닌 옛 주문의
  취소·지연 웹훅은 지금의 이용권을 건드리지 않는다.
- **결제 승인 응답이 유실(타임아웃 등)돼도 무조건 실패로 확정하지
  않고** 토스 조회 API로 실제 상태를 재확인한 뒤 판단한다. 확정 못
  하면 주문을 `failed`로 낙인찍지 않고 재시도 가능한 상태로 남긴다.
- **부분 취소를 전액 취소와 다르게** 처리한다 — 부분 취소는 이용권을
  자동으로 회수하지 않는다(환불 정책 미확정 — 아래 5절에 별도 보고).
- **활성 이용권이 있으면 새 결제를 서버가 직접 거부**한다(중복 구매
  방지, 만료일 안내는 클라이언트가 응답의 `expiresAt`으로 표시).
- **코스 생성의 체험 차감·결과 저장을 하나의 DB 트랜잭션으로 묶었다**
  — 저장이 실패하면 체험도 차감되지 않는다. 생성 잠금에 만료·소유권
  검증을 추가해 프로세스가 도중에 죽어도 그 계정이 영원히 막히지
  않는다. 같은 멱등키에 실제로 다른 요청 본문이 오면 충돌로 처리한다.
- **장소 조회를 Legacy Find Place에서 Places API(New)로 전환**했다 —
  첫 검색 결과를 무조건 확정하지 않고, 지역 힌트와 실제로 맞는 후보를
  우선한다(동명 장소 오확정 방지). 일괄 조회 엔드포인트를 추가해
  장소마다 반복 설정하지 않아도 되게 했다.
- **API 비용 통제를 실제로 코드로 집행**했다 — 호출 종류·SKU별 예상
  비용을 원장에 기록하고, 계정별→전체 순으로 한도를 확인해(계정
  한도로 거부될 요청이 전체 한도를 갉아먹지 않게), 한도를 넘으면
  실제 호출 자체를 하지 않는다. `phase=import`처럼 클라이언트가
  자기 신고하는 값만으로 더 큰 한도를 받을 수 없게 했다(더 큰 한도는
  서버가 실제로 처리하는 배치 크기로만 정해진다). 여러 세그먼트로
  나뉘는 코스는 예산이 일부만 감당 가능하면 전부 추정으로 대체한다
  (일부만 실제·일부만 추정으로 뒤섞이지 않는다).
- **Google Routes 중간 경유지 상한(25개)을 지킨다** — 넘으면 연결된
  여러 번의 호출로 나누고(연결 구간·실제 호출 수 보존), 11개 이상인
  구간은 더 비싼 요금(SKU)으로 비용을 기록한다.
- 서비스 전체 이번 달 비용 한도가 이미 꽉 찼으면 새 결제 자체를
  막는다(유료 고객이 결제만 하고 정작 코스를 못 만드는 상황 예방).

**2차 갱신(이전) 이전에는 이 절이 설명하는 "무료체험 확인"·"장소
조회"가 실제로는 클라이언트가 먼저 계산하고 서버에는 결과만 뒤늦게
알리는 구조였다 — 사용자가 직접 테스트해서 찾아낸 문제였다(동시
요청으로 무료체험 우회 가능, 실패한 추정 결과도 체험이 차감됨,
장소 조회가 로그인·한도 없이 열려 있음 등). 아래는 그 구조를
서버 집행 방식으로 다시 짠 뒤 실제로 검증한 내용이다.**

- 구글맵 저장 목록 내보내기(Google Takeout) ZIP/CSV/JSON을 실제로
  읽어 장소를 가져온다.
- 가져온 장소를 도시별로 나누고, 유형을 짐작하되 사람이 직접 고치면
  그 선택을 유지한다.
- **장소 조회(`/api/places/lookup`)는 이제 로그인 없이는 아예 호출할
  수 없다**(인증 필수로 막음). 초기 가져오기(160~300곳처럼 한 번에
  많이 확인하는 상황)와 이후 재조회는 **서로 다른, 환경변수로 조절
  가능한 일일 한도**를 따로 둔다(`PLACE_LOOKUP_IMPORT_DAILY_LIMIT`/
  `PLACE_LOOKUP_REQUERY_DAILY_LIMIT`, 계정별+서비스 전체 상한
  `PLACE_LOOKUP_GLOBAL_DAILY_CAP`도 별도) — "위치 조회 하루 30회"처럼
  두 상황을 하나의 값으로 묶는 안은 사용자가 명시적으로 반려했다(첫
  가져오기부터 막힐 수 있다는 이유). 지금은 테스트 어댑터(가짜
  좌표·결정론적) 기준으로 인증·한도 분리 동작을 실제 HTTP 요청으로
  검증했다 — 실 Google Places 키 연결은 아직 미검증(④).
- **개인화 코스 생성이 전부 서버 집행으로 바뀌었다.** 로그인 필수(샘플
  체험만 예외), 클라이언트가 만든 멱등키로 재시도해도 실제 작업을
  중복 실행하지 않음, 계정당 동시 생성 잠금(같은 계정이 동시에 두
  요청을 보내도 하나만 진행), 시간당 시도 횟수 제한, 그리고 **무료체험은
  실제 경로 계산이 성공했을 때만(`routedReal===true`) 딱 한 번
  차감** — 추정(직선거리) 결과로 대체됐을 때는 차감하지 않아서 재시도가
  계속 무료로 가능하다. 이 과정에서 "좌표 없는 곳이 정거장 목록에
  순서·구간 없이 잘못 끼어드는" 실제 버그를 새 테스트로 찾아 고쳤다
  (`server/routes/course-generation.mjs`의 좌표 필터링).
- 걸어서 도는 코스는 이제 **Google Routes(WALK) 서버측 어댑터**로
  실제 경로를 계산한다(기존 공개 OSRM 데모 URL 방식은 폐기 —
  실서비스 트래픽용이 아니었고, `/trip` 파라미터 위험도 있었다).
  방문 순서는 비용 없는 최근접 이웃 방식으로 우리가 먼저 정하고,
  Google Routes에는 그 순서 그대로 딱 한 번만 요청해 실제 구간
  거리·시간을 받는다(정렬 자체를 API에 맡기지 않음 — 도보 모드에서
  지원 여부·과금 등급이 불확실했기 때문). 말이 안 되는 속도의 응답은
  실제 경로로 인정하지 않고 추정으로 대체한다. **이 세션은
  `developers.google.com`으로 나가는 네트워크가 막혀 있어(EGRESS_BLOCKED)
  공식 문서를 다시 확인하거나 실제 키로 성공 응답을 받아보지
  못했다** — 요청 형태는 계약 테스트(`server/test/provider-contracts.test.mjs`)
  로 검증했지만 실제 연결은 미검증(④).
- 로그인 코드 이메일은 **Resend** 어댑터로 실제 API를 호출하는 코드를
  작성했다(`POST https://api.resend.com/emails`). 발송 실패 시
  방금 만든 로그인 코드를 되돌려 재사용 못 하게 하고, 쿨다운·IP
  레이트리밋·연속 실패 잠금까지 갖췄다. 실제 키로 진짜 이메일이
  도착하는지는 미검증(④, 같은 이유로 `resend.com` 문서도 이 세션에서
  못 열어봤다).
- 결제는 **토스페이먼츠** 결제창+서버 승인 연동 코드를 작성했다 —
  서버가 먼저 주문(금액·주문번호)을 만들고, 결제창은 그 주문으로만
  진행되며, 승인 API 호출 전에 서버가 직접 주문 소유자·금액을 다시
  확인한다(클라이언트가 준 금액을 그대로 믿지 않음). 웹훅은 페이로드를
  그대로 믿지 않고 토스 조회 API로 다시 확인한 뒤에만 반영한다. **이
  세션은 `docs.tosspayments.com`으로 나가는 네트워크가 막혀 있어
  공식 스펙(인증 방식·쿼리·이벤트 처리)을 다시 확인하지 못했다** —
  학습 시점 기억으로 작성했고, 실제 클라이언트 키·시크릿으로 결제창이
  뜨는지는 미검증(④).
- **운영(production) 환경에서는 테스트/모의 기능이 확실히 차단된다.**
  결제·이메일에 필요한 시크릿이 없으면 서버 자체가 부팅을 거부한다
  (`assertBootReady` — 실제로 자식 프로세스를 띄워 종료코드 1을
  확인했다). 장소조회·경로 키가 없으면 부팅은 막지 않되 그 기능만
  정직하게 "unavailable"로 표시한다(가짜 응답으로 대체하지 않음).
  개발용 결제 시뮬레이션 엔드포인트는 production에서 라우트 자체가
  등록되지 않는다(호출 자체가 불가능 — 내부 조건문으로만 막는 게
  아니라 아예 없음). "키가 있다"와 "실제로 연결이 확인됐다"도
  `/api/health`에서 서로 다른 필드(`services` vs `verified`)로
  구분해 보여준다.
- 계정별 장소 보관함·날짜별 일정을 서버에 저장하고(`/api/places`,
  `/api/courses`), 로그인 시 이 기기의 손님 데이터와 다른 기기에
  이미 있던 데이터를 둘 다 잃지 않게 병합하며, 로그아웃 시 이
  기기에서 로컬 데이터를 지워 다음에 로그인하는 계정과 섞이지 않게
  한다 — 전부 실제 브라우저(Chromium)로 로그인→병합→로그아웃→다른
  계정 로그인→데이터 미노출→재로그인→복원까지 종단 검증했다
  (`scripts/test-account-sync.mjs`).

## 3. 비용 — 무엇이 얼마나 드는가

### 3-0. 이 절을 읽기 전에 — 숫자의 신뢰 수준

공급자가 확정돼(토스페이먼츠·Resend·Google Places+Routes) 이번에는
"확인 필요"라고만 적지 않고 실제로 계산까지 해 본다. 하지만 정직하게
밝혀야 할 제약이 있다: **이 세션은 outbound 네트워크가 막혀 있어
(EGRESS_BLOCKED) 세 공급자의 공식 가격표 페이지를 이번에도 열어보지
못했다**(`mapsplatform.google.com`, `resend.com`,
`tosspayments.com` 모두 시도했고 전부 차단됨). 아래 단가는 **학습
시점 기억에 남아 있는 대략적인 자릿수**이지, 지금 이 순간의 공식
고시 가격이 아니다 — 실제 계약 전 반드시 각 공식 페이지에서
재확인해야 한다. 이 제약을 감안해 아래 표는:

1. **단가를 변수로 두고 사용량(요청 건수)을 먼저 정확히 계산**한다
   (이 부분은 지금 코드의 실제 설계로부터 나온 확정값이다 — 지어낸
   게 아니다).
2. 학습 기억 기준 **자릿수 추정 단가**를 참고용으로 병기하되, "약
   얼마 이하일 가능성이 높다" 수준의 범위로만 제시하고 "정확히
   얼마"라고 단정하지 않는다.
3. 실제 계약 시점에 확인한 진짜 단가를 이 표의 빈칸에 넣기만 하면
   바로 실제 비용이 나오게 구조를 짜 뒀다.

### 3-1. 요청 건수 — 실제 코드 설계에서 나온 확정값

지금 코드(`server/rate-limit.mjs`, `server/routes/course-generation.mjs`,
`server/adapters/routing.mjs`)의 실제 동작 기준:

| 사용자 행동 | 실제로 나가는 외부 API 호출 |
|---|---|
| 저장 장소 최초 가져오기(위치 불확실 후보 확인) | 장소 1곳당 Google Places 요청 **최대 1건**(위치가 이미 확인된 곳은 0건 — 짐작 유형·주소만으로 이미 확정된 곳은 다시 안 부른다) |
| 이후 개별 재조회("서버로 위치 후보 찾아보기" 버튼) | 누른 횟수만큼 Google Places 요청 1건씩(10분 캐시 안에 같은 질의면 0건) |
| 코스 생성·재계산 1회 | Google Routes(`computeRoutes`) 요청 **보통 1건**(방문 순서는 비용 없는 로컬 계산으로 먼저 정하고, 실제 구간 거리·시간만 API에 묻는 설계 — 정거장이 **25곳을 넘으면** 경유지 상한 때문에 여러 번의 연결된 호출로 나뉜다: `ceil((정거장 수 − 1) / 25)`건. 하루 코스는 보통 한 자리~십수 곳이라 대부분 1건이지만, 여러 날짜를 한 코스로 묶는 등 정거장이 많은 경우는 늘어날 수 있다 — `server/adapters/routing.mjs`의 세그먼트 분할 로직, `docs/RELEASE_STATUS.md` 참고) |
| 로그인 1회(코드 요청) | Resend 이메일 발송 1건 |
| 결제 승인 1건 | 토스페이먼츠 거래 수수료 1건 |

**사용량 상한(이미 코드로 구현·검증됨 — 예전엔 계정별 호출 횟수 제한이
전혀 없었다는 지적이 이번에 해소됐다)**: 초기 가져오기 일일 한도(`PLACE_LOOKUP_IMPORT_DAILY_LIMIT`,
기본 400)와 재조회 일일 한도(`PLACE_LOOKUP_REQUERY_DAILY_LIMIT`,
기본 60)를 분리했고, 코스 생성도 시간당 한도(`GENERATION_RATE_LIMIT_PER_HOUR`,
기본 10)가 있다. 전부 환경변수라 계약 후 실제 단가를 보고 숫자를
조정할 수 있다.

### 3-2. 사용자가 지정한 세 시나리오(저장 50/160/300곳 × 월 코스
생성 10/30/50회)의 요청 건수 계산

**가정(명시)**: 최초 가져오기 시 장소 전부가 위치 확인이 안 된
상태라고(최악의 경우로) 가정한다 — 실제로는 링크에 좌표가 이미 있는
곳은 0건이라 실제 값은 이보다 작거나 같다. 재조회는 저장 장소 수의
10%를 한 달에 한 번씩 다시 확인한다고 가정한다(이 숫자는 실제 사용
패턴 관찰 전까지의 임의 가정 — 4절 "확인 안 된 가설"에도 동일하게
표시).

| 저장 장소 수 | 최초 가져오기 Places 요청(1회성) | 월 재조회 Places 요청(가정) |
|---|---|---|
| 50곳 | 최대 50건 | 약 5건/월 |
| 160곳(제작자 실제 사례) | 최대 160건 | 약 16건/월 |
| 300곳 | 최대 300건 | 약 30건/월 |

| 월 코스 생성 횟수 | 월 Google Routes 요청 |
|---|---|
| 10회 | 10건 |
| 30회 | 30건 |
| 50회 | 50건 |

무료체험(가입 후 첫 실제 경로 성공 1회)은 위 "월 코스 생성" 중 1건을
대체할 뿐 추가 요청을 만들지 않는다 — 실패(추정) 결과는 체험을 안
쓰므로 사용자가 재시도하면 그만큼 Routes 요청이 추가될 수 있다는
점만 유의(성공할 때까지 재시도 횟수는 예측 불가 — 지어내지 않는다).

### 3-3. 단가(5차 갱신 — 실제 요청 필드 기준 등급으로 바로잡음)와
9,900원 이용권 1건의 원가 그림

**5차 갱신 핵심**: 3차/4차 문서는 Google Places 단가를 "가장 싼
등급"이라는 학습 기억으로 약 15원/건으로 추정했다. ChatGPT가 지적한
대로, 우리 코드가 실제로 요청하는 필드마스크(`places.id`,
`places.displayName`, `places.location`, `places.formattedAddress`)는
**Text Search Pro 등급**에 해당하고 가장 싼 등급이 아니다. 아래
표는 ChatGPT가 제시한 공식 첫 유료 등급 단가(이 세션이 직접
`mapsplatform.google.com`에 접속해 재확인한 것은 아니다 — 여전히
EGRESS_BLOCKED, 5-1절 참고)를 그대로 코드(`server/config.mjs`의
`buildCostEstimateMicros`)에 반영한 결과다. **공식 등급·달러 단가·
계산용 환율·안전 여유를 서로 다른 값으로 명확히 나눴다** — 안전
여유(15%)는 예산 상한에만 적용하고, 실제 원가 계산(이 표)에는
안전 여유를 안 섞은 순수 단가만 쓴다(부풀려진 숫자로 원가를 낮게
착각하지 않기 위해).

| SKU | 공식 첫 유료 등급 단가(ChatGPT 제공, 이 세션 미재확인) | 계산용 환율(가정, 실시간 아님) | 원화 환산 단가 |
|---|---|---|---|
| Places Text Search, **Pro** 등급 | $32 / 1,000건 | 1,400원/$ | **약 44.8원/건** |
| Routes computeRoutes, **Essentials** 등급(경유지 11개 미만) | $5 / 1,000건 | 1,400원/$ | **약 7원/건** |
| Routes computeRoutes, **Pro** 등급(경유지 11개 이상 — `ROUTES_HIGH_VOLUME_THRESHOLD`) | $10 / 1,000건 | 1,400원/$ | **약 14원/건** |

| 항목 | 확인해야 할 곳 |
|---|---|
| 위 세 SKU의 실제 등급명·단가 | Google Maps Platform 공식 가격표 — 이 세션은 여전히 접속 불가, 계약 전 반드시 사람이 직접 재확인 |
| Google Maps Platform 월 무료 사용량 | 과거 월 정액 크레딧에서 SKU별 무료 사용량 방식으로 바뀌었을 가능성 — "0원일 수도 있다" 이상으로 단정하지 않는다 |
| 토스페이먼츠 카드 결제 수수료 | 일반(미계약) 요율 기준 9,900원의 몇 퍼센트대로 기억(정확한 요율 불확실) — 토스페이먼츠 가맹 계약 시 실제 고지 요율 |
| Resend 이메일 발송 | 소규모 발송량은 무료 등급 가능성 — 정확한 일일/월 한도는 Resend 공식 가격표에서 확인 |

**9,900원 이용권 1건의 원가 계산(포함/제외 항목을 명시한다)**:

```
원가 = (토스 결제 수수료 1건)                              [포함 — 위 표의 추정 요율]
     + (Resend 발송 단가 × 이 손님의 30일간 로그인 횟수)     [포함 — 추정 단가]
     + (Places Text Search Pro 단가 × 최초 가져오기 건수 + 재조회 건수) [포함 — 44.8원/건]
     + (Routes 단가 × 30일간 실제 생성·재계산 횟수, 경유지 수에 따라 7원 또는 14원/건) [포함]

제외(이 계산에 안 들어감, 별도 항목): 서버·DB 호스팅비(계정 수와
무관하게 나가는 고정비라 "이용권 1건당 원가"에 나누어 넣지 않았다 —
6절에서 별도로 다룬다), 환불 처리 자체의 운영 비용(사람이 처리하는
시간 등 — 지금은 0으로 가정), Google Maps Platform의 무료 사용량
크레딧(있다면 원가를 낮추는 방향이지만, 정책을 확인하지 못해 0원으로
가정 — 보수적 가정).
```

**세 시나리오(3-2절 건수 × 위 정확화된 단가)의 실제 계산 — 단가
자체는 아직 이 세션이 공식 문서로 재확인 못 했지만("확인해야 할 곳"
표 참고), 최소한 "가장 싼 등급이 아니라 Pro 등급"이라는 등급 자체는
반영된 계산이다(4차의 "약 15원/건" 추정보다 훨씬 근거 있는 수치)**:

**⚠ 6차 갱신 — 아래 표는 "이용권 사용량에 한도가 없다고 가정했을 때"의
낡은 계산이다.** 5차 시점엔 코스 생성·위치 조회 횟수 자체에 상한이
없어서 "저장 300곳·월 50회 재계산"이 실제로 가능한 사용 패턴이었다.
**6차에서 유료 이용권에 실제 사용량 한도(위치 확인 최대 50곳+코스
생성 최대 30회, 30일 기준 — `server/entitlement-usage.mjs`)를
집행했으므로, 아래 "300곳·월 50회"(=330건 조회) 시나리오는 이제
한 이용권 기간 안에서 물리적으로 불가능하다**(50건을 넘는 순간
서버가 그 자리에서 위치 확인을 거부한다 — 5절 참고). 이 표는 "한도를
두기 전에는 이런 헤비유저가 존재할 수 있었다"는 **역사적 근거**로만
남겨 두고, 실제로 지금 가능한 최악의 경우는 바로 아래 3-3-1절의
새 표를 봐야 한다. **또한 아래 "9,900원 대비" 칸의 표현을 6차에서
고쳤다** — 이 계산은 결제 수수료·장소/경로 API 원가만 뺀 것이지
서버 호스팅비·이메일·무료 체험 손님 비용·환불·세금을 전혀 안 뺀
숫자라, "흑자/적자"라는 말은 실제 손익을 뜻하는 것처럼 오해를 줄 수
있어 쓰지 않는다 — 대신 "매출 − 표에 포함된 변동비"라는 좁은
의미의 차액으로만 표시한다:

| 시나리오(한도 도입 전 가정 — 이제 실제로는 불가능할 수 있음) | Places 조회 원가(건수×44.8원) | Routes 계산 원가(건수×7원, Essentials 가정) | 토스 수수료(3% 가정) | Resend(무료 가정) | **표에 포함된 변동비 합계** | 매출(9,900원) − 위 변동비 (이윤이 아님 — 아래 주석) |
|---|---|---|---|---|---|---|
| 50곳 · 월 10회 | 55건 = 약 2,464원 | 10건 = 약 70원 | 약 297원 | 약 0원 | **약 2,831원** | +약 7,069원 |
| 160곳(제작자 실사례) · 월 30회 | 176건 = 약 7,885원 | 30건 = 약 210원 | 약 297원 | 약 0원 | **약 8,392원** | +약 1,508원 |
| 300곳 · 월 50회(6차 이전 가정 — 지금은 이용권 한도로 물리적으로 불가능할 수 있음) | 330건 = 약 14,784원 | 50건 = 약 350원 | 약 297원 | 약 0원 | **약 15,431원** | −약 5,531원(변동비가 매출 초과) |

**"매출 − 변동비"는 이윤·순이익·흑자가 아니다** — 이 표에 포함된
항목은 결제수수료·Places/Routes API 원가뿐이다. **서버 호스팅비,
이메일(Resend), 결제 안 하는 무료 체험 손님의 비용, 환불, 세금은 이
표 어디에도 포함돼 있지 않다**(각 항목이 포함/제외됐는지는 매 계산마다
명시한다는 원칙 — 6절·3-3-1절 참고). 이 넷을 반영하면 실제 순이익은
이 표의 숫자보다 항상 더 낮다.

**참고 — 이제는 역사적 배경으로만 남긴 4차 문서의 낙관 오류**: 4차
문서는 Places 단가를 실제보다 약 3분의 1 수준으로 낮게 잡아 "가장
비싼 시나리오도 원가 5,650원으로 남는 장사"라고 적었었다. 5차에서
정확한 단가(44.8원/건)로 다시 계산하자 300곳·월 50회 시나리오가
매출을 초과한다는 게 드러났고, 6차에서는 애초에 그런 사용량 자체를
이용권 한도로 못 만들게 막았다(아래 3-3-1절).

이 표는 **"장소 조회 원가가 이용권 원가의 대부분을 차지한다"는 구조를
보여주기 위한 것**이지, 확정 원가표가 아니다 — 위 계산의 전제(Places·
Routes 등급별 정확한 실제 단가, 토스 수수료율, Google 무료 크레딧
유무)가 전부 미검증이라는 걸 다시 강조한다. **확정된 것은 3-2절의
"건수"뿐이고, 3-3절의 "단가"는
전부 추정**이다 — 이 둘을 섞어 계산한 위 표의 "원가"도 당연히
추정치다. 실제 계약 후 단가만 갱신하면 이 표 구조 그대로 진짜 원가가
나온다.

### 3-3-1. 6차 갱신 — 이용권 한도가 실제로 씌워진 뒤의 진짜 최악 원가

**핵심: "저장 개수"·"실제 유료 조회 건수"·"경로 요청 건수"·
"실패·재시도 건수"는 서로 다른 변수이고, 각각 따로 계산해야 한다**
(지시 5절 반영 — 이 넷을 하나로 뭉뚱그려 "300곳 저장 = 300건 조회
원가"처럼 계산하던 5차까지의 방식이 오해를 만들었다):

- **저장 개수(storage count)** — `PUT /api/places`에 들어 있는
  장소 배열 길이. **몇 곳을 저장하든 그 자체는 0원이다**(가져오기
  자체는 유료 API를 안 부른다 — `server/test/reliability-and-cost.test.mjs`
  로 이미 확인된 사실, 아래 3-2절 첫 행). 300곳을 저장한 손님도
  실제로 위치 확인을 한 번도 안 누르면 원가는 0원이다.
- **실제 유료 위치 조회 건수(billable lookup count)** — 저장 개수와
  무관하게, **엔타이틀먼트 한도가 실제로 씌우는 값**이다:
  무료체험 계정은 평생 최대 10곳, 유료 이용권은 30일 기간당 최대
  50곳(`config.entitlementUsage`). 이미 위치가 확인된 장소를 다시
  조회해도(재확인·재수입 등) 이 한도를 또 깎지 않는다(영구
  dedupe — `entitlement_place_confirmed`).
- **경로 요청 건수(route request count)** — 코스 생성 성공 횟수와도
  다르다: 정거장이 25곳을 넘으면 한 번의 코스 생성이 여러 건의 Routes
  호출로 나뉜다(3-1절). 코스 생성 성공 자체는 무료체험 평생 1회,
  유료 30일 기간당 최대 30회로 한도가 씌워진다.
  (`config.entitlementUsage.paidCourseLimit`).
- **실패·재시도 건수(retry count)** — **이용권 한도의 보호를 안
  받는 유일한 변수다.** 실패(추정 결과)·재조회·타임아웃 재시도는
  "성공"이 아니라서 고객에게 약속한 사용 횟수는 안 깎지만, 서버가
  실제로 외부 API를 부르는 건 맞아서 **진짜 회사 비용은 그대로
  든다.** 이 변수만은 고객 약속(엔타이틀먼트)이 아니라 **내부 비용
  안전상한**(`config.costSafetyCap`, 6차 신규)이 유일한 방어선이다 —
  무료체험 계정 누적 700원, 유료 이용권 하나당 누적 3,500원을 넘어서는
  순간 그 이상의 실제 유료 호출 자체를 막는다(`server/cost-ledger.mjs`의
  `chargeCostBatch`, `server/test/cost-safety-cap.test.mjs`).

**이 넷을 분리해서 계산한 5가지 시나리오**(요청 5절이 지정한 시나리오
그대로):

| 시나리오 | 저장 개수 | 실제 유료 조회 건수 | 코스 생성 성공 건수 | 계산(원가) | 비고 |
|---|---|---|---|---|---|
| 300곳을 저장했지만 실제 위치 확인은 10건만 함 | 300곳 | 10건 | 0회(위치 확인만, 코스 미생성) | 10 × 44.8원 = **약 448원** | 저장 개수는 원가에 전혀 영향 없음을 보여줌 — 5차까지의 "300곳=14,784원" 계산은 "300곳을 전부 조회했다"는 가정이 만든 착시였다 |
| 유료 이용권 하나가 한도(위치확인 50+코스 30)를 전부 소진 | 무관(50곳 이상) | 50건(한도 최대치) | 30회(한도 최대치) | 50×44.8 + 30×7 = 2,240 + 210 = **약 2,450원** | 이게 **엔타이틀먼트 한도만으로 정해지는, 실패·재시도가 전혀 없을 때의 이론적 최댓값**이다. 9,900원 매출 대비 약 7,450원의 표-포함-변동비 차액(흑자 아님, 위 주석과 동일 원칙) |
| 재방문 손님이 이미 확인된 장소를 재사용(신규 조회 0건) | 저장 300곳(전부 기존 확인 장소) | **0건**(전부 재사용 — 영구 dedupe로 미차감) | 10회 | 10 × 7원 = **약 70원** | "재방문 여행자 지원"이 실제로 원가를 낮추는 방향으로 작동함을 보여줌 — 재방문 손님은 오히려 원가가 가장 낮은 축에 든다 |
| 무료체험 가입자가 많고 유료 전환율이 낮음(예: 가입 100명 중 5명만 결제) | 계정별 상이 | 계정당 최대 10건(무료 한도) | 계정당 최대 1회(무료 한도) | 계정 1명 최악 = 10×44.8+7 = **약 455원**, 가입 100명이 전부 한도까지 다 쓰면 최악 총액 = 100×455원 = **약 45,500원**(매출 0원) | 이게 R6-4(안전상한 700원)가 실제로 계산했던 "무료체험 최악치 ≈455원"과 일치 — 700원 상한 안에 여유 있게 들어옴. 하지만 **전환율이 낮을수록 이 무료 비용의 총합이 순수 비용**이라는 점은 그대로다(4절 "확인 안 된 가설" 참고) |
| 실패·재시도가 늘어나는 경우(경로 분할 포함) | 무관 | 성공 50건(한도) + 실패/재시도 N건 | 30회(한도, 실패는 미차감) | 최소 2,450원(위 이론적 최댓값) + 실패·재시도 비용, 단 **내부 안전상한(3,500원)에서 그 이상의 실제 호출을 강제로 막음** | 실패·재시도가 아무리 늘어나도 이 이용권 하나의 실제 비용은 **3,500원을 넘을 수 없다**(구조적 상한 — `server/test/cost-safety-cap.test.mjs`로 확인) |

**결론 — 6차 이전과 달라진 것**: 5차까지는 "이용권 사용량에 실질적
상한이 없어서, 헤비유저 한 명이 원가를 매출보다 크게 만들 수 있다"는
게 실제 위험이었다. 6차에서 이용권 사용량 한도(엔타이틀먼트)와 내부
비용 안전상한을 함께 도입한 결과, **유료 이용권 하나의 실제 원가는
이제 이론적으로도(엔타이틀먼트 기준) 약 2,450원, 실패·재시도까지
감안한 절대 상한(안전상한 기준)으로도 3,500원을 넘지 않는다** — 이
숫자와 9,900원 매출의 차액(표에 포함된 항목 기준 약 6,400~7,450원)을
"흑자"라고 부르지 않는 이유는 위 주석과 같다(서버 호스팅비·이메일·
무료 체험 손님 비용·환불·세금 전부 미포함). **다만 안전상한 자체가
충분한지는 별개 질문이다** — 3,500원 상한이 30회 코스 생성을
정상적으로 다 제공하기에 부족하면(즉 정상 사용만으로 상한에 먼저
닿으면) 그건 "손님이 약속받은 걸 다 못 받는" 문제이므로, 위 표의
"이론적 최댓값 2,450원 < 안전상한 3,500원"이라는 여유(약 1,050원)가
계속 유효한지 실제 단가 확정 후 다시 계산해 확인해야 한다.

**무료 사용자(체험 1회만 쓰고 결제 안 함)의 비용 — 6차 갱신, 이용권
한도 반영 후 다시 계산**: 5차까지는 무료 체험 손님이 저장한 장소
수만큼 전부 위치 확인을 할 수 있다고 가정해 "300곳 저장 = 약
13,447원"이라는 표를 실었다. **6차에서 무료체험 계정에도 위치 확인
한도(평생 최대 10곳, `config.entitlementUsage.freePlaceLookupLimit`)를
실제로 씌웠으므로, 저장 개수와 무관하게 무료 체험 손님 한 명의 실제
유료 조회 원가는 이제 "최대 10건"으로 고정된 상한이 있다**:

| 항목 | 계산 | 비고 |
|---|---|---|
| 무료체험 1명 최악 원가(위치확인 10건 + 코스 1회) | 10×44.8원 + 7원 = **약 455원** | 저장 개수(50곳이든 300곳이든)와 무관 — 3-3-1절 시나리오 4와 동일 계산. 내부 비용 안전상한(700원)보다 낮아 상한이 정상적으로 여유를 두고 있음 |
| 가입 100명, 전부 한도까지 다 씀(현실적 상한 없음, 최악 가정) | 100×455원 = **약 45,500원**(매출 0원) | 무료→유료 전환율이 낮을수록 이 비용의 총합이 순수 회사 부담이라는 점은 그대로다 — 정확한 전환율은 4절대로 검증 전 |

**즉 6차부터는 "저장 장소가 많은 무료 체험자"라는 이유만으로 원가가
치솟지 않는다** — 위치 확인 한도가 저장 개수와 완전히 분리돼 있기
때문이다(지시 1절 "저장 개수와 실제 조회 횟수를 분리하라"를 그대로
반영한 구조). 남는 진짜 위험은 "가입자 수 × 낮은 전환율"이지 "가입자
1명이 저장을 얼마나 많이 했는가"가 아니다 — **이 비용 구조 때문에
무료체험 한도(`ENTITLEMENT_FREE_PLACE_LOOKUP_LIMIT` 등)와 내부 비용
안전상한(`COST_SAFETY_CAP_FREE_KRW_MICROS`, 6차 신규)이 단순한 남용
방지 그 이상으로 실제 예산 방어선 역할을 한다**는 점을 분명히 해 둔다.

**무료 구간 적용 전/후 구분**: Google Maps Platform에 월 무료
사용량이 있다면(3-3 표 참고, 정책 자체가 불확실) 그 구간 안에서는
위 표의 Places·Routes 원가가 0원에 가깝고, 그 구간을 넘긴 뒤부터
표의 단가가 실제로 적용된다. 이 문서는 **무료 구간이 없다고
가정한 보수적(최악) 시나리오**로 위 표를 계산했다 — 실제로는 이보다
쌀 가능성이 있지만, 비쌀 가능성은 낮다(정책이 지금보다 더 나빠지는
쪽으로 바뀔 근거는 없다).

### 3-3-2. 7차 갱신 — 계정별 하루 비용 한도가 위 이론적 최댓값과 충돌하던 버그를 고침

**6차까지는 위 3-3-1절의 "이론적 최댓값 2,450원"이 실제로는 하루 안에
받을 수 없는 값이었다** — 계정별 하루 비용 한도(`costBudget.
perAccountDailyMicros`, 기본 500원)가 무료/유료 구분 없이 똑같이
적용됐기 때문에, 위치확인 단가(약 44.8원) 기준 하루에 약 11건만
쓰면 그날은 더 이상 위치 확인이 안 됐다. 유료 손님이 "하루 안에
50곳을 몰아서 확인"하려 하면(예: 여행 출발 전날 한꺼번에 정리하는
흔한 사용 패턴) 실제로는 여러 날에 나눠 써야만 하는 결과가 됐다 —
**이건 의도한 정책이 아니라, 무료체험 크기(10곳+코스1회 ≈ 500원
이내)에 맞춰 정한 값을 유료에도 그대로 재사용한 버그였다.**

7차에서 계정별 일일/월간 비용 한도가 이 계정의 이용권 기간 전체
누적 안전상한(무료 700원/유료 3,500원)보다 낮게 잡히지 않도록
고쳤다(`server/cost-ledger.mjs`). 그 결과 위 3-3-1절의 "이론적
최댓값(약 2,450원, 실패·재시도까지 감안한 절대 상한 3,500원)"이
**실제로 하루 안에도 받을 수 있는 값**이 됐다 — 다만 **이용권 기간
(30일) 전체 누적 총량은 그대로 3,500원 이하로 유지**된다(하루 안에
몰아 쓸 수 있을 뿐, 매일 3,500원씩 새로 받는 게 아니다).

**서비스 전체 하루/월간 비용 한도(`COST_GLOBAL_DAILY_KRW_MICROS`
기본 3,000원, `COST_GLOBAL_MONTHLY_KRW_MICROS` 기본 27,000원)는
이번 수정에서 건드리지 않았다** — 이건 개별 계정 문제가 아니라
회사 전체 예산 상한이라 ChatGPT가 판단할 사업 결정 영역이라고
보기 때문이다. 다만 계산상 참고할 점: 유료 손님 한 명이 하루 안에
전체 이용권 몫(약 2,450원)을 몰아 쓰면, **서비스 전체 하루 한도
(3,000원) 안에서는 그런 손님을 하루에 1명 정도만 감당**한다(그
이상 동시에 몰리면 전체 하루 한도에 먼저 걸려 그 이후 요청은
거부된다 — 개별 손님 잘못이 아니라 순전히 트래픽이 몰린 결과다).
**실제 유료 손님이 여러 명 생기고 이런 "몰아 쓰기"가 흔해지면, 이
전체 한도를 예상 동시 손님 수에 맞춰 올려야 한다** — 코드는 이미
환경변수로 조정 가능하게 돼 있고(`COST_GLOBAL_DAILY_KRW_MICROS`
등), 실제 숫자를 얼마로 올릴지는 실사용 데이터를 보고 ChatGPT와
함께 정할 사업 결정이다.

### 3-3-3. 7차 갱신 — 신규 장소 확인 한도 우회 차단(매출 누수 위험 해소)

ChatGPT가 실제로 재현한 우회: 무료 위치확인 한도를 1로 두고, 같은
클라이언트 장소 식별자에 검색어만 바꿔 보내면 서로 다른 실제 장소
6곳을 확인받고도 서버에 기록된 사용량은 1로만 남았다 — 즉 **이론상
무료체험 손님이 위치확인 한도를 무제한으로 우회해 유료 손님과 같은
가치를 공짜로 받을 수 있었다**(직접적인 매출 누수 위험). 7차에서
"신규 확인 여부"를 클라이언트가 불러주는 문자열이 아니라 공급자가
실제로 돌려준 장소 식별자로 재판정하도록 고쳤다(`server/entitlement-
usage.mjs`) — 같은 실제 장소를 재사용하는 정상적인 경우는 계속
비과금이지만, 실제로 다른 장소를 확인할 때마다 정직하게 한도가
깎인다. 사업적으로는 "무료체험이 무제한 위치확인 도구로 오용될 수
있었던 구멍을 막았다"는 뜻이다 — 광고 문구·판매 페이지에 별도로
반영할 내용은 없다(소비자에게 보이는 약속·가격은 그대로다).

### 3-3-4. 7차 신규 — 착장 판단용 날씨 카드(직접 비용 없음)

WeatherAPI.com 무료 등급(상업적 사용 허용, 월 100,000회, 공식
가격표 https://www.weatherapi.com/pricing.aspx 확인)으로 "오늘
동선" 화면에 날씨 카드를 추가했다. **이 기능 자체는 유료 계약이
없고 직접 비용이 0원이다**(무료 등급 안에서 동작). 서버가 지역
단위(~1km)로 캐시를 공유해 같은 지역을 여러 사용자가 봐도 실제
호출은 드물게 나가고, 서비스 전체 하루 호출 상한(`WEATHER_GLOBAL_
DAILY_CAP`, 기본 2,000회/일)도 걸어 뒀다 — 월 100,000회 한도를
지키기 위한 안전판이다. 이 한도가 실제 트래픽에 비해 너무 낮거나
높은지는 실사용 데이터로 나중에 조정하면 된다(코드 수정 없이
환경변수만 바꾸면 됨).

**가격 정책에 영향 없음** — 날씨는 무료(비회원) 사용자도 볼 수
있고, 위치확인·코스생성 이용권/비용 원장을 전혀 안 건드린다. 즉
이 기능을 판매 상품의 유료 항목으로 넣거나 가격에 반영할 필요가
없다 — 무료로 계속 제공해도 회사에 실질적 비용 부담이 없는
구조다.

### 3-3-5. 9차 신규 — 한도 소진 후 유료 검색 반복으로 인한 비용 상한 소진 위험 해소

ChatGPT가 지적한 위험: 이용권 한도를 다 쓴 계정이 새 검색어를 계속
보내면(재사용인지 신규인지는 실제 외부 호출 없이는 알 수 없으므로)
매번 실제 유료 Google Places 호출이 나가 비용 상한을 소진할 수
있었다 — "이미 확인된 실제 장소 재사용은 한도와 무관하게 공짜"라는
약속을 지키려다, 그 판정 자체에 필요한 외부 호출을 무제한 허용해
버린 것이다.

**해결**: 계정당 하루 "한도 초과 상태에서 시도해 볼 수 있는 횟수"에
작은 안전판을 뒀다(`entitlementOverLimitVerificationDailyLimit`, 기본
**20회/계정/일**). 이미 확인된 실제 장소 재사용(같은 로컬 슬롯+같은
검색 조건으로 이미 링크된 경우)은 이 안전판을 아예 거치지 않으므로
여전히 무제한 공짜다 — 이 안전판은 오직 "신규일 수도 있는 새 검색
시도" 횟수만 하루 단위로 제한한다.

**비용 영향(추정)**: 위치확인 단가 약 44.8원(3-3절) 기준, 계정당 하루
최대 약 20 × 44.8원 = **약 896원**의 추가 노출이 이론상 가능하다 —
단, 이건 "이용권 한도를 이미 다 쓴 계정이 매일 20건씩 새 검색을
반복하는 최악의 경우"이고, 실제로는 대부분 이용권 자체의 원가
안전상한(무료 700원/유료 3,500원 누적, 3-3절)이 먼저 걸린다. 이
20이라는 숫자는 확정 수치가 아니라 제안값이며, 실사용 데이터(정당한
재확인이 하루에 몇 건이나 필요한지)로 조정해야 한다.

**API 공급자 데이터 보관·캐시 조건**: 이 안전판·기존 로컬 링크
캐시(`entitlement_place_local_link`)가 Google Places API의 실제
"결과 보관·캐시 허용 기간" 정책과 맞는지는 이번 세션에서 공식
문서로 재확인하지 못했다(EGRESS_BLOCKED, 5-1절과 같은 제약). **이
안전판·캐시 구현이 "장소 정보를 무기한 자유롭게 저장해도 된다"는
승인은 아니다** — 실제 서비스 전 Google Places API 이용약관의 데이터
보관 조건을 사람이 직접 확인해야 한다(미검증 상태를 확인 완료로
표시하지 않는다).

### 3-4. 초기 운영 예산(월 5만원) 배분 제안 — 확정 아님

**5차 갱신 핵심 지적 반영**: "월 5만원은 초기 전체 운영 목표이며
전액 Google 예산이 아니다. 무료 구간 소진 후 원가와 무료 체험자
비용까지 계산하고, 유료 사용자가 늘었는데 전체 예산을 고정해 서비스를
계속 막는 방식도 피하라"는 지시에 따라, 이 절은 **① 초기 비용
상한**과 **② 매출 증가 시 예산을 늘리는 기준**을 명확히 구분해서
정리한다 — 이전 문서(4차까지)는 이 둘을 구분하지 않고 "월 5만원 →
Google 예산 3만원"이라는 고정값 하나만 제시했었다.

**월 5만원 목표를 고정비와 Google 예산으로 나누는 배분(가정)**:

| 항목 | 성격 | 월 예상액 | 근거 |
|---|---|---|---|
| 서버 호스팅(작은 VM 또는 컨테이너 1대) | 고정비 — **가정치**(실제 견적 아님) | 약 5,000~15,000원 | 국내외 소규모 Node.js 호스팅사의 최저가형 요금제 자릿수 추정(정확한 사업자·요금제 미정이라 확인 안 됨) |
| DB 백업(서버가 실제로 켜지면 필요 — 6절 4번) | 고정비 — **가정치** | 약 0~3,000원 | 파일 기반 SQLite를 별도 스토리지에 주기적으로 복사하는 정도로 가정 — 실제 백업 대상(오브젝트 스토리지 등) 미정 |
| Resend 이메일 | 고정비에 가까움(소량은 무료 등급 가능성) | 약 0원(가정) | 3-3절 참고 — 무료 등급 정확한 한도는 미확인 |
| 토스페이먼츠 | 고정비 아님(거래 건당 변동비, 이미 위 원가 계산에 포함) | — | 3-3절 참고 |
| **고정비 소계(가정)** | | **약 5,000~18,000원** | |
| **Google API(Places+Routes) 예산 — 남는 금액** | | **약 32,000~45,000원** | 5만원 − 위 고정비 가정 |

**① 초기 비용 상한(코드에 실제로 반영된 값)**: `server/config.mjs`의
`costBudget.globalMonthlyMicros` 기본값은 **27,000원/월**이다 — 위
Google 예산 범위(약 32,000~45,000원)의 하단보다도 낮게, 안전 여유
15%(`costSafetyMarginRatio`)를 적용해 보수적으로 잡았다(고정비 가정이
빗나갈 여지, 예상치 못한 SKU 추가 호출 등을 대비). **이건 "서비스
전체가 한 달에 쓸 수 있는 절대 상한"이고, 이 한도에 도달하면
`isServiceUnavailableForNewSales`(R5-4 항목)가 신규 결제 자체를
막는다** — 이미 결제한 손님의 이용권은 안 건드린다.

**이 초기 상한으로 몇 명을 감당할 수 있는가 — 6차 갱신: 이용권 한도
도입 후에는 "헤비유저"의 정의 자체가 바뀐다.** 5차까지는 손님이
저장·재계산을 얼마든지 반복할 수 있어 "300곳·월 50회"급 사용자가
실제로 나올 수 있었다. 6차부터는 유료 이용권 하나가 30일 동안 실제로
쓸 수 있는 최댓값이 위치확인 50건+코스 30회로 못 박혀 있으므로,
**"한 이용권이 낼 수 있는 최악의 원가"는 이제 하나의 숫자(약
2,450원, 실패·재시도까지 넣어도 안전상한 3,500원)로 수렴한다**
(3-3-1절). 이 상한 기준으로 다시 계산하면:

| 유료 손님 유형 | 30일 원가 | 27,000원 예산으로 감당 가능한 명수 |
|---|---|---|
| 가벼운 사용(위치확인 10건+코스 5회 정도) | 약 483원 | 약 55명 |
| 이용권 한도를 전부 소진(위치확인 50건+코스 30회, 이론적 최댓값) | 약 2,450원 | 약 11명 |
| 실패·재시도까지 겹쳐 안전상한에 도달(구조적 절대 최댓값) | 약 3,500원 | 약 7명 |

**이 표가 뜻하는 것**: 이용권 한도 도입 전(5차까지)에는 "300곳·월
50회급 헤비유저 1명이 예산을 통째로 위협"할 수 있었지만, 6차부터는
**한 이용권이 낼 수 있는 최악의 원가 자체가 3,500원으로 구조적으로
막혀 있어서, 27,000원 예산으로 최소 약 7명은 "무슨 일이 있어도"
감당할 수 있다는 하한선이 생겼다.** 다만 이 계산도 Places/Routes
단가가 지금의 추정치(3-3절)와 실제로 얼마나 다른지에 따라 달라진다
— 실제 계약 단가 확정 후 반드시 다시 계산해야 한다. 계정별 일일/월간
한도(`COST_PER_ACCOUNT_DAILY_KRW_MICROS`,
`COST_PER_ACCOUNT_MONTHLY_KRW_MICROS`, 5차 신설)와 이번 6차의 내부
비용 안전상한은 서로 다른 층위의 방어선이다 — 전자는 하루/한 달
단위의 속도 제한, 후자는 "이 이용권 하나가 평생(30일 기간 동안) 낼 수
있는 절대 최댓값"이다.

**② 매출 증가 시 예산을 조정하는 기준(고정하지 않는다)**: "유료
사용자가 늘었는데 전체 예산을 고정해 서비스를 계속 막는 방식도
피해야 한다"는 지시에 따라, 이 문서는 27,000원을 **영구 고정값이
아니라 초기 안전값**으로 규정한다. 유료 손님 수가 늘면 다음 규칙으로
`COST_GLOBAL_MONTHLY_KRW_MICROS`를 올릴 것을 제안한다(확정 아님 —
실제 결정은 매출이 실제로 들어온 뒤 사업 쪽에서):

```
다음 달 Google 예산 제안 = (이번 달 실제 유료 결제 건수 × 9,900원 × 손님당
                            평균 원가 비율(3-3절 기준 약 30~150%)) × 1.2(여유)
```

즉 **"이번 달 실제로 들어온 매출에 비례해 다음 달 예산을 올린다"**는
원칙이다 — 매출과 무관하게 27,000원을 영원히 고정하면, 유료 손님이
늘어도 서비스가 계속 막히는(가장 나쁜) 상황이 된다. 반대로 매출
증가 없이 예산만 무한정 올리면 회사가 적자를 떠안는다 — 그래서
"매출에 비례한 조정"을 원칙으로 제안한다. 실제 조정 주기(매달/분기)
와 승인 절차는 사업 쪽에서 정할 결정 사항으로 남긴다(5-2절).

**경로·이메일 등 다른 외부 호출 비용도 검토했는가**: 그렇다 — 위
계산에 Resend(이메일)와 Google Routes(경로)를 전부 포함했다. Places가
가장 큰 비중을 차지하는 이유는 단가 자체보다 **건수가 압도적으로
많기 때문**이다(코스 생성은 계정당 월 수십 건이지만, 장소 조회는
저장 목록 규모(수백 건)에 비례한다).

### 3-5. 제안 — 사용 한도 (확정 아님, 검토용 제안 — 갱신)

**이 숫자들은 개발 담당이 엔지니어링 안전장치로 제안하는 값이지,
사업적으로 확정된 한도가 아니다.** 실제 값은 ChatGPT/사용자가 정할
몫이다. 2차 갱신 때의 제안("코스 생성 30일 N회", "위치 조회 하루
M회")은 사용자가 명시적으로 반려했다 — "위치 조회 하루 30회"로
묶으면 후쿠오카 160곳을 처음 정리하는 사용자부터 막힌다는 이유였다.
그래서 이번에는 **초기 가져오기와 이후 재조회를 애초에 다른 값으로
분리해 코드로 구현**했다(3-1절) — 이제 남은 결정은 "그 분리된 두
값과 코스 생성 한도를 각각 얼마로 둘지"뿐이다.

- **코스 생성·재계산**(`GENERATION_RATE_LIMIT_PER_HOUR`, 지금 기본값
  시간당 10): 지금 값은 "동시 다발적 남용을 막는 임시 안전판"이지
  사업적으로 설계된 월간 한도가 아니다. 30일 단위로 다시 볼지, 지금의
  시간당 한도로 충분한지는 실제 초기 체험단(5~10명) 관찰 후 정하는
  게 안전하다.
- **초기 가져오기**(`PLACE_LOOKUP_IMPORT_DAILY_LIMIT`, 기본
  400/일): 300곳을 하루 안에 다 정리해도 안 막히도록 넉넉하게 잡은
  값 — 후쿠오카 160곳 사례를 실제로 통과시킬 수 있는지 기준으로
  골랐다.
- **재조회**(`PLACE_LOOKUP_REQUERY_DAILY_LIMIT`, 기본 60/일): 하루에
  같은 계정이 "위치 확인" 버튼을 60번 넘게 누르는 건 일반 사용
  패턴으로 보기 어렵다는 가정 — 이것도 실제 관찰 전 임의 가정이다.
- 모든 한도는 **막을 때 "한도 초과"라고 정직하게 알린다** — 조용히
  실패하거나 가짜 성공을 보여주지 않는다(이 세션 전체를 관통하는
  원칙과 동일, 이미 구현·테스트됨).
- 위 세 값 모두 `server/config.mjs`의 환경변수라 코드 수정 없이
  숫자만 바꿀 수 있다(가격과 같은 패턴).

### 3-6. 재방문 여행자(반복 구매) 지원 — 비용·가격 구조(5차 신규)

같은 도시·나라를 반복 방문하는 여행자(마케팅에서 "재방문 여행자"로
부르는 손님층)를 위해 여행 분리(trips)·방문 기록(visits)·다음 여행
코스 후보 제안 기능을 이번에 추가했다(서버는 완료, 화면 연결은
`docs/RELEASE_STATUS.md` 7절 참고). 이 기능이 **가격·비용 구조에
어떤 영향을 주는지** 정리한다.

- **새 가격 구간을 만들지 않는다** — "재방문 여행자용 요금제"
  같은 것은 없다. 기존 9,900원/30일 이용권 구조를 그대로 쓴다.
- **기록 자체(여행 만들기·방문 표시·과거 여행 열람)는 항상 무료다**
  — `server/routes/trips.mjs`, `visits.mjs`,
  `next-trip-suggestions.mjs` 어디에도 유료 외부 API(Places/Routes)
  호출이 없다(순수 DB 읽기/쓰기). 여행을 몇 개를 만들든, 도시를 몇 번
  바꾸든, 방문 표시를 몇 번을 하든 **비용이 전혀 안 든다** —
  `server/test/trips-and-visits.test.mjs` §4에서 실제로 확인했다.
- **새 코스를 실제로 생성/재계산할 때만 비용이 든다** — 이건 재방문
  여행자든 처음 오는 여행자든 완전히 동일한 기존 정책(무료체험 1회 +
  이후 유료)을 따른다. 재방문 여행자라고 코스 생성이 더 싸거나
  비싸지 않는다.
- **여행을 바꾸거나 도시를 전환해도 무료체험이 다시 채워지지
  않는다** — 계정당 무료체험은 여전히 평생 1회다(여러 여행을 만들 수
  있다고 해서 무료체험도 여행 개수만큼 늘어나는 게 아니다). 이는
  `server/test/trips-and-visits.test.mjs` §4로 확인됐다.
- **이용권이 만료된 뒤에도 여행·방문 기록은 계속 보인다** — 새 코스
  생성만 막히고, 과거에 만든 여행·방문 표시·메모는 전부 그대로
  남는다(만료 후에도 기존 코스 열람은 유지된다는 기존 원칙, 1절과
  동일한 원칙을 여행 단위로 확장한 것).
- **이 기능이 "재구매"를 늘리는 방식은 가격이 아니라 경험이다** —
  "저장해놓고 못 간 곳을 다음 여행에서 마저 가보기"가 재구매의
  동기가 되길 기대하는 것이지, 재방문 손님에게 별도 할인·구독을
  파는 구조가 아니다(마케팅 문서 참고,
  `docs/MARKETING_LAUNCH_PLAN.md`).
- **비용 예측에 주는 영향**: 이 기능 자체는 3-1~3-4절의 비용 계산에
  새 항목을 추가하지 않는다(유료 API 호출이 없으므로). 다만 "다음
  여행 코스 후보 제안"이 재구매를 실제로 늘린다면, 같은 계정이 한
  달 안에 여러 번 코스를 재계산하는 빈도가 늘 수 있다 — 이건 이미
  3-3절 "300곳·월 50회" 시나리오가 다루는 것과 같은 종류의 사용량
  증가이므로, 별도 표를 만들지 않고 기존 헤비유저 계산에 포함된
  것으로 본다.

## 4. 확인 안 된 가설 (숫자·주장을 만들지 않음)

- 9,900원/30일이라는 확정 가격에 **실제로 돈을 낼 사람이 얼마나
  있는지**는 여전히 검증 전이다. 검증 계획은
  `MARKETING_LAUNCH_PLAN.md` 4절(초기 체험단 5~10명) 참고.
- **Google Routes 실제 성공률** — 이 세션은 `developers.google.com`
  으로 나가는 네트워크가 막혀 있어 실제 키로 성공 응답을 한 번도
  못 받아봤다(2절 참고). 실제 인터넷 환경·실제 키로 다시 확인 필요.
- **3-2절의 재조회 비율(저장 장소의 10%/월) 가정** — 실제 관찰 전
  임의로 잡은 값이다. 체험단 운영 중 실제 재조회 횟수를 기록하면
  더 정확한 값으로 바꿀 수 있다.
- **3-3절의 API 단가·Google Maps Platform 무료 사용량 정책** — 이
  세션에서 공식 가격표를 열어보지 못해 학습 기억에만 의존했다.
  계약 전 재확인 전까지는 "확인 필요"로 취급해야 한다.
- **179건 실제 Google Takeout 데이터셋 재실행 — 이번 세션에서도
  여전히 차단됨**: 이 샌드박스에는 그 실제 파일이 없다. 필요하면
  사용자가 다시 올려줘야 한다.

## 5. 남은 결정 사항

### 5-0. 부분 환불 정책 미확정 — ChatGPT/사용자 결정 필요(별도 보고)

토스 결제가 부분 취소(예: 일부 금액만 환불)로 처리되면, 지금 코드는
**주문 상태만 `partially_cancelled`로 남기고 이용권을 자동으로
건드리지 않는다**(`server/adapters/payment-toss.mjs`의
`cancelPayment`/`handleTossWebhookEvent`). 이건 "정책이 없어서 아무
것도 안 하기로 한 것"이지, "부분 환불 시 이용권을 유지하기로 확정한
것"이 아니다 — 다음 질문이 아직 열려 있다:

- 부분 환불 비율만큼 이용권 기간을 비례해서 줄여야 하는가(예: 절반
  환불이면 남은 15일만 인정)?
- 아니면 부분 환불은 결제 금액 조정일 뿐 이용권과는 무관하게 둘 것인가
  (환불 사유가 "가격 조정" 같은 것이라면 이 편이 자연스러울 수 있다)?
- 부분 환불이 일정 비율(예: 50% 이상)을 넘으면 전액 취소와 동일하게
  취급할 것인가?

**이 질문에 대한 답이 나오기 전까지, 소비자 화면에는 부분 취소를
받을 수 있는 UI 자체를 만들지 않는다**(완성되지 않은 기능을 완성된
것처럼 제공하지 말라는 지시 반영 — 지금 부분 취소는 토스 쪽에서
발생한 이벤트를 서버가 안전하게 "기록만" 하는 수준이지, 사용자가
스스로 요청할 수 있는 기능이 아니다). 결정이 나면
`revokeEntitlementIfCurrentOrder` 호출 부분에 그 정책을 반영하면 된다
(코드 구조는 이미 분리해 뒀다).

### 5-1. 이메일·결제·경로 — 실제 키로 첫 연결 확인

공급자는 확정됐고(Toss/Resend/Google Places+Routes) 그 API를
호출하는 코드도 작성됐지만, **이 세션은 세 공급자의 공식 문서
사이트에 전부 접속이 막혀 있어(EGRESS_BLOCKED) 스펙을 다시 확인하거나
실제 키로 검증하지 못했다.** 실제 키를 발급받아 처음 넣어 볼 때
아래를 반드시 확인해야 한다:
- Resend: 로그인 코드 요청을 눌러 본인 이메일에 실제로 도착하는지.
- 토스페이먼츠: 결제창이 실제로 뜨고, 결제 완료 후 서버 로그에
  승인(confirm) 응답이 정상적으로 오는지, 웹훅이 실제로 우리 서버
  형식과 맞는지(코드 작성 시 기억에 의존했으므로 실제 스펙과 필드명이
  다를 가능성을 열어둔다).
- Google Routes: `computeRoutes` 응답이 우리가 기대한 필드 마스크로
  실제로 오는지, WALK 모드 요청이 거절되거나 다른 요금 등급으로
  청구되지 않는지.
이 셋 중 하나라도 실제 스펙과 다르면 어댑터 코드(`server/adapters/`)
만 고치면 되도록 이미 그 경계에서 분리해 뒀다(계약 테스트
`server/test/provider-contracts.test.mjs`가 그 경계를 지킨다).

### 5-2. 사용 한도 확정 + 헤비유저 원가 초과 문제 — 6차에서 (A)안으로 실행됨

**5차까지 남아 있던 결정**: 3-5절의 제안(코스 생성·초기 가져오기·
재조회 각각 상한)을 실제 숫자로 확정할지, 다른 방식(예: 초과분은
추가 결제로 풀기)으로 갈지 — (A) 저장·재계산 실사용량 자체를
9,900원으로 감당되는 범위로 제한 / (B) 구간별 요금 분리 / (C) 소수
헤비유저의 손실을 인수비용으로 감수, 셋 중 하나를 사업 쪽이 골라야
했다.

**6차 처리 — (A)안을 실제로 구현했다(개발 담당 임의 실행이 아니라,
이번 라운드 지시 "초기 테스트 상품의 사용 한도를 확정하라"에 따른
것)**: `server/entitlement-usage.mjs`가 유료 이용권 하나당 30일 동안
위치 확인 최대 50곳+코스 생성 최대 30회로 실사용량 자체를 막는다
(3-3-1절). 이 한도 안에서는 이론적 최댓값이 약 2,450원, 실패·재시도를
더해도 내부 안전상한(3,500원)을 구조적으로 못 넘는다 — "300곳·월
50회"급으로 원가가 매출을 넘던 5차 시나리오는 더 이상 발생할 수
없다. **(B)·(C)는 채택하지 않았다** — 가격 구간을 나누지도, 손실을
그냥 감수하지도 않고, 사용량 자체에 한도를 씌우는 방식으로 해결했다.

**단, 이 숫자들은 여전히 "확정된 시장가격"이 아니라 초기 테스트
상품 스펙이다** — 50곳/30회라는 한도가 실제 손님 만족도·재구매율에
비해 너무 박한지 넉넉한지는 아직 검증 전이고, Places/Routes 단가가
실제 계약가와 다르면 이 한도의 여유(약 1,050원, 3-3-1절)도 달라진다.
**출시 전 실사용 데이터로 다시 봐야 할 것**: (1) 유료 손님 대부분이
30회 한도 안에서 만족하는지, (2) 위 원가 계산이 실제 단가로도
유효한지, (3) 안전상한(3,500원)에 실제로 도달하는 계정이 얼마나
자주 나오는지(자주 나온다면 정상 사용도 막고 있다는 뜻이라 상한을
올려야 함).

## 6. 실제 전환에 필요한 계정·크리덴셜 — 어디서 설정하고 어떻게 확인하는지

**절대 채팅창에 실제 비밀키를 붙여넣지 말 것.** 실제 값은 서버가
실행될 환경(호스팅 서비스의 환경변수 설정 화면)에 직접 입력한다.

|---|---|---|---|
| 운영 환경 표시 | `APP_ENV=production` | 서버 환경변수(운영 배포 시 반드시 설정 — 안 하면 development로 동작해 테스트 기능이 안 막힘) | `/api/health`의 `appEnv`가 `"production"`인지 확인 |

| 결제창(클라이언트) 키 | `TOSS_CLIENT_KEY` | 토스페이먼츠 가맹점 콘솔에서 발급하는 클라이언트 키(공개돼도 되는 값) | 이용권 화면에서 개발용 시뮬레이션이 아니라 실제 토스 결제창이 뜨는지 확인 |

| 코스 생성 입력 상한 | `MAX_PLACES_PER_GENERATION`(기본 60), `MAX_BUDGET_MINUTES`(기본 1440) | 서버 환경변수 | 실제 여행 코스 규모에 비해 너무 빠듯하면(예: 여러 날짜를 한 코스로 묶는 사용 패턴이 실제로 있다면) 값을 올려야 함 |

각 서비스는 **독립적으로** real/test가 판정된다(`docs/DESIGN_INTEGRATION_REPORT.md`
1-B-11) — 장소 조회 키만 먼저 넣어도 결제·이메일은 그대로 테스트
모드로 안전하게 남아 있다. 한 서비스씩 순서대로 실제로 켜고 확인해도
된다. 단, **운영(`APP_ENV=production`)으로 전환하는 순간에는** 결제·
이메일 필수값이 전부 갖춰지지 않으면 서버 자체가 시작되지 않는다 —
장소조회·경로 키만 없는 채로 운영을 시작하는 것은 허용된다(그
기능만 "개발 중"으로 정직하게 비활성 표시).

## 7. 최소 제휴 준비(9차 신규) — 구조만, 실제 계약·게시는 안 함

1-2절의 "추가 수익(보조)" 방향에 맞춰, 제휴처를 실제로 등록하지 않은
채로 나중에 등록만 하면 바로 켤 수 있는 최소 구조를 미리 만들어
뒀다. **지금은 승인된 실제 제휴 링크가 하나도 없다** — 그래서 이
기능은 소비자 화면 어디에도 아직 보이지 않는다(의도된 기본 상태).

- **데이터 구조**: `server/affiliates.mjs`의 `AFFILIATE_OFFERS`(빈
  배열로 배포) — 항목마다 `id·type(esim/transit/ticket/lodging)·
  city·label·url·active`를 갖는다.
- **표시 조건**: 그 도시에 `active:true`인 제휴가 있을 때만, 정해진
  진입점(출국 준비 안내·코스에 필요한 티켓/교통 안내)에 링크
  카드가 뜬다. 없으면 완전히 숨는다 — "곧 열립니다" 같은 자리
  채우기도 안 만든다.
- **안전장치**: 허용 도메인 화이트리스트(`ALLOWED_AFFILIATE_DOMAINS`)
  검증, `target="_blank" rel="noopener noreferrer"`로 새 창 오픈,
  "제휴 링크"라는 표시를 항상 붙인다. 클릭 이벤트(`affiliate_click`)
  만 기록하고, 이건 예약·매출이 아니라 "클릭이 있었다"는 사실만
  의미한다 — 예약/취소/정산 데이터는 실제로 그 제휴사에서 확인할 수
  있게 되는 시점에만 별도로 집계한다.
- **금지 사항(코드로 보장)**: 제휴 유무·수수료가 코스 생성 로직에
  전혀 영향을 주지 않는다(제휴 모듈은 코스 생성 코드를 아예 import
  하지 않음). 사용자의 저장 목록·좌표·이메일 등 개인 데이터를 제휴
  링크 URL에 실어 보내지 않는다(정적으로 등록된 URL을 그대로 열 뿐,
  쿼리 파라미터를 조합해 만들지 않음). 임의 URL로의 리다이렉트 기능
  자체가 없다(화이트리스트에 없는 도메인은 링크 생성 단계에서부터
  걸러진다).
- **아직 안 한 것**: 실제 제휴 계약 체결, 실제 제휴사 링크 등록,
  광고 게시. 전부 사용자·ChatGPT의 별도 승인이 있어야 진행되는
  일이다.

## 8. 한국에서 현지 위치인 것처럼 테스트하는 모드(9차 신규)

6-3절 지시대로, **OS의 실제 GPS를 흉내 내거나 가로채지 않는** 앱 안
"테스트 위치" 기능을 넣었다(`navigator.geolocation`을 전혀 건드리지
않음). 이 기능만으로 실제 현지 GPS·로밍·도보 조건을 검증했다고
**절대 주장할 수 없다** — 그냥 앱 로직이 참고하는 기준 좌표를 사람이
명시적으로 지정한 값으로 바꿔치기할 뿐이다.

- **허용 대상(중요한 한계)**: 지금 이 저장소에는 "승인된 테스트
  계정/스테이징"을 구분하는 서버 쪽 화이트리스트가 없다. 그래서
  최소 구현으로 URL에 `?testmode=1`을 한 번 붙이면 그 브라우저에
  계속 풀리는 방식(로컬스토리지 플래그)을 썼다 — **이건 진짜 계정
  기반 접근 제어가 아니다.** 실제로 특정 계정만 허용하려면 서버에
  계정 화이트리스트(예: `accounts.test_access` 플래그)와 이를
  확인하는 API가 새로 필요하며, 지금은 없다.
- **고를 수 있는 위치**: 하카타역·텐진 프리셋 2곳, 또는 위도·경도
  직접 입력. 숙소는 아직 좌표 자체가 없어(R9-9에서 확인 — `POST
  /api/trips`가 숙소 이름만 저장하고 좌표는 안 받음) 프리셋에서
  뺐다 — 나중에 숙소 지오코딩을 붙이면 추가할 수 있다.
- **일관되게 적용되는 곳**: 지금 실제로 구현된 위치 의존 기능은
  6-1절의 거리순 정렬뿐이다(코스 출발지·목적지 날씨는 좌표가 아니라
  선택한 도시 기준이라 이 테스트 위치와 무관하다 — "내 주변 날씨"
  같은 기능 자체가 아직 없다). 테스트 위치가 켜져 있으면 거리순
  정렬의 기준점이 평소의 "지정 위치"(보유 장소 평균 좌표) 대신 이
  좌표로 바뀌고, 화면 문구에 "테스트 위치(◯◯) · 실제 GPS 아님"이
  항상 같이 뜬다 — 실제 위치처럼 보이지 않게 하기 위해서다.
- **상단 배너**: 켜져 있는 동안 화면 맨 위에 "🧪 테스트 위치 사용
  중: ◯◯ · 실제 위치 아님(수동 지정)" 배너가 항상 보이고, "실제
  위치로 되돌리기"를 누르면 즉시 꺼진다.
- **실제/모의 API와의 분리**: 이 기능은 저장 목록·정렬 화면에만
  관여하고, 결제·이용권·장소 조회 같은 실제 과금·서버 판정 경로를
  전혀 건드리지 않는다(별도 저장 키, 별도 코드 경로 — 결제 시뮬레이션
  라우트가 production에는 아예 등록 안 되는 것과 같은 "실제와 모의를
  절대 안 섞는다"는 원칙을 그대로 따른다).
- **QA에 필요한 나머지 시나리오는 이미 있는 검증으로 커버됨(새로
  안 만듦 — 중복 방지)**: 저장 실패는
  `scripts/test-storage-migration.mjs`(저장소 가득 참 흉내), 응답
  지연·저장 중 충돌은 `scripts/test-sync-conflict-devices.mjs`,
  타임존은 `server/test/weather-timezone.test.mjs`, 결제
  실패·취소는 `scripts/test-purchase-flow.mjs`가 이미 실제로
  재현·검증한다. "GPS 거부/미확인" 자체는 앱에 실제 GPS 기능이
  아직 없어(`nearby()` 화면이 스스로 "GPS 연결 전"이라고 밝힘) 지금
  당장은 테스트할 대상이 없다 — 이 테스트 위치 기능은 그 실제 GPS
  기능이 나중에 생겼을 때 기기 GPS 없이도 개발 중 화면 동작을
  미리 확인해 볼 수 있게 준비해 둔 것이다.
- **아이폰 실기기·비공개 프리뷰**: 지금 이 저장소는 정적 파일
  (`src/design/index.html`)이라 어떤 URL로도 아직 공개 배포되지
  않았다(이번 승인 범위 밖). 아이폰에서 직접 열어 보려면 최소한
  다음 중 하나가 필요하고, 어느 쪽도 아직 설정돼 있지 않다 — 사용자가
  택할 사항이라 임의로 진행하지 않았다.
  1. 비밀번호로 보호된 스테이징 서브도메인에 이 정적 폴더를 올리고
     그 HTTPS 주소를 아이폰 사파리에서 직접 여는 방법(가장 단순).
  2. 로컬 개발 서버를 임시 터널(예: 사내 승인된 터널링 도구)로 잠깐
     공개해 그 세션 동안만 여는 방법(세션이 끝나면 주소가 사라짐).
  3. 위 6-3절 계정 화이트리스트를 실제로 만든 뒤, 그 계정으로 로그인해야만
     `?testmode=1`이 통하게 서버에서 한 번 더 확인하는 방법(가장 안전하지만
     구현이 더 필요함).
  어떤 방법을 쓰든 실제 배포 승인은 이번 라운드 범위가 아니므로, 사용자가
  방법을 고르면 그에 맞춰 다음 라운드에서 구현한다.

## 9. 소규모 베타·피드백 체계(9차 신규)

6-4절 지시를 실제로 구현했다. **실제 유료 모집은 이번에도 켜지 않았다**
(가격이 미정인 지금은 시작하지 않는다는 원칙 그대로) — 아래는 전부
"켜면 바로 쓸 수 있게 준비된 구조"다.

- **"불편함 보내기"**: 유형(가져오기/위치·동선/이용 방법/결제/기타) +
  한 줄 설명(최대 300자) + 선택 연락처. 로그인 여부와 무관하게 보낼 수
  있다(아직 로그인 못 한 상태에서 겪은 문제도 알려야 하므로). **화면
  스크린샷 첨부는 이번에 구현하지 않았다** — 개인정보(저장한 장소가
  화면에 그대로 보임)와 초기 운영비용을 고려한 의도적 최소 범위이며,
  그 사실을 화면 문구에서 숨기지 않는다. 최소 진단정보(appBuild·현재
  화면·오류 코드·기기 종류 4개 키만)를 서버가 화이트리스트로 강제해,
  실수로든 고의로든 전체 저장목록·정밀 GPS·결제정보가 같이 실리는 걸
  구조적으로 막는다(server/feedback.mjs). 오류 코드는 이번 라운드에서
  장소 위치 확인 실패 경로 하나만 부분적으로 채웠다 — 전체 실패
  경로를 다 연결하진 않은 의도된 최소 범위다.
- **코스 생성 직후 짧은 설문**: "실제로 이 코스로 여행하셨나요?" +
  선택 입력으로 "가장 큰 불편"을 묻는다. 카드 형태로 얹힐 뿐 코스
  화면의 다른 버튼(확인·새로 만들기)을 전혀 막지 않고, 같은 여행
  코스에는 한 번만 뜬다.
- **소규모 관리자 화면**(`src/design/admin.html`): ADMIN_TOKEN 하나로만
  보호된다(설정 안 하면 관리자 API 자체가 401이 아니라 501 — "아직
  준비 안 됨"으로 정직하게 막힌다, 빈 문자열끼리 비교해 아무 토큰
  없이 통과하는 사고 방지). 받음/처리 중/해결됨 상태 전이, 유형별
  개수 집계, 결제·"데이터 손실/사라짐" 키워드가 들어간 접수를
  화면에서 먼저 보여주는 우선순위 정렬(완벽한 분류가 아니라 운영자가
  먼저 보게 돕는 보조 장치일 뿐임을 화면에도 안내), 초대 코드
  발급·비활성화, 신규 모집 일시중지/재개 버튼을 담았다. 하루 한 번
  훑어보고 처리할 목록을 고르는 걸 전제로 만든 화면이다.
- **초대 코드**: 만료(기본 14일)·코드당 인원(기본 8명)·전체 모집
  상한(기본 30명)을 갖는다. **기본값은 꺼짐**
  (`REQUIRE_INVITE_CODE_FOR_SIGNUP=false`) — 켜지 않는 한 기존 열린
  가입 흐름이 그대로 유지된다(기존 회귀 테스트 전부가 이 기본값으로
  계속 통과함을 확인했다). 한 계정(=한 이메일)이 여러 번 "신규
  등록"으로 코드를 반복 소모할 수 없다 — 코드 소모는 그 이메일로
  계정이 "처음" 만들어지는 그 순간에만 일어나고, 이미 있는 계정의
  재로그인은 초대 코드와 완전히 무관하다(server/auth.mjs의
  loginOrCreateAccount). "5명→10명"은 예시였을 뿐 확정 값이 아니다 —
  아래에 실제 채택한 기본값과 근거를 남긴다.
  - 코드당 인원 8명: 예시보다 살짝 여유(초대 실수·한두 명 이탈 감안),
    여전히 "소규모".
  - 전체 모집 상한 30명: 초기 운영 여력(문의 응대 1인, 하루 1회
    검토)을 기준으로 "코드 하나(8명)의 3~4배" 정도로 잡은 제안값.
    확정 아님 — 응대가 밀리면 낮추고, 여유가 있으면 관리자 화면에서
    코드를 더 만들면 된다.
- **신규 모집 일시중지**: 결제·데이터손실급 심각 이슈가 생기면
  관리자 화면 버튼 하나로 즉시 멈출 수 있다(코드 재배포 불필요). 단,
  초대 코드 게이트 자체가 꺼져 있으면(기본 상태) 이 일시중지는 아무
  효과가 없다 — "모집"이라는 개념 자체가 게이트가 켜졌을 때만 의미가
  있기 때문에, 이 라운드에서는 일부러 범위를 그렇게 좁혔다(게이트가
  꺼진 상태에서까지 모든 개발용 회원가입을 막는 건 과잉 범위라고
  판단).
- **가입→가져오기→코스완성→실사용→피드백 퍼널**: 새 이벤트
  3종(`signup_completed`/`place_visited`/`feedback_submitted`/
  `survey_submitted`)만 추가했다 — 가져오기·코스완성 단계는 이미 있던
  이벤트(`import_result`/`course_generated`)로 충분해 중복으로 새로
  안 만들었다. 전부 기존 이벤트와 같은 화이트리스트 방식(허용된
  이벤트 이름·속성 키·값만 서버·클라이언트 양쪽에서 강제)이라 장소명
  등 개인 데이터가 섞일 방법이 없다.
- **아직 안 한 것**: 실제 유료 모집 시작, 화면 스크린샷 첨부, 결제형
  고객지원 SaaS·유료 AI 요약(6-4절 지시대로 시작부터 안 넣음).

### 9-1. 초대 모집 SNS 초안(게시 안 함 — 준비만)

실제 게시는 사용자·ChatGPT의 별도 승인이 있어야 한다. 가격·구체 기능을
확정된 것처럼 말하지 않고, "지금/곧 여행 가는 사람의 진짜 불편을
검증하고 싶다"는 목적을 앞세운 초안이다.

**Threads (짧은 글):**
> 여행 갈 때마다 구글맵에 저장만 해두고 정작 그 자리에서 뭘 어떻게
> 돌아야 할지 몰라서 헤맸던 적 있으신가요? 저장해둔 장소로 하루 동선을
