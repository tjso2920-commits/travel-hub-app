# 사업 결정 정리 (travel hub) — ChatGPT 판단용

작성: 2026-09-10(1차) · 갱신: 2026-09-10(2차 — 확정 상품 반영, 비용·
사용 한도 제안 추가) · 기준 커밋: `ab87eca`(브랜치 `design-integration`)

이 문서는 남은 결정 사항을 정리하는 곳이다. 브랜드·가격·기능 범위는
이미 확정돼 반영했다(아래 1절) — 남은 건 실제 서비스 연결 방식과
사용 한도처럼 아직 안 정해진 것들이다. 숫자를 지어내지 않는다 —
확인 안 된 값은 "모른다/확인 필요"라고 그대로 적는다.

## 1. 확정된 사업 방향 (반영 완료)

- 모바일 중심 서버 기반 여행 웹앱, 표시명 **travel hub**.
- 후쿠오카 전용이 아니라 사용자의 저장 장소를 기준으로 여러 도시에서
  사용(도시별 분리, 여러 날짜 일정 정리까지 구현·검증 완료 —
  `docs/DESIGN_INTEGRATION_REPORT.md` 1-B-11).
- 첫 상품: **9,900원·30일 여행 이용권, 결제 승인 시 시작, 자동결제
  없음.** `server/config.mjs`의 기본값을 그대로 확정 상품으로 반영했다
  (여전히 환경변수로만 바꾸는 구조 — 코드에 숫자를 안 박는다는 원칙은
  유지).
- 무료: 샘플, 장소 가져오기·보관·검색·수동 정리, 개인화 코스 생성
  성공 1회. 유료: 추가 코스 생성·조건 변경 후 재계산·여러 날짜 일정
  정리. 전부 구현·검증 완료.
- 만료 후에도 기존 장소와 코스 열람은 유지된다(서버 게이트를 안 타는
  순수 열람 — `scripts/test-multi-day.mjs`에서 환불 뒤에도 열람되는
  것까지 확인).
- 무제한 사용은 아직 확정 안 됨 — 3-3절에 제안을 정리해 뒀다.

기존 `src/landing.html`(브랜드 "별표털기", 서버 없음, 한 번 결제)과의
충돌은 위 확정 방향대로 **(A) travel hub로 완전히 전환**하는 것으로
해소된 것으로 보고 진행한다 — `src/landing.html`은 여전히 손대지
않았고(폐기 여부는 실제 공개 배포 시점에 결정), `src/design/`
기준으로만 개발을 이어간다. 옛 마케팅 문서(`가격_판매전략.md` 등,
서버 없는 단일 파일·한 번 결제 전제)는 이제 전제 자체가 안 맞으므로
`MARKETING_LAUNCH_PLAN.md`(이번에 확정 상품 기준으로 갱신됨)를 쓴다.

## 2. 확인된 사실 (실제로 코드를 돌려서 검증함)

- 구글맵 저장 목록 내보내기(Google Takeout) ZIP/CSV/JSON을 실제로
  읽어 장소를 가져온다.
- 가져온 장소를 도시별로 나누고, 유형을 짐작하되 사람이 직접 고치면
  그 선택을 유지한다. 서버 위치 조회(불확실한 후보 확인 포함)도 화면
  까지 실제로 연결됐다(테스트 어댑터 기준 — 실 Google Places 키
  미검증).
- 걸어서 도는 코스를 만든다. 실제 도보 경로 계산(OSRM)이 되면 그
  경로를, 안 되면 방문 순서만 정직하게 대체로 보여준다. 이 샌드박스는
  `router.project-osrm.org`로 나가는 네트워크가 막혀 있어 **실제 성공
  응답을 한 번도 못 받아봤다** — 파라미터는 공식 문서 기준으로
  맞췄지만 실제 인터넷 환경 성공률은 미검증.
- 서버(계정·세션·코스 저장·무료체험 1회 제한·결제 웹훅 서명 검증·
  환불/만료 처리·서비스별 독립 연결 상태 판정)는 전부 실제 코드로
  구현되고 실제 HTTP 요청으로 테스트했다.
- **실제 이메일 발송·실제 결제(PG) 연동은 단순 설정이 아니라 코드
  작성이 더 필요하다** — `docs/RELEASE_STATUS.md` 3절에 정확히 뭐가
  없는지 정리해 뒀다(이메일 어댑터는 스텁, 결제는 체크아웃 시작 코드
  자체가 없음).

## 3. 비용 — 무엇이 얼마나 드는가

### 3-1. 비용을 만드는 항목 (실제 금액은 공식 가격표 확인 필요)

숫자를 지어내지 않는다 — 아래는 "무엇을 쓰면 돈이 드는가"라는 구조이지,
실제 단가가 아니다. 계약 전 반드시 **그 시점의** 공식 가격표를 다시
확인해야 한다(요금제는 자주 바뀐다 — 특히 Google Places는 최근 몇 년
사이 과금 체계 자체가 여러 번 바뀌었다).

| 항목 | 무료로 가능한 범위 | 유료로 전환되는 조건 | 확인해야 할 곳 |
|---|---|---|---|
| 장소 조회(불확실한 후보 확인) | 테스트 어댑터(가짜 좌표)로는 무료 | 실제 Google Places API 키 연결 시 요청 건수에 따라 과금(보통 월 일정액 무료 크레딧 + 초과분 종량) | Google Cloud 콘솔의 Places API 가격표(요청 시점에 재확인) |
| 도보 경로 계산 | 지금은 공개 무료 OSRM 데모 서버 사용 | **이 데모 서버는 실 서비스 트래픽용이 아니다** — 자체 OSRM 서버(정액 서버 호스팅비) 또는 유료 라우팅 API(종량제)로 전환 필요 | OSRM 프로젝트 공식 사용 정책 + 선택한 대안의 가격표 |
| 서버 호스팅 | 없음 — 지금은 로컬에서만 실행됨 | 실제로 켜는 순간부터 최소 서버비 발생(트래픽 늘면 증가) | 선택할 호스팅사 가격표 |
| 결제(PG) | 없음(시뮬레이션만) | 결제 성공 건마다 거래 수수료(보통 정률+정액) | 선택할 PG사 가맹 조건 |
| 이메일 발송(로그인 코드) | 테스트 어댑터는 무료 | 발송량에 따라 과금(대부분 소량 무료 구간 있음) | 선택할 이메일 발송 서비스 가격표 |

### 3-2. 9,900원 이용권 하나의 "사용량별" 원가 구조

**정액 비용(판매 건수와 무관, 결제 1건당 고정)**:
- PG 거래 수수료 1건 (9,900원의 일정 비율 — PG 계약에 따라 다름)
- 이 손님의 로그인 코드 이메일 발송 몇 건(로그인할 때마다 1건 — 30일
  동안 재로그인 횟수만큼)

**사용량 비례 비용(이 손님이 이용권 기간 30일 동안 실제로 얼마나
쓰는지에 따라 늘어남)**:
- 코스 생성·재계산 1회당 도보 경로 계산 요청 1건(자체 OSRM이면
  거의 0원에 가까운 한계비용 — 서버가 이미 떠 있으면 요청 하나 더
  처리하는 비용은 미미하다. 유료 라우팅 API로 가면 요청당 실비 발생)
- 위치 후보 확인(장소 상세의 "서버로 위치 후보 찾아보기") 버튼 누른
  횟수당 장소 조회 요청 1건

**지금 코드의 실제 위험 — 사용량에 상한이 없다**: 결제 후에는
`daGateThenBuildCourseSheet`가 코스 생성·재계산·새 날짜 추가를
전부 무제한 통과시킨다. `/api/places/lookup`에도 계정별 호출 횟수
제한이 없다. 즉 **한 손님이 30일 안에 코스를 수백 번 재계산하거나
위치 확인 버튼을 수백 번 누르면, 그 손님 한 명에게 받은 9,900원보다
그 손님 때문에 나가는 실제 API 비용이 더 커질 수 있다**(특히 유료
라우팅 API나 종량제 Places 요금제를 쓸 경우). 자체 OSRM으로 도보
경로를 처리하면 이 위험은 크게 줄어들지만(요청 하나당 한계비용이
거의 0), 장소 조회는 Google Places를 쓰는 한 여전히 요청당 비용이다.

### 3-3. 제안 — 사용 한도 (확정 아님, 검토용 제안)

**이 숫자들은 내가(개발 담당) 엔지니어링 안전장치로 제안하는 값이지,
사업적으로 확정된 한도가 아니다.** 실제 값은 ChatGPT/사용자가 정할
몫이고, 정해지면 `server/config.mjs`에 설정값으로 추가해 코드
수정 없이 바꿀 수 있게 만들면 된다(가격과 같은 패턴).

- **코스 생성·재계산**: 이용권 기간(30일) 동안 계정당 최대 N회 제안.
  기준: 실제 여행 계획 세우는 데 하루 몇 번 이상 재계산할 일이
  흔치 않다는 가정 — 예를 들어 "30일에 50회"면 하루 평균 1.6회로
  일반적인 사용 패턴은 전혀 못 느끼면서 악의적/실수로 인한 무한
  반복은 막을 수 있다. **정확한 N은 실제 초기 체험단(5~10명)이 30일
  안에 실제로 몇 번 재계산하는지 관찰한 뒤 정하는 게 더 안전하다** —
  지금 숫자를 확정하지 않는다.
- **위치 후보 확인(`/api/places/lookup`) 호출**: 계정당 하루 최대
  M회 제안. 기준: 사용자가 실제로 "위치가 불확실한" 곳을 하루에
  수십 개씩 확인할 일은 드물다 — 예를 들어 "하루 30회"면 일반 사용은
  전혀 못 느끼면서 자동화된 남용은 막힌다.
- 두 한도 모두 **막을 때 "한도 초과"라고 정직하게 알려야 한다** —
  조용히 실패하거나 가짜 성공을 보여주면 안 된다(이 세션 전체를
  관통하는 원칙과 동일).
- 이 한도는 아직 코드에 구현하지 않았다 — 값이 정해지면 그때 실제
  서버 코드(trial.mjs와 비슷한 계정별 카운터 테이블)로 구현할 수
  있다(설계는 간단하다 — 지금 급하게 임의 값으로 넣어 두면 나중에
  실제 관찰 데이터와 안 맞을 수 있어 일부러 미루고 제안만 남긴다).

## 4. 확인 안 된 가설 (숫자·주장을 만들지 않음)

- 9,900원/30일이라는 확정 가격에 **실제로 돈을 낼 사람이 얼마나
  있는지**는 여전히 검증 전이다. 검증 계획은
  `MARKETING_LAUNCH_PLAN.md` 4절(초기 체험단 5~10명) 참고.
- OSRM 실제 성공률(2절 참고) — 실제 인터넷 환경에서 다시 확인 필요.
- **179건 실제 Google Takeout 데이터셋 재실행 — 이번 세션에서도
  여전히 차단됨**: 이 샌드박스에는 그 실제 파일이 없다. 필요하면
  사용자가 다시 올려줘야 한다.

## 5. 남은 결정 사항

### 5-1. 이메일·결제 실제 연동 — 누가 언제 만들지

`docs/RELEASE_STATUS.md` 3절 참고. 이메일 발송 어댑터 구현과 결제
체크아웃 시작 코드는 **환경변수 설정이 아니라 새 코드 작성**이
필요하다 — 어떤 이메일 서비스·어떤 PG를 쓸지 정해지면 그에 맞춰
구현할 수 있다(제공자만 정해지면 하루 이내 작업 규모로 예상되지만,
정확한 소요는 그 서비스의 API 문서를 실제로 보기 전엔 단정하지
않는다).

### 5-2. 도보 경로 계산 방식

지금의 무료 공개 OSRM 데모 서버를 실 서비스에서 계속 쓸 수 없다(3-1절
참고). 자체 OSRM 서버를 직접 운영할지, 유료 라우팅 API로 옮길지 —
자체 호스팅 쪽이 사용량이 늘어도 한계비용이 거의 안 느는 대신 항상
켜져 있는 서버 관리 부담이 있고, 유료 API 쪽은 관리 부담이 없는 대신
사용량에 정비례해 비용이 늘어난다(3-2절 "사용량에 상한이 없다" 위험과
직결).

### 5-3. 사용 한도 확정

3-3절의 제안(코스 생성·위치 조회 각각 상한)을 실제 숫자로 확정할지,
다른 방식(예: 초과분은 추가 결제로 풀기)으로 갈지.

### 5-4. 179건 실사용 데이터 재검증 여부

여전히 파일이 없어 재실행 못 함 — 필요하면 다시 받아야 한다.

### 5-5. 과거 커밋에 남은 개인정보 처리 여부

`docs/DESIGN_INTEGRATION_REPORT.md` 11절에 정리됨(현재 파일은 고쳤으나
git 히스토리에는 남아 있음) — 히스토리 재작성 여부는 아직 결정 안 됨.

## 6. 실제 전환에 필요한 계정·크리덴셜 — 어디서 설정하고 어떻게 확인하는지

**절대 채팅창에 실제 비밀키를 붙여넣지 말 것.** 실제 값은 서버가
실행될 환경(호스팅 서비스의 환경변수 설정 화면)에 직접 입력한다.

| 필요한 것 | 환경변수 | 어디서 설정 | 설정 후 확인 방법 |
|---|---|---|---|
| 서버 호스팅 | — | Node.js를 지원하는 아무 호스팅(작은 VM, 컨테이너 서비스 등) 선택 후 `node server/index.mjs` 실행 | 배포 주소 + `/api/health`에 접속해 `{"ok":true,...}` 응답이 오는지 확인 |
| 장소 조회 API 키 | `GOOGLE_PLACES_API_KEY` | Google Cloud 콘솔 → API 및 서비스 → 사용자 인증 정보에서 발급, Places API로 키 제한 설정 | 서버 환경변수에 넣고 재시작 → `/api/health`의 `services.placeLookup`이 `"real"`로 바뀌는지 확인 → 앱에서 위치 미확인 장소 상세의 "서버로 위치 후보 찾아보기"를 눌러 실제 후보가 오는지 확인 |
