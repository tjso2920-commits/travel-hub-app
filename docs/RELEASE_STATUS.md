# 출시 상태 (RELEASE_STATUS)

작성: 2026-09-10 · 기준 커밋: `30d5736`(브랜치 `design-integration`)

이 문서는 "무엇이 실제로 되는지"를 네 단계로 구분해 정리한다. **테스트
통과를 실제 공급자 연결 성공으로 보고하지 않는다** — ②는 가짜 응답으로
코드 경로만 확인한 것이고, ③만 실제 외부 서비스와 통신해 성공한 것이다.

- **①** 코드 구현 완료(동작에 필요한 외부 서비스가 없거나, 이 앱 자체가
  서버·DB를 직접 갖고 있어 "외부 연동"이라는 개념이 없는 기능)
- **②** 모의(mock) 응답으로 검증 — 실제 코드 경로(요청 생성 → 처리 →
  응답 반영)는 전부 진짜고, 응답을 주는 쪽만 가짜(테스트 어댑터, 서명된
  가짜 웹훅, `page.route()` 모의 등)
- **③** 실제 외부 서비스 연결까지 검증(실제 키·실제 네트워크로 성공
  응답을 실제로 받아봄)
- **④** 미구현 또는 설정 필요(코드 자체가 없거나, 있어도 스텁이라 실제
  요청을 못 보냄)

## 2. 이번 세션에서 못 하는 검증 — 사용자가 직접 확인할 최소 절차

아래는 "실기기 검증을 완료했다"고 추정하지 않고, 미검증 상태 그대로
남긴 항목과 사용자가 직접 확인하는 절차다.

### 2-1. 실제 Google Takeout 데이터

- **상태**: 179건 실사용 데이터셋이 이 샌드박스에 없어 재실행하지
  못했다(2026-09-09 이전 세션이 로컬에 가진 파일로 추정).
- **확인 절차**: 본인 구글 계정의 Takeout에서 저장 목록을 다시
  내보내 `src/design/index.html`(또는 배포된 주소)의 "가져오기"에서
  그대로 선택 → 가져오기 결과 화면의 "새로 추가/자동 갱신/전체" 숫자가
  실제 저장한 곳 수와 대체로 맞는지, 리뷰·캘린더·Gmail 같은 다른
  서비스 파일이 섞여 있어도 걸러지는지 확인.
- **기대 결과**: 저장한 장소 대부분이 인식되고, 중복(같은 상호를 여러
  목록에 저장한 경우)은 "이름이 같은 곳이 있다"는 후보로 뜬다(자동
  병합 안 함) — 화면에서 직접 "같은 곳이에요"를 눌러야 합쳐진다.

### 2-2. 모바일 Safari(iOS)

- **상태**: 이 샌드박스에는 실제 iPhone·Safari가 없어 전혀 검증
  못했다. 자동화 테스트는 전부 데스크톱 Chromium 기준이다.
- **확인 절차**: 실제 iPhone에서 Safari로 배포 주소를 열어
  (1) ZIP 파일 선택·가져오기가 되는지(iOS 파일 앱 연동),
  (2) GPS 출발지 사용 시 위치 권한 팝업이 뜨고 실제 좌표를 주는지,
  (3) 로그인 코드 입력 시 숫자 키패드가 자동으로 뜨는지(`inputmode`
  적용 확인), (4) 다이얼로그(시트)가 열렸을 때 배경이 스크롤 안 되고
  화면이 밀리지 않는지 확인.
- **기대 결과**: 전부 데스크톱과 동일하게 동작해야 한다 — 특히 파일
  선택은 iOS Safari에서 종종 다르게 동작하는 대표 사례라 반드시 실기기
  확인이 필요하다.

### 2-3. 느린 네트워크

- **상태**: 폰트 로딩만 느린 네트워크(Chrome DevTools 프로토콜
  네트워크 에뮬레이션)로 검증했다(`scripts/test-font-coverage.mjs`).
  로그인·결제·코스 생성 전체 흐름을 느린 네트워크 조건에서 검증하지는
  않았다.
- **확인 절차**: 크롬 개발자도구 Network 탭에서 "Slow 3G"로 두고
  로그인 코드 요청 → 결제 → 코스 생성까지 눌러 보며, 버튼을 여러 번
  누르게 되는 화면(중복 요청 위험)이나 응답을 기다리는 동안 아무
  안내도 없이 멈춘 것처럼 보이는 화면이 있는지 확인.
- **기대 결과**: 각 요청 중에는 "코스 만드는 중…" 같은 진행 안내가
  이미 있다(`runCourseGeneration`) — 로그인·결제 버튼에는 아직 로딩
  중 비활성화 처리가 없어, 느린 네트워크에서 사용자가 버튼을 여러 번
  누르면 중복 요청이 나갈 수 있다(서버 쪽은 멱등하게 설계돼 있어
  데이터가 깨지진 않지만, 화면 반응성은 개선 여지가 있다 — 4절 참고).

## 3. 출시 차단 항목 (실제 서비스 연결 필요 — 우선순위 순)

1. **이메일 발송 어댑터 구현** — 지금은 스텁이다. 실제 로그인 코드
   메일을 보내려면 `server/adapters/email.mjs`의 `smtpAdapter`를 실제
   이메일 API(예: Resend, SendGrid) 호출 코드로 새로 작성해야 한다.
   이게 없으면 **실제 사용자는 로그인 자체를 못 한다** — 가장 급한
   항목.
2. **결제 체크아웃 시작 코드** — 지금은 서버가 "웹훅을 받는 쪽"만
   있다. 실제 PG(토스페이먼츠 등) 결제창을 여는 코드(클라이언트가
   결제창으로 이동하거나 위젯을 띄우는 부분)와, 그 PG의 실제 웹훅
   필드명에 맞춘 `normalizeWebhookEvent` 매핑을 새로 써야 한다.
3. **도보 경로 계산 서비스 전환** — 지금 쓰는 공개 무료 OSRM 데모
   서버는 실 서비스 트래픽용이 아니다(`BUSINESS_DECISIONS.md` 3절).
   자체 OSRM 서버를 띄우거나 유료 라우팅 API로 바꿔야 한다.
4. **장소 조회 실 연결 확인** — 코드는 있다. `GOOGLE_PLACES_API_KEY`를
   넣고 실제로 몇 번 호출해 성공 응답이 오는지, 요청당 비용이 예상과
   맞는지 확인이 필요하다(코드 변경은 필요 없을 가능성이 높다).

1·2번이 없으면 로그인도, 유료 전환도 실제로는 안 된다 — 서버 코드·DB
스키마·테스트는 전부 준비돼 있지만, **이 두 가지가 이번 세션에서
새로 구현되지 않은 진짜 남은 작업**이다(단순 설정이 아니라 코드
작성이 필요하다는 점을 분명히 한다).

## 4. 알려진 개선 여지(출시를 막지는 않지만 남겨 둔 것)

- 로그인·결제 버튼에 요청 중 비활성화 처리가 없다(중복 클릭 시 서버는
  멱등하게 처리하지만, 화면 반응은 개선 여지 있음).
- 날짜별 코스가 서버(`/api/course`)에 올라가지 않는다 — 지금은
  브라우저 로컬 저장소에만 남는다(여러 기기 동기화 미지원).
- 결제 수 제한(사용 한도) — 유료 이용권 기간 안에서 코스 생성 횟수를
  서버가 따로 제한하지 않는다. 실제로 무제한 허용할지, 원가 보호를
  위해 한도를 둘지는 아직 결정되지 않았다(`BUSINESS_DECISIONS.md`
  "이용권 원가·사용 한도" 절 참고).
