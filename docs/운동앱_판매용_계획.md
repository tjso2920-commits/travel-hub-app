# 운동앱 판매용 전환 계획

**아직 만들지 않았다.** 사용자가 "나중에 만들어달라 하면 이 문서 토대로 만들어라"고
지시한 상태다. 요청이 오면 이 문서를 먼저 읽고 시작한다.

작성: 2026-07-31
대상 파일: `tjso2920-commits/cutting-traker` 의 `index.html` (단일 HTML)

---

## 왜 지금은 못 파는가

파일 안에 **한 사람의 개인 데이터가 콘텐츠로 박혀 있다.** 남에게 주면 그 사람 앱에
남의 체중과 남의 근무 시간표가 뜬다.

박혀 있는 것:

| 위치 | 내용 |
| --- | --- |
| 랜딩·헤더 | `96 → 80kg` 목표 |
| 하루 식단 흐름 | `인포 06–12`, `16:00–16:30 스태프밀`, `주방 중간`, `퇴근 후` |
| 단백질 섹션 | `86~88kg 기준`, `170~190g` |
| `PF_PERSONAL` | 개인이 자주 먹는 음식 프리셋 |
| 주간 운동 기본값 | 이 사람의 분할과 종목 |

`SALE_MODE` 상수와 `PF_GENERIC` 은 이미 있다. 뼈대는 깔려 있고 데이터만 안 갈렸다.

---

## 해야 할 일

### 1. 하루 식단 흐름을 사용자 입력으로

지금은 시간표가 HTML 에 하드코딩이다. 이게 개인정보 노출의 핵심이다.

- 기본값은 **직업 무관한 일반형**으로 (`기상 / 아침 / 운동 직후 / 점심 / 오후 / 저녁 / 자기 전`)
- 사용자가 각 칸의 **시간과 내용을 직접 고칠 수 있게** 한다
- localStorage 에 저장 (새 키 만들지 말고 `prof` 안에 넣는다)
- 교대·야간 근무자를 위해 **칸 추가·삭제**도 되게 한다

이걸 하면 개인정보가 빠지는 동시에 **적용 범위가 넓어진다.** 지금은 주방 노동자
전용이지만, 바뀌면 누구든 자기 하루에 맞춰 쓴다.

### 2. 숫자를 프로필에서 계산

- `96 → 80kg`, `86~88kg`, `170~190g` 을 전부 `prof` 기반 계산으로
- 이미 `prof.cur`, `prof.goal`, `prof.kcal`, `prof.prot` 이 있다. 그걸 쓰면 된다
- 단백질 권장은 `체중 × 2.0~2.2g` 로 계산해서 표시

### 3. 첫 실행 화면

구매자가 처음 열면 빈 화면이 아니라 **3단계 안내**가 떠야 한다.

1. 목표 방향(감량/유지/증량) + 현재·목표 체중
2. 주간 운동 요일 고르기 (기본 루틴 3종 제시: 3분할 / 4분할 / 전신 주3회)
3. Gemini 키 (건너뛰기 가능 — 없어도 앱은 돈다)

### 4. 판매용 빌드 분리

여행앱과 같은 구조로 간다.

```
private/personal.html   개인용 마스터 (형님이 쓰는 것)
src/index.html          판매용 생성물
scripts/build-sales.mjs 개인용 → 판매용 변환
```

- `SALE_MODE` 를 `true` 로 뒤집고
- 개인 문자열을 일반 문자열로 치환
- **앵커 검사**: 치환 대상이 하나라도 안 맞으면 빌드를 실패시킨다
- 판매용에 개인 문자열이 남아 있으면 배포를 막는 검사기(`verify-sales-only`)

### 5. 검사

여행앱 방식 그대로. 실제 Chromium 으로 돌린다.

- 판매용을 **데이터 0으로 띄워** 스크린샷 → 개인 흔적이 화면에 남지 않았는지
- `96`, `스태프밀`, `인포`, `86~88` 같은 문자열이 판매용에 없는지 정적 검사
- 기존 94건은 그대로 통과해야 한다

## 팔 때의 위치

여행앱과 **같은 사람에게 팔지 않는다.** 겹치는 고객이 아니다.

- 여행앱: 후쿠오카 가는 사람
- 운동앱: 커팅하는 사람

가격은 여행앱보다 낮게 잡는다. 기능이 더 좁다.
사진 칼로리 분석이 유일한 차별점이고, 그건 **쓸수록 정확해지는 개인 보정**이
핵심이다 — 이 점을 소개 문구의 중심에 둔다.

## 순서

1~3번을 먼저 한다. 그것만 해도 **남에게 줄 수 있는 상태**가 된다.
4~5번은 실제로 팔기 직전에 한다. 미리 만들면 유지할 것만 늘어난다.
