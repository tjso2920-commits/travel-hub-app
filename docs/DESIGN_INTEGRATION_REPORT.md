# 디자인 통합 결과 (2026-09-09, 3차 갱신 — 코드 검토 반영)

2차 보고를 ChatGPT가 코드 수준까지 검토했고, 실제 버그 5건을 지적받았다.
전부 재현·수정했다. 이 문서는 전체를 대체한다. 브랜치: `design-integration`
(origin 에 푸시함, `master`는 안 건드림, 공개 배포 안 함).

**먼저 정정할 것**: 2차 보고의 "170곳이 정답"은 틀렸다. 이름만 같은 곳을
자동으로 합치던 규칙 자체가 버그였고(아래 1절), 그 규칙으로 만든 170이라는
숫자도 같이 틀린 숫자였다. 이번엔 숫자를 먼저 정해 놓고 로직을 맞추지
않았다 — 로직을 바르게 고친 뒤 나온 숫자를 그대로 6절에 적는다.

## 0. 확정된 제품 방향 (변경 없음)

> 장소 보관과 여행 일정을 분리한다. 담아 둔 장소는 여러 도시를 포함해 계속
> 보관한다. 여행지를 바꿔도 지우지 않는다. 여행지 선택은 필터다.

## 1. 코드 검토 5개 항목 — 문제·원인·수정

### ① 이름만 같은 장소의 자동 병합 중단

**지적받은 문제**: `daMerge`가 URL·좌표·주소가 모두 다른 곳도 이름만 같으면
하나로 합쳤다. 서울과 부산의 동명 가게가 하나로 합쳐지는 걸 재현하셨다고
하셨는데, 실제로 재현됐다 — 주소가 있어도 병합 판정 자체가 주소를 안 보고
있었다.

**원인 두 가지**:
1. 좌표가 둘 다 없는 장소를 `이름|null|null`로 키를 만들어 "정확히 같은
   좌표"로 오판했다. `null`은 "좌표가 없다"는 뜻이지 "좌표가 같다"는 뜻이
   아닌데, 문자열로 이어붙이면 이 둘이 똑같아 보인다.
2. 위 키가 안 맞아도 이름만 같으면 병합하는 별도 경로가 있었다(직전 턴에
   "숫자를 맞추려고" 넣었던 규칙 — 이번에 뺐다).

**수정**(`private/personal.html`의 `fmMerge`, `src/design/import-adapter.js`의
`daMerge` 양쪽 동일 로직):

- 자동 병합은 **검증된 식별자**(`placeId`, URL, 또는 "이름 + 실제 좌표"만)로만
  한다. 좌표가 없는 장소는 `kName()`이 `null`을 돌려줘서 애초에 키 후보에서
  빠진다.
- 이름만 같고 검증된 식별자가 안 맞으면 자동으로 합치지 않고
  `dupCandidateIds`(서로 참조하는 "중복 후보" 목록)로만 남긴다. 사람이 화면에서
  "같은 곳이에요"를 눌러야 실제로 합쳐진다(`src/design/spots.js`의
  `resolveDup`, 어댑터의 `daResolveDup`).
- 이름은 같아도 **다른 곳이라는 증거**(주소로 확정된 도시가 서로 다르거나,
  좌표가 둘 다 있는데 5km 넘게 떨어짐)가 있으면 후보로도 안 묶는다
  (`fmPlacesConflict`/`daPlacesConflict`) — 서울·부산 재현 케이스가 바로 이거다.

**요청하신 세 숫자를 구분해 보고**(179건 원본, 실제 파일 재검증 — 6절에 전체
내역): **자동으로 새로 추가된 곳 178** / **검증된 식별자로 자동 갱신된 곳 1**
/ **확인이 필요한 중복 후보 8쌍(장소 16개가 연관)**. "보존된 장소 수"는 사람이
후보를 확인하기 전까지는 **178곳**이다(후보를 사람이 "같은 곳"이라고 확인할
때마다 하나씩 줄어든다 — 이건 이제 자동이 아니라 사람이 하는 일이므로 미리
숫자를 정해 둘 수 없다). 회귀 테스트 `t49`에 서울/부산 재현, 좌표 없는
동명 장소, 후보 확인 후 병합까지 전부 고정해 뒀다.

### ② 재가져오기 시 사용자 수정 내용 보존

**지적받은 문제**: 같은 URL의 CSV를 다시 넣으면 앱에서 고친 메모(note)가
CSV의 옛 값으로 덮어써졌다.

**원인**: 검증된 식별자로 매칭되면 무조건 새로 들어온 값으로 필드를 덮고
있었다 — "재수입"과 "사용자가 그 사이에 고쳤다"를 구분할 방법이 없었다.

**수정**: 장소마다 `originName`/`originNote`/`originAddress`(마지막으로
가져왔을 때의 원본 값)를 따로 저장한다. 재수입 시:

- **지금 값이 저장해 둔 원본 값과 같으면** → 사용자가 안 고친 것이므로 새
  원본 값으로 정상 갱신.
- **지금 값이 원본 값과 다르면** → 사용자가 그 사이 고친 것이므로 안 건드림.
- 두 경우 모두 `origin*` 자체는 항상 최신 원본으로 갱신해 둔다 — 나중에
  "원본이 뭐였는지"는 계속 추적 가능하게.

`t49`에 "재수입해도 사용자가 고친 메모는 안 덮임" / "안 고쳤으면 정상
갱신됨" 두 시나리오를 다 넣어 뒀다.

### ③ 여행지 필터 변경과 일정 초기화 분리

**지적받은 문제**: 나라·도시를 둘러보기만 해도 초기화 확인창이 뜸. 또
`tripReset`이 경비를 지우는데 백업에는 경비가 없고, 백업 오류도 무시하고
그냥 진행했다.

**원인**: 코드를 보니 `tripReset`이 `budget_v1`이라는 **존재하지 않는
storage 키**를 읽고/쓰고 있었다 — 실제 예산·지출은 `foodMap.budget`,
`foodMap.spends`, `foodMap.tripDays`인데 별도 키를 보고 있어서 백업도 삭제도
둘 다 실제로는 안 되고 있었다(직접 디버깅해서 확인한 진짜 버그).

**수정**:

- `fmSetCountry(v)` — 나라/도시를 바꾸기만 할 때는 **확인창 없음**. 지금
  편집 중인 일정이 있으면 `foodMap.itineraryStale = true`만 표시해 둔다(화면에
  "여행지가 바뀌었습니다" 안내).
- `fmStartNewTrip()` — 명시적으로 눌러야만 실행되는 별도 함수. 확인창에
  "장소는 지워지지 않고 보관됩니다"를 명시하고, **백업을 실제 필드
  (`hotel`/`d1`/`d2`/`course`/`plan`/`budget`/`spends`/`tripDays`)로 정확히
  만들어 내려받은 뒤에만** 지운다.
- `tripReset()` — 백업(`fm2Download`)이 예외를 던지면 **아무것도 지우지 않고**
  `alert`로 사람 말로 알려준다. 성공해야만 비운다.

디버깅 중 함께 발견한 관련 버그: `tripHasData()`가 초기화 뒤에도 계속
`true`를 돌려주고 있었다 — `renderFoodMap()`이 지워진 `foodMap.hotel`을
`{name:'',lat:null,...}` 같은 빈 껍데기로 다시 만들어 두는데, `!!foodMap.hotel`은
이 빈 껍데기도 참으로 본다. `foodMap.hotel && foodMap.hotel.name`으로
고쳤다. `t46`에 백업 성공/실패, 취소, 예산 보존까지 재작성해 뒀다.

### ④ "지역 확인 필요" 장소를 실제로 쓸 수 있게

**지적받은 문제**: 안내만 있고 사용자가 도시를 지정하는 흐름이 없었다.
또 후쿠오카 판정 사각 범위를 도시 확정처럼 쓰면 안 된다(범위가 실제
후쿠오카시보다 넓어서 사가·나가사키·구마모토 일부까지 포함한다).

**수정**(`src/design/spots.js`):

- 도시 미확인 장소 상세에 "이 장소 도시 지정하기" 버튼 → 도시 선택 시트
  (`cityAssignSheet`). 여러 장소를 고른 뒤 한 번에 지정하는 일괄 지정도
  같은 시트로 처리(`daAssignCity(places, ids, city)`).
- **도시 지정은 좌표 확인이 아니라는 문구를 시트에 명시**했다. 좌표가 없는
  장소는 도시를 지정해도 여전히 동선·거리 계산에는 못 쓴다(`hasCoords`가
  `true`인 곳만 계산 대상 — 화면에서 이걸 실제로 계산 가능한 것처럼 보이게
  하지 않는다).
- 후쿠오카 사각 범위는 `fmCityHint`/`daCityHint`라는 **별도 함수**로
  분리했다 — 확정값 `p.city`에는 절대 안 쓰고, "짐작으로 후쿠오카 같아요"
  라는 제안에만 쓴다. 확정은 `fmCityGuess`(주소 텍스트 매칭)만 한다.
- 중복 후보(③에서 나온 `dupCandidateIds`)도 같은 상세 화면에서 "같은
  곳이에요 · 합치기" / "다른 곳이에요" 두 버튼으로 처리한다.

### ⑤ 가져오기 완료·데이터 보존 확인

**지적받은 문제**: `handleRealFile`이 `A.saveFoodMap()`의 반환값을 무시하고
있었다 — 저장이 실패해도 성공한 것처럼 다음 화면으로 넘어갔다.

**수정**: `saveFoodMap()`의 `true`/`false` 반환을 확인해서, 실패하면
저장 공간이 가득 찼거나 시크릿 모드일 수 있다는 안내를 보여주고 **가져오기
화면으로 되돌아간다**(성공 화면으로 넘어가지 않음). 방금 병합한 내용은
storage에 실제로 안 들어간 상태이므로, 다음에 화면을 새로 열면 저장 전
상태(`foodMap`을 storage에서 다시 읽음)로 정리된다.

**cp1_/cs1_ 저장 공간 불일치**: `src/design/`(개발 중인 새 화면)은 `cp1_`,
현재 판매용(`src/index.html`)은 `cs1_`를 쓴다. 지금은 `src/design/`이 아직
production에 안 붙어 있어서 문제가 안 되지만, **이 화면을 판매용 자리에
붙이는 순간 사용자 storage가 갈린다.** `import-adapter.js`는 이미
`<meta name="sale-mode">`로 접두어를 정하게 바꿔 뒀다(하드코딩 상수가
아니라 메타 태그 하나만 바꾸면 되게) — 하지만 **실제 마이그레이션(기존
`cp1_` 사용자를 `cs1_`로 옮기는 코드)은 아직 안 짰다.** 출시 전 체크리스트에
반드시 넣어야 한다: (1) 붙이는 시점에 `cp1_foodmap_v1`이 있고
`cs1_foodmap_v1`이 없으면 자동 이전, (2) 이전 실패 시 기존 `cp1_` 데이터는
그대로 두고 사람 말로 안내.

**Takeout 도움말 문구**: "일반 저장 목록은 '저장됨(Saved)'을 선택하세요.
별표로 저장한 장소도 챙기려면(또는 어느 쪽인지 잘 모르겠으면) '지도(내
장소)'도 함께 선택하세요"로 바꿨다 — Saved만 안내하면 별표 장소를 놓친다.

## 2. 정정된 실제 수치 — "170에 맞추지 않았다"

사용자 실제 Takeout 파일(기본 목록 CSV 161행 + 가고 싶은 장소 CSV 3행 +
저장한 장소 GeoJSON 15개 = 179건)에 **고친 로직을 그대로 다시 돌려서** 나온
숫자다. 리뷰 데이터(5개)는 여전히 장소가 아니라서 제외했다.

```
1) 기본 목록 CSV        → added 161, updated 0, dupCandidates 0
2) 가고 싶은 장소 CSV    → added 2,   updated 1, dupCandidates 0   (CSV끼리 이름 완전 일치 1건 자동 갱신)
3) 저장한 장소 GeoJSON   → added 15,  updated 0, dupCandidates 8   (CSV와 이름은 같은데 URL·좌표 형식이 달라 후보로만 연결)
──────────────────────────────────────────────────────────────
합계                     added 178, updated 1, dupCandidates 8쌍(장소 16개 연관)
```

- **자동으로 병합된 것**: 1건(가고 싶은 장소 CSV와 기본 목록 CSV에 완전히
  같은 URL로 들어 있던 곳 — 검증된 식별자로 확실히 같은 곳이었다).
- **확인이 필요한 후보**: 8쌍. GeoJSON 쪽은 좌표·전용 URL 형식(`?cid=...`
  계열)이 있고 CSV 쪽은 그게 없어서, 이름만 보고 "혹시 같은 곳일 수 있다"고
  표시만 해 둔 상태다. **이 8쌍이 실제로 같은 곳인지는 코드가 아니라 화면에서
  사람이 확인해야 한다** — 2차 보고에서 "9건이 자동으로 겹친 것"이라고 한
  것 자체가, 겹쳐도 되는지 확인 안 하고 자동으로 합치던 버그의 결과였다.
- **지금 보관된 장소 수**: **178곳**(후보 상태의 16개도 각각 별개 레코드로
  전부 포함, 아직 하나도 사람이 확인 안 한 상태 기준). 사람이 8쌍을 전부
  "같은 곳"으로 확인하면 170으로, 전부 "다른 곳"으로 확인하면 178로 그대로
  남는다 — **진짜 정답은 사용자가 실제로 확인하기 전까지는 코드가 정할 수
  없다.** 이게 이번 검토가 지적한 핵심이었고, 숫자를 미리 정해 두지 않는
  걸로 반영했다.

도시 확정 현황(변경 없음, 참고용): 후쿠오카 13곳·다른 도시 1곳은 주소로
확정, **나머지 164곳은 지역 확인 필요**다(구글 Takeout 기본 CSV 내보내기
자체가 주소를 안 줘서다 — 거짓으로 도시를 우기지 않은 정직한 숫자다). 이번에
④에서 붙인 일괄 지정 화면으로 사람이 직접 채울 수 있다.

## 3. `private/personal.html` ↔ `src/index.html` 빌드 반영 (재확인)

`private/personal.html`이 유일한 원본이고 `npm run build`가 전체를 다시
생성한다 — 관계 자체는 2차 보고와 동일하다. 이번에 고친 `fmMerge`,
`fmPlacesConflict`, `tripHasData`, `tripReset`, `fmSetCountry`도 빌드 후
`src/index.html`에서 실제로 동작하는지 실행해서 확인했다(코드가 있는지
grep한 게 아니라 테스트를 두 파일 모두에서 돌렸다):

```
node scripts/test/t46.mjs private/personal.html  → 전체 통과
node scripts/test/t46.mjs src/index.html         → 전체 통과
node scripts/test/t49.mjs private/personal.html  → 전체 통과
node scripts/test/t49.mjs src/index.html         → 전체 통과
```

## 4. 파서·병합 로직이 원본과 새 화면에서 다르게 동작하지 않도록

`src/design/import-adapter.js`의 `daMerge`/`daCityGuess`/`daCityHint`/
`daPlacesConflict`는 `private/personal.html`의 `fmMerge`/`fmCityGuess`/
`fmCityHint`/`fmPlacesConflict`를 그대로 옮긴 것이다 — 함수 위 주석마다
원본 위치를 적어 뒀고, 이번 수정도 두 파일에 각각 동일하게 반영했다(의도적으로
뺀 부분은 자동 분류 호출과 무료판 한도 체크뿐이고, 주석에 "다음 단계에서
연결"이라고 명시해 뒀다 — 실수로 빠뜨린 게 아니라는 뜻이다). 지금은 사람이
두 파일을 나란히 놓고 대조하는 방식으로 동기화를 확인하고 있다 — 자동으로
두 파일의 동작이 갈리는 걸 잡아주는 테스트는 아직 없다. 다음 단계(②③④
진행 중)에서 두 파일이 같은 입력에 같은 결과를 내는지 비교하는 공용
테스트를 만드는 걸 제안한다(로직을 한 파일로 합치자는 게 아니라, 계속
따로 두되 결과가 갈리면 바로 잡히게 하는 것).
