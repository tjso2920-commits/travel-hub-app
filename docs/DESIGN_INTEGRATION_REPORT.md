# 디자인 통합 1차 결과 (2026-09-09)

`design/handoff-v5/` 인수인계 묶음 + 사용자가 보낸 실제 Google Takeout 데이터로
작업했다. 브랜치: `design-integration` (origin 에 푸시함, `master`는 안 건드림).

---

## 1. 읽은 문서

`00_START_HERE.md → 01_CLAUDE_PROMPT.txt → 02_DESIGN_CONTRACT.md →
03_INTEGRATION_AND_ACCEPTANCE.md → 05_IMPORT_ONBOARDING_SPEC.md →
06_UPDATES_AND_EXPORT_CORRECTION.md → approved-design/{index.html,spots.css,spots.js}`
순서대로 읽었다. `SHA256SUMS.json` 무결성도 `verify_bundle.py`로 통과 확인(38개
파일). `docs/DESIGN_HANDOFF.md`(내가 지난 세션에 써 둔 것)도 다시 확인했다 —
"AGENTS.md"는 이 저장소에 없고, 그 역할은 `docs/HANDOFF.md` +
`docs/DESIGN_HANDOFF.md`가 하고 있다.

## 2. 시작 전 저장소 상태

- `private/personal.html`이 여전히 원본이고, `npm run build`로 만든
  `src/index.html`이 깃허브에 올라간 것과 바이트 단위로 일치함을 재확인했다.
- `classic.html`은 승인 묶음 안에만 두고(`design/handoff-v5/approved-design/`),
  저장소의 최신 소스를 덮어쓰지 않았다.
- 실제 CSV/JSON(사용자가 보낸 것)은 어디에도 커밋하지 않았다 — 임시 폴더에서만
  검증하고, 저장소에는 **같은 모양의 합성 데이터**만 테스트로 남겼다.

## 3. 실제 데이터로 먼저 확인한 것 (요청하신 "정확성 먼저")

사용자가 보낸 두 ZIP을 풀어서 실제 내용을 봤다.

| 파일 | 내용 | 실제 파싱 결과 |
|---|---|---|
| `Save/기본 목록.csv` | 구글 기본 저장 목록(제목·메모·URL·태그·댓글, 한글 헤더) | 161곳, 이름 빠짐 0건 |
| `Save/가고 싶은 장소.csv` | 사용자가 만든 커스텀 목록 | 3곳 |
| `지도(내 장소)/저장한 장소.json` | GeoJSON, 좌표 있음 | 15곳(그중 2곳은 한국 — 경주·이태원) |
| `지도(내 장소)/리뷰.json` | 리뷰(별점·설문) | 5건 — **장소 목록이 아니므로 수입 대상에서 제외**했다 |

세 파일을 다 합치고 중복 제거하면 **178곳**. CSV 쪽은 주소도 좌표도 아예 없고,
URL도 좌표가 안 박힌 내부 feature-id 형식(`!1s0x...`)이라 `fmCoordFromUrl()`로도
못 꺼낸다. **좌표가 있는 건 178곳 중 15곳(8%)뿐** — 이게 지도 표시 정확도의
진짜 현재 한계다.

### 발견한 실제 버그 — `private/personal.html` 수정 (design-integration과 별개 커밋)

`fmInFukuoka()`가 좌표 없는 곳을 전부 걸러내고 있었다. 178곳 중 **165곳(93%)**이
"후쿠오카권" 필터에서 사라지는 걸 실제 데이터로 확인했다. `null>=32.7`이 조용히
`false`가 되는 게 원인 — `fmInArea()`(일반 나라용)는 "잴 근거 없으면 안 뺀다"
원칙이 있었는데 후쿠오카 전용 경로만 빠져 있었다. 고친 뒤 178곳 중 176곳 통과
(제외된 2곳은 좌표로 확인된 진짜 한국 주소). 회귀 테스트 `t48` 추가, 48개 검사
전부 기존 알려진 3건 제외 통과.

## 4. 실제로 만든 것 (design-integration 브랜치)

```
design/handoff-v5/              ← 승인 묶음 그대로 보존(원본, 안 건드림)
src/design/
  index.html                    ← 승인 마크업 이식(스크립트 참조만 변경)
  spots.css                     ← 승인 CSS 그대로 + 빈 사진 상태 스타일 추가분만
  spots.js                      ← 승인 이벤트 로직 그대로 + 데이터를 fixture→실데이터로
  import-adapter.js             ← 신규. personal.html 파싱 로직을 그대로 이식
  assets/                       ← 승인 사진·폰트 그대로
scripts/design-integration-check.mjs  ← 신규. 실제 브라우저로 파일 업로드까지 검증
```

`private/personal.html`의 `src/index.html`(지금 팔리는 앱)은 **UI 쪽은 전혀
안 건드렸다** — `fmInFukuoka` 버그 수정 한 곳만 예외(순수 로직 수정, 화면 변경
없음). `src/design/`은 완전히 새로운 별도 화면이라 기존 사용자에게 영향 없다.

### 어댑터가 하는 일 (`import-adapter.js`)

`private/personal.html`의 CSV/JSON 파서(`fmCsv`, `fmCsvRows`, `fmObj`, `fmJson`,
`fmCoordFromUrl`, `fm2Coord`)를 **새로 만들지 않고 그대로 옮겼다** — 이미 실제
178곳으로 검증된 코드를 재사용하는 게 다시 짜는 것보다 안전하다고 판단했다.
파일 위 주석에 각 함수의 원본 위치를 적어 뒀다(`personal.html`이 바뀌면 같이
맞춰야 한다는 표시).

## 5. 실제 브라우저로 검증한 것

`scripts/design-integration-check.mjs`(Playwright, 실제 Chromium)로 자동 검사
10건 — 전부 통과. 사용자의 실제 파일로도 수동 검증(스크린샷 첨부):

1. **처음 열면 데이터가 없어서 샘플 3곳**이 뜬다(이탈 방지 — 05_SPEC 요구사항)
2. **가져오기 다이얼로그**에서 실제 CSV 선택 → **161곳 확인**(실제 숫자, 지어낸 값 아님)
3. 3개 파일 다 가져온 뒤 **178곳**이 실제로 화면에 표시됨(카드 그리드까지)
4. 카드 하나를 열면 **실제 저장했던 이름**("멘야잇시 라멘")과 **실제 그 장소의
   구글맵 링크**가 뜬다 — "근처 아무 가게 검색"이 아니라 저장한 그 장소.
5. **사진이 없으면 승인 디자인의 사진 자리 안에서 빈 상태**(회색 칸 + 카테고리
   첫 글자)로만 뜬다. 샘플 사진(izakaya.webp 등)을 실제 매장 사진으로 붙이지
   않았다.
6. 검색("라멘") 정상 동작, 재수입 시 중복 0건(161→161, 새로 추가 0·기존 갱신
   161).
7. 도시 선택 시트: 지금은 활성 여행 하나뿐이라는 걸 **숨기지 않고 그대로
   안내**한다(6절 "결정이 필요한 것" 참고).
8. 콘솔/런타임 오류 0건.

## 6. 실제로 연결된 기능 vs 아직 샘플/데모

| 기능 | 상태 |
|---|---|
| CSV 가져오기(제목/메모/URL, 한글·영문 헤더) | ✅ 실제 연결, 실 데이터로 검증 |
| JSON(GeoJSON "지도(내 장소)") 가져오기 | ✅ 실제 연결, 좌표까지 반영 |
| 리뷰 데이터 자동 제외 | ✅ 연결 |
| 재수입 시 중복 방지(URL 또는 이름+좌표 키) | ✅ 연결, 실측 검증 |
| 도시별 카드 표시 | ✅ 연결(단, 지금은 "도시 1개"만 실질적으로 동작 — 8절 참고) |
| 장소 상세의 실제 구글맵 링크 | ✅ 연결(저장된 URL 우선, 없으면 이름 검색) |
| 사진 없을 때 빈 상태 | ✅ 연결(가짜 사진 금지 지켰음) |
| 검색·선택·오늘 동선 담기 | ✅ 실 데이터로 동작(동선 계산 자체는 다음 항목) |
| **ZIP 파일 직접 업로드** | ❌ 아직. 지금은 zip을 사람이 먼저 풀어서 csv/json을 골라야 한다. 05_SPEC이 요구하는 "ZIP 그대로 업로드"는 브라우저에서 압축을 풀 라이브러리가 필요한 별도 작업 — 화면 문구에도 "ZIP은 아직 자동으로 못 풀어요"라고 정직하게 적어 뒀다 |
| **카테고리 자동 분류(맛집·카페·이자카야 등)** | ❌ 아직. `personal.html`에는 `fmInfer()`라는 이름 기반 분류기가 이미 있는데(순서 규칙, 51개 실제 가게 이름으로 검증됨) 이 어댑터에는 아직 안 붙였다. 지금은 카테고리 정보가 원래 없는 CSV라 전부 "기타"로만 뜬다 |
| **사진·전화번호·영업시간(실제 매장 정보)** | ❌ Places API 등 공급자 연동이 필요 — 03_INTEGRATION 2단계(B), 아직 손 안 댐 |
| **GPS·최단 동선·이동시간** | ❌ 아직. 승인 디자인 자체가 이미 "아직 연결되지 않았습니다"라고 정직하게 표시하던 부분이라 그대로 뒀다 |
| **여러 도시 동시 관리(멀티 여행)** | ⚠️ 데이터 구조 결정 필요 — 8절 |
| **판매용(`SALE_MODE=true`) 전환** | ❌ `import-adapter.js`에 `SALE_MODE=false` 하드코딩, 실제 배포 전 정리 필요(TODO 주석 남김) |

## 7. 수행한 테스트 / 안 한 테스트

**했음**
- `scripts/design-integration-check.mjs` — 실제 Chromium, 진짜 파일 업로드,
  10개 자동 검사(위 5절)
- 기존 47개 jsdom 검사 + 새 `t48`(fmInFukuoka 회귀) — 48개 중 기존에 알려진
  3건만 실패, 새 회귀 없음
- `npm run verify`, `npm run build` 정상
- 사용자의 실제 파일 3개로 수동 전 과정(가져오기→표시→상세→검색→재수입) 확인

**안 했음 (솔직히 남김)**
- **실제 iPhone Safari**에서의 테스트 — 지금까지는 전부 데스크톱 Chromium
  자동화다. `03_INTEGRATION_AND_ACCEPTANCE.md` 6절이 요구하는 "실제 iPhone
  Safari에서 다운로드·앱 복귀·파일 선택까지 검증"은 아직 못 했다.
- **느린 네트워크 시뮬레이션** — `PERFORMANCE.json`도 "network_timing_measured:
  false"라고 이미 명시돼 있었고, 여기서도 아직 안 쟀다.
- **320px 초좁은 화면·글자 200% 확대·키보드 등장 시 레이아웃** — 아직 안 봄.
  기존 앱(`private/personal.html`)의 `npm run audit`가 이런 걸 검사하는데,
  `src/design/`은 아직 그 검사망 밖에 있다(9절에 남김).
- **잘못된 CSV(따옴표 깨짐·컬럼 순서 다름 등) 방어** — 어댑터가 쓰는 파서 자체는
  `personal.html`에서 이미 검증된 것이라 기본 방어는 되지만, 이 화면에서 직접
  깨진 파일을 넣어보진 않았다.

## 8. 결정이 필요한 것 (제가 임의로 안 정한 것)

**여러 도시(여행)를 동시에 관리할 것인가.**
승인 디자인은 후쿠오카·삿포로·뉴욕을 한 화면에서 넘나드는 걸 전제로 한다
(`03_INTEGRATION_AND_ACCEPTANCE.md`: "후쿠오카에서 선택한 장소가 뉴욕 동선에
섞이지 않음"). 그런데 지금 앱의 실제 데이터 구조는 **활성 여행 하나만** 관리한다
— 나라를 바꾸면 이전 여행을 백업하고 비운다(`tripReset()`, 이전부터 그랬다).
이 둘이 정면으로 다르다. 지금은 "활성 여행 하나 = 도시 하나"로 정직하게 축소해
두고 화면에도 그렇게 안내했다(6절 스크린샷 참고). 여러 여행을 실제로 동시
저장하려면 `foodmap_v1`의 데이터 구조를 바꿔야 하고, 이건 기존 사용자 저장
데이터에 영향을 주는 결정이라 제가 임의로 하지 않았다.
→ **정할 것: 지금처럼 "여행 하나"로 계속 갈지, 여러 여행을 동시에 저장하는
구조로 바꿀지.** 후자면 마이그레이션 계획을 따로 세워야 한다.

**이 새 화면(`src/design/`)을 실제로 어디에 연결할 것인가.**
지금은 기존 앱과 완전히 분리된 별도 페이지다(안전하게 검증하려고 일부러
그렇게 뒀다). 다음 중 뭘 원하시는지에 따라 다음 단계가 달라진다.
1. 기존 앱(`src/index.html`) 안에 새 탭/화면으로 추가
2. 이 화면이 새 메인 화면이 되고 기존 화면은 "기존 앱 열기" 링크로만 남음
3. 완전히 이 디자인으로 교체(기존 UI 코드 정리)

**카테고리 자동 분류를 언제 붙일 것인가.** 지금 하면 필터 칩이 "기타" 하나가
아니라 실제로 여러 개로 나뉜다 — 승인 디자인이 원래 기대하던 모습에 훨씬
가까워진다. 다음 단계로 바로 넣어도 되는 작업이라 우선순위만 여쭙는다.

## 9. 다음 단계 제안 (승인 시 진행)

우선순위 순서로 제안한다 — 결정 필요한 8절 항목은 먼저 답 주시면 좋다.

1. 카테고리 자동 분류(`fmInfer`) 연결 — 필터가 실제로 의미 있어짐
2. `src/design/`을 `npm run audit`(대비·터치영역·가로넘침·iOS 확대유발) 검사망에 포함
3. 실제 iPhone Safari 수동 검증(다운로드 → 파일 앱 → 이 화면에서 선택)
4. 8절 결정에 따라: (a) 여러 여행 구조 설계 또는 (b) 지금 구조 유지 확정
5. ZIP 직접 업로드(브라우저 zip 라이브러리 검토 — 새 외부 의존성이라 신중히)
6. 이 화면을 기존 앱에 실제로 연결(8절 두 번째 결정에 따라)
