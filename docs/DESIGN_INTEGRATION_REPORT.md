# 디자인 통합 결과 (2026-09-10, 5차 갱신 — 재현된 버그 4건 수정 + 정정)

3차 보고 이후 ChatGPT가 다시 코드 수준까지 검토해 6개 항목(①~⑥)을
추가로 지적했고, 이어서 로드맵 ②(ZIP 직접 가져오기)·③(유형 분류)·
④(실제 코스 생성)와 폰트 문제·⑦(실제 위치 확인)까지 처리한 것이 4차
보고였다. **이번 5차는 4차 보고 내용 중 실제로 재현된 버그와 과장된
표현을 정정한 라운드다** — 아래 "## 1-B"를 반드시 4차 내용과 함께
읽을 것. 브랜치: `design-integration`(origin에 푸시함, `master`는 안
건드림, 공개 배포 안 함).

---

## 0. 확정된 제품 방향 (변경 없음)

> 장소 보관과 여행 일정을 분리한다. 담아 둔 장소는 여러 도시를 포함해 계속
> 보관한다. 여행지를 바꿔도 지우지 않는다. 여행지 선택은 필터다.

## 1-B. 5차 갱신 — 재현된 버그 4건 + 표현 정정 (2026-09-10)

4차 보고 이후 ChatGPT가 다시 검토해 지적한 항목 중, **실제로 코드를
재현해 확인된 것만** 여기 정리한다. "설계했다"·"완료했다"는 표현이
붙어 있던 항목 중 실제로는 라벨링/휴리스틱 수준이었던 것도 여기서
바로잡는다.

### 1-B-1. 표현 정정 — "실제 도보 경로 완료"는 틀린 표현이었다

4차 보고 7절이 OSRM 연동을 설명하면서 검증 수준을 문장 안에 적어
두긴 했지만("이 샌드박스는... 실제 공개 서버 연결 자체는 여기서
확인하지 못했다"), 대화 중 구두로 "실제 도보 경로 완료"라고 요약해
전달한 적이 있다 — 이 표현은 철회한다. 지금까지도, 이번 5차 수정
이후로도 확인된 것은 다음까지다:

- OSRM Trip 서비스에 **공식 문서가 지원을 확인한 파라미터 조합**으로
  요청을 만든다(아래 1-B-2).
- 그 응답이 온다면, 정확한 모양으로 해석하고 방문 순서·구간 거리를
  올바르게 뽑아낸다(mock 응답으로 확인).
- 응답이 도보로 보기엔 말이 안 되는 속도라면 실제 경로로 인정하지
  않고 직선거리 추정으로 정직하게 넘어간다(아래 1-B-2, 새로 추가).

확인되지 않은 것: 이 개발 환경(샌드박스)은 조직 네트워크 정책으로
`router.project-osrm.org`로 나가는 실제 요청 자체가 막혀 있다
(`curl`로 직접 확인 — 프록시가 `CONNECT tunnel failed, response 403`을
돌려준다). 그래서 **진짜 공개 OSRM 서버에 실제로 연결되는지는 이
환경에서 검증할 방법이 없다.** 최종 사용자 브라우저는 이 프록시를
거치지 않지만, "실제 서버 연결까지 확인했다"는 말은 이 환경에서는
할 수 없다 — 실제 배포 환경에서 별도로 확인해야 하는 항목으로 남긴다.

### 1-B-2. OSRM Trip 파라미터 조합 수정 (재현된 문제)

**문제**: `src/design/course.js`가 `roundtrip=false&source=first`로
호출하면서 `destination`을 안 넘겼다(기본값 `any`). OSRM 공식 문서
(https://project-osrm.org/docs/v5.24.0/api/)를 확인한 결과, Trip
서비스가 실제로 지원을 보장하는 조합은 세 가지뿐이다:

```
roundtrip=true,  source=any,   destination=any
roundtrip=true,  source=first, destination=any
roundtrip=false, source=first, destination=last
```

`roundtrip=false` + `destination` 생략(`any`)은 이 목록에 없다 —
지원이 확인되지 않은 조합이었다. 그렇다고 `destination=last`를 그냥
붙이면 "마지막에 담은 곳"이 사용자 의도와 무관하게 강제로 코스의
종점이 되어 버린다(금지 지시사항).

**수정**: 공식 지원 조합인 `roundtrip=true&source=first`로 바꿨다
(출발지에서 출발해 전부 들르고 출발지로 돌아오는 순환 경로). 응답의
`legs` 배열 마지막 구간(마지막 방문지 → 출발지로 돌아오는 구간)만
잘라내 편도로 쓴다 — 방문 순서·구간별 실거리는 순환이든 편도든
동일하게 유효하다.

**추가 방어**: 프로필 오응답(예: 서버가 도보 대신 자동차 프로필로
응답)을 클라이언트에서 확신할 방법이 없으므로, 구간 평균 속도가
사람 도보 범위(시속 약 1~7.9km, `courseSpeedPlausible`)를 벗어나면
"실제 경로"로 인정하지 않고 직선거리 추정으로 넘어간다.

**검증**: `scripts/test-course-generation.mjs`에 정상/실패/**비정상
속도** 세 가지 mock 시나리오를 모두 추가해 전체 통과 확인(1-B-1의
한계는 그대로 남음 — mock 검증일 뿐 실제 서버 연결 검증 아님).

### 1-B-3. 코스 생성 — 가용 시간·출발 시각·도시 필터 미반영 (재현된 문제)

**문제 4가지, 전부 재현됨**:
1. `runCourseGeneration`이 `budgetMinutes`를 입력창에서 읽기만 하고
   실제 계산에는 전혀 쓰지 않았다 — 가용 시간을 얼마를 넣어도 코스
   길이가 안 바뀌었다.
2. 출발 시각이 `9 * 60`(오전 9시)으로 고정돼 있었다 — 밤에 눌러도
   "9시부터"로 계산해 도착 예정 시각이 실제와 무관했다.
3. "오늘 동선"(`route`) 후보 목록이 `route.has(id)`만 확인하고 현재
   보고 있는 도시로 거르지 않았다 — 도시를 바꾼 뒤에도 이전 도시
   장소 id가 `route`에 남아 있으면 코스 계산에 섞여 들어갈 수 있었다.
4. "새로 만들기"를 누르면 `delete foodMap.course`로 **기존 코스를
   먼저 지우고** 나서 새 코스를 만들었다 — 출발지 화면을 취소하거나
   생성이 실패하면 이전 코스가 사라진 채로 안 돌아왔다.

**수정**:
1. `courseGenerate`(course.js)가 `opts.budgetMinutes`를 실제로 써서,
   출발 시각부터 누적 시간이 예산을 넘기는 지점부터는 뒤쪽 곳을
   전부 `excludedReasons[id]='time-budget'`로 분리한다(좌표가 없어서
   빠진 것과는 다른 이유로 화면에 따로 안내).
2. 출발 시각을 여행지 **현지 시각의 지금 시각**으로 계산한다
   (`A.destNow(city)` — 도시명→IANA 시간대 매핑 후
   `Intl.DateTimeFormat`으로 환산. 나라 안에 시간대가 여럿인 나라는
   대표 시간대로 근사 — 한계로 남김).
3. `showRoute`/`buildCourseSheet`/`runCourseGeneration`이 후보 목록을
   `p.city === city`로 한 번 더 거른다.
4. "새로 만들기"는 이제 기존 코스를 바로 지우지 않고 출발지 시트로만
   넘어간다 — 새 코스가 실제로 완성되고 저장에 성공했을 때만
   `foodMap.course`를 교체한다(`runCourseGeneration` 안에서). 취소·
   실패 시 이전 코스가 그대로 남는다.

저장되는 코스 객체에도 `city`·`origin`·`mode`·`startMinutes`·
`budgetMinutes`·`excludedReasons`를 같이 남겨, 나중에 "이 코스가 어느
도시·어떤 조건으로 만들어졌는지" 확인할 수 있게 했다. 도시를 바꾼
뒤 `showRoute()`를 다시 열면, 저장된 코스의 `city`가 지금 도시와
다를 경우 그 코스를 자동으로 보여주지 않는다(다른 여행지 코스가
지금 코스인 것처럼 뜨는 사고 방지).

**검증**: `scripts/test-course-generation.mjs`에 가용 시간 초과 시나리오,
"새로 만들기 취소해도 기존 코스 보존" 시나리오를 새로 추가해 통과 확인.

### 1-B-4. daMerge/daResolveDup 재발 버그 — 별칭 승인 vs 미해결 충돌 구분 안 됨 (재현된 문제)

**재현 시나리오**: 같은 상호를 placeId A/B로 각각 저장 → 사람이 "같은
곳이에요·합치기"로 수동 병합(B가 A의 별칭(`aliasPlaceIds`)으로 남고
삭제됨) → **삭제된 B의 placeId로 다시 파일을 가져오면 레코드가
2개로 다시 늘어났다**(병합이 무의미해짐).

**원인**: `fmMerge`/`daMerge`의 "강한 식별자 충돌 검사"가 `x.placeId`가
기존 레코드의 **주 식별자**와 다르면 무조건 충돌로 보고 자동 병합을
막았다 — `x.placeId`가 그 레코드의 `aliasPlaceIds`(사람이 이미
"같은 곳"이라고 승인해 남겨 둔 별칭)에 있는 경우까지 구분 없이
튕겨냈다.

**수정**: `x.placeId`가 `aliasPlaceIds`에 있으면 충돌이 아니라 별칭
재확인으로 본다. 완전히 무관한 placeId(별칭 목록에 없음)는 여전히
충돌로 처리해 자동 병합하지 않는다(정상 동작 유지).

**부가 발견·수정**: 식별자가 전혀 없는 항목(URL·주소·좌표 없음)은
**같은 파일을 반복해서 올릴 때마다** 매번 새 "중복 후보" 레코드가
쌓여 개수가 계속 늘었다(사람이 매번 확인해야 하는 대상이 계속
쌓인다는 뜻 — "질문을 반복 안 하는 것"과 "레코드 자체가 안 느는
것"은 다르다). `importKeys`(출처+내용 지문) 기록을 추가해, 같은
출처에서 이미 받아들인 내용의 재수입은 후보로 또 쌓지 않고 기존
레코드를 갱신 처리하게 했다. 다른 출처에서 온 동일 이름은(증거가
없으므로) 여전히 정직하게 후보로 남는다.

**검증**: `private/personal.html`(`scripts/test/t49.mjs` 9·10절 추가)·
`src/index.html`(같은 파일 재빌드 후 재실행)·`src/design/import-adapter.js`
(`scripts/design-integration-check.mjs` 재수입 시나리오 갱신) 세 곳
전부에서 동일하게 확인. **미완료 항목**: 실제 Google Takeout 179건
데이터셋으로 이번 최종 로직을 재실행해 신선한 수치를 보고하는 작업은
이 세션의 샌드박스에 그 파일이 없어 수행하지 못했다 — 이전 세션이
로컬에 갖고 있던 파일로 추정되며, 이번 컨테이너에는 없다(추정치를
"재검증 수치"로 보고하지 않는다). 같은 파일을 다시 전달받으면 바로
재실행해 보고할 수 있다.

### 1-B-5. daNeedsLookup — "완료"가 아니라 라벨링 휴리스틱이었다 (정정, 수정 완료)

4차 보고가 이 항목을 로드맵 ⑦의 일부로 "완료"라고 적었는데, 실제로는
**저장된 링크가 짧아서 좌표를 URL 문자열만으로 못 뽑는 경우를 표시만
하는 안내 휴리스틱**이지, 실제 좌표 조회 기능이 아니다(이 성격 자체는
지금도 그대로다 — 실제 서버 조회는 여전히 미구현, 아래 참고).

**재현된 구체 버그**: 좌표가 없는 FID 링크(`!1s0x...:0x...`, 좌표
성분 없이 식별자만 있는 형태)가 축약 링크 패턴에도, cid 패턴에도 안
걸려 `needsLookup=false`로 잘못 판정됐다 — "더 확인할 것 없음"으로
조용히 넘어간 것이다.

**수정**: `daNeedsLookup`을 `daLookupState(p)`라는 상태 분류 함수
기반으로 다시 짰다 — `has-coords`(좌표 있음) / `short-link`(축약
링크) / `place-id-no-coords`(FID·cid·place_id 등 특정 장소 식별자는
있는데 URL에 좌표가 없음 — 이번에 새로 잡음) / `ambiguous-search`
(검색 URL이라 애초에 어떤 장소인지도 특정 안 됨) / `no-evidence`
(URL 자체가 없음 — 이전엔 `false`였는데, 이건 확인할 게 없는 게
아니라 근거가 가장 부족한 상태라 이제 확인 필요로 분류). 화면 안내
문구도 상태별로 정확하게 나눴다(예: FID 링크를 더 이상 "축약
링크"라고 잘못 부르지 않는다). **여전히 미구현인 것**: 실제 서버
쪽 장소 조회 실행 자체(소비자 API 키 요구 금지 원칙상 백엔드가
필요 — 8절/#21). 이번 수정은 "어떤 상태인지 정확히 구분해 보여주기"
까지다.

**검증**: `scripts/design-integration-check.mjs`에 FID 링크 재현
시나리오를 추가해 통과 확인.

### 1-B-6. ZIP 처리 — 파일명만으로 걸러 다른 서비스 파일까지 압축 해제될 수 있었다 (재현된 문제, 수정 완료)

**문제 3가지**:
1. 필터가 파일명 확장자(csv/json)와 "review 포함 여부"만 봤다 —
   계정 전체 Takeout ZIP 안의 Gmail·캘린더 등 **다른 서비스** 파일도
   경로와 무관하게 압축을 풀어버릴 수 있었다.
2. 항목 하나당 30MB, 개수 500개 상한은 있었지만 **전체 압축해제
   총량**에는 상한이 없었다 — 500개가 상한 근처까지 쌓이면 합계가
   커질 수 있었다.
3. 타임아웃이 "결과만 먼저 포기"했다 — `setTimeout`으로 실패 결과를
   반환할 뿐, 내부적으로 돌고 있던 `fflate.unzip()`(비동기 콜백 기반)
   작업 자체는 계속 실행되고 있었다.

**수정**: `fflate.unzip()`(취소 불가한 비동기 콜백 API) 대신
`fflate.Unzip`+`fflate.UnzipInflate`(스트리밍 API)로 다시 짰다 —
항목을 우리가 하나씩 직접 통제하므로:
- 경로 필터(`daIsPlacesPath`)를 새로 추가해 Saved·저장(됨)·Maps·
  지도(내 장소) 폴더 **안에** 있는 csv/json만 압축을 푼다.
- 전체 압축해제 총량 상한(기본 200MB)을 추가했다.
- 시간 예산을 넘긴 시점부터는 남은 항목의 압축 해제(`file.start()`)
  자체를 시작하지 않는다 — 이게 진짜 "중단"이다.

**검증**: `scripts/test-zip-import.mjs`에 다른 서비스 파일 배제·전체
용량 상한·타임아웃 중단 시나리오를 추가해 통과 확인. **전부 합성
(직접 만든) ZIP으로만 검증했다** — 실제 Google Takeout이 만드는
정확한 폴더명은 로케일·시점에 따라 다를 수 있어, 이 환경에서는
실제 Takeout ZIP으로 재현·검증하지 못했다(사용자의 실제 개인
Takeout ZIP을 테스트 재료로 요청하지 않는다는 원칙 유지). 실사용에서
정상 파일이 걸러진다는 보고가 오면 경로 패턴을 넓혀야 한다.

## 1. 추가 코드 검토 6개 항목 — 문제·원인·수정 (4차, 위 1-B로 일부 정정됨)

### ① daMerge: origin\* 필드가 없는 기존 레코드를 무조건 덮어쓰던 버그

**지적받은 문제**: `exact.originNote`가 없는(마이그레이션 전에 만들어졌거나
`fmAdd`로 손으로 추가한) 기존 레코드는 `exact.note === (exact.originNote
!== undefined ? exact.originNote : exact.note)`가 `exact.note === exact.note`
꼴이 되어 항상 참이 된다 — 즉 원본 추적이 없는 곳은 사용자가 이미 고친
값이든 아니든 무조건 새 값으로 덮였다.

**수정**: origin\*이 없으면 **이번엔 값을 그대로 두고** origin\*만 새로
채운다(원본을 모르면 사용자가 이미 고쳐 놨을 수도 있으니 보수적으로
보존). 다음 재수입부터는 정상적으로 비교 가능해진다. 단, 이번에
보수적으로 보존된 필드는 origin\*이 "이번 수입 값"으로 설정되므로, 그
뒤로도 사용자가 실제로 고친 적이 없어도 값 자체가 우연히 그 값과
같아지기 전까지는 계속 안전하게 보존되는 쪽으로 남는다(자동으로
다시 덮어쓰기 시작하는 것보다 사람이 확인하게 남겨두는 쪽이 안전하다는
판단 — `t49`에 이 정확한 시나리오를 회귀 테스트로 고정).

### ② daResolveDup: 별칭 식별자 보존 + 메모 병합 + 참조 이전

**지적받은 문제 3가지**:
1. 합친 뒤 삭제되는 쪽의 URL·placeId를 별칭으로 안 남겨서, 그 파일을
   다시 가져오면 이미 합친 곳이 **새 레코드로 재생성**될 수 있었다.
2. 양쪽 메모가 다 있고 다르면 한쪽을 버렸다.
3. 방문 기록·분류·일정 참조(오늘 동선)가 삭제되는 쪽 id에 남아 있으면
   조용히 사라졌다.

**수정**(`fmResolveDup`/`daResolveDup` 양쪽 동일):
- `aliasUrls`/`aliasPlaceIds`에 삭제되는 쪽의 식별자를 남기고, `fmMerge`/
  `daMerge`의 검색 키(`regKeys`)에도 이 별칭들을 등록한다 — 재수입 시
  별칭으로 살아남은 레코드를 다시 찾아 "갱신"으로 처리되지, 새 레코드가
  또 생기지 않는다.
- 메모가 양쪽에 다 있고 다르면 `a.note + ' / ' + b.note`로 이어붙인다.
- 방문 기록·분류는 살아남는 쪽에 없으면 삭제되는 쪽에서 가져온다.
- 반환값을 `{mergedId, survivorId}`로 바꿔서, 호출자(`spots.js`)가 "오늘
  동선"(`route`)·선택(`selected`)에 남아 있던 삭제되는 쪽 id를 살아남는
  쪽으로 옮길 수 있게 했다.
- `dismiss`(다른 곳이에요)한 조합은 `dismissedDupKeys`(이름+주소+URL
  내용 기반 키)로 기억해 뒀다가, 같은 조합이 재수입돼도 같은 판단을 또
  묻지 않는다 — 식별자가 없는 동일 파일의 반복 업로드에도 사람이 같은
  질문에 매번 답할 필요가 없다.

Playwright로 화면에서 실제로 "같은 곳이에요·합치기"를 눌러 별칭이
남는지, 그 별칭 URL로 재수입해도 새 레코드가 안 생기는지까지 확인했다
(`design-integration-check.mjs`).

### ③ 식별자 충돌 우선순위 + URL 종류 구분

**지적받은 문제**: 이름+동일 좌표(`kName`) 매칭이 서로 다른 placeId가
있어도 병합할 수 있었다. 또 검색 URL(`/maps/search/?...`)을 특정 장소
식별자로 취급하면, 대체 링크 생성 함수(`fmLink`)가 우연히 같은 검색
URL을 만들어 냈을 때 서로 다른 장소가 같은 식별자로 오인될 위험이
있었다.

**수정**:
- `fmIsPlaceUrl`/`daIsPlaceUrl` 신설 — `/maps/search/`는 식별자로 안 쓰고,
  `place_id:`, `cid=`, FID(`!1s0x...`), `/maps/place/`만 특정 장소
  식별자로 인정한다.
- `fmPlacesConflict`/`daPlacesConflict`에 "양쪽에 placeId가 실제로 있고
  서로 다르면 충돌"을 추가 — 이름+좌표가 같아 보여도 placeId가 다르면
  자동 병합을 거부한다(같은 건물의 다른 가게 등).

### ④ finishCityAssign/resolveDup 저장 실패 시 롤백

**지적받은 문제**: `handleRealFile`만 저장 실패 시 원상 복구했고,
`finishCityAssign`·`resolveDup`은 저장이 실패해도 메모리 상태가 반쯤
바뀐 채로 남아, 나중에 다른 저장이 성공하면 그 실패한 변경까지 몰래
같이 저장될 위험이 있었다.

**수정**: 세 함수 모두 같은 패턴으로 통일 — 저장 실패 시
`foodMap = A.loadFoodMap()`로 storage의 마지막 정상 상태를 다시 읽어
메모리를 맞춘다.

### ⑤ tripHasData: 코스·경비만 있어도 감지

**지적받은 문제**: 숙소 이름·시작일이 없으면 코스나 예산만 있어도
"일정 없음"으로 판정돼, 여행지를 바꿀 때 되돌릴 수 없이 조용히 지워질
뻔했다.

**수정**: `foodMap.course`/`foodMap.plan`이 있거나, 예산이 0보다 크거나,
지출 기록이 하나라도 있으면 "일정 있음"으로 본다.

### ⑥ 백업 파일 실제 복원 경로

**지적받은 문제**: "백업 파일을 내려받는다"까지만 있고, 그 파일을 다시
불러와 실제로 복원하는 경로가 없었다.

**수정**: `fmRestoreTrip(inp)` 신설 — 백업 json을 다시 읽어 숙소·날짜·
코스·예산·지출을 그대로 되돌린다. 형식이 아닌 파일은 거부하고 기존
일정을 안 건드린다. "여행 준비" 패널에 "📂 백업 파일로 일정 복원하기"
버튼을 추가했다. (다운로드가 실제로 기기에 저장됐는지는 웹에서 확인할
수 없다는 한계는 그대로 — "성공"은 "예외 없이 끝났다"는 뜻이다.)

### cp1_/cs1_ 저장소 이전 — 실제 구현

3차 보고에서 "계획만 있고 코드는 없다"고 밝혔던 부분을 이번에 실제로

## 2. 한글 폰트 완성형 전체 지원

**지적받은 문제**: 실제 korean-400/500/600.woff2가 각각 294자만 담고
있어 '쿄·토·멘' 같은 흔한 한글 음절도 시스템 폰트로 대체됐다.

내려받아 자체 호스팅 — 완성형 한글 11,172자 전부(U+AC00-D7A3)와 자모,

늘어 이번 범위에서 뺐다.

**검증(실제 Chromium)**: `document.fonts` API로 '쿄·토·멘' 포함 실제
텍스트가 Noto Sans KR로 커버됨을 확인했고, 372개 조각 중 실제 쓰는
문자에 필요한 조각만(테스트 34개) 내려받아 분할 로딩이 실제로 동작함을
확인했다(`scripts/test-font-coverage.mjs`). 전송량: `korean-fonts.css`
원본 244KB → gzip 70KB(한 번 받으면 캐시됨), 첫 진입 시 실제 폰트 조각
전송은 약 670KB(전엔 3파일 약 60KB였지만 글자가 빠져 있었다). 모바일
뷰포트(390×844)에서 렌더링 확인. **iPhone Safari 실기기 검증은 아직
안 했다** — "실기기 미검증"으로 남긴다.

## 4. ZIP 직접 가져오기 (로드맵 ②)

사용자가 미리 압축을 풀 필요 없이 Takeout ZIP을 그대로 선택할 수 있게
했다. `fflate`(MIT 라이선스, 32KB)를 `src/design/vendor/`에 자체
호스팅해 브라우저에서 직접 zip을 읽는다 — 외부 CDN이 아니라 저장소에
포함했다.

- **압축 해제 "전에" 파일명으로 걸러낸다**(`fflate`의 `filter` 콜백) —
  Saved CSV·저장한 장소 JSON만 압축을 풀고, 리뷰 파일명은 애초에 안
  푼다. 사진 등 우리가 안 쓰는 대용량 항목은 압축조차 안 푼다 — 이게
  진짜 안전장치다(다 풀고 나서 버리면 이미 브라우저가 멈춘 뒤다).
- **안전장치**: 압축 파일 자체 300MB 상한, 개별 항목 압축 해제 후 30MB
  상한, 최대 500개 항목, 60초 시간 제한.
- 일부 파일이 형식 깨짐 등으로 실패해도 성공한 파일은 그대로 반영한다.
  가져오기 결과 화면에 **파일별 성공/실패/제외 이유**를 목록으로 표시한다.

**검증(실제 Chromium + 진짜 zip 파일)**: 중첩 폴더의 CSV 2개+JSON 1개
정상 처리, 리뷰 파일 제외(제외 이유와 함께 표시됨), 같은 zip 재업로드
시 중복 폭증 안 함, 개별 항목 용량 제한 실제 동작, 손상된 zip과 대상
파일 없는 zip 각각 안내 확인(`scripts/test-zip-import.mjs`).

**확인한 한계**: zip 파일명의 한글 처리는 표준 UTF-8 플래그 비트
(APPNOTE.TXT 11번)를 따른다. 이 비트가 없는 zip(예: 이 샌드박스의
Info-Zip 기본 설정)은 한글 파일명이 깨질 수 있다는 걸 실제로 재현하고
원인을 확인했다 — Python zipfile처럼 비트를 표준대로 세우는 도구로
만든 zip은 정상 동작함을 교차 확인했다. **실제 Google Takeout ZIP으로는
검증하지 못했다**(실기기 미검증과 같은 성격의 한계 — Google이 현대적
표준을 따를 것으로 보는 게 합리적이지만 직접 확인하지는 않았다).

## 5. 실제 위치 확인 — 저장된 식별자 우선, API 키 요구 없음 (로드맵 ⑦)

도시 일괄 지정과 실제 좌표 확인을 구분해 온 데 이어, 좌표 확인 자체도
"저장된 정보로 바로 되는 것"과 "추가 조회가 필요한 것"을 나눴다.

- `daNeedsLookup` 신설 — 좌표가 없고 URL이 `goo.gl/maps`·
  `maps.app.goo.gl` 같은 축약 링크이거나 `cid`만 있어 URL 문자열만으로는
  좌표를 못 뽑는 경우만 "추가 조회 필요"로 표시한다. FID(`!3d!4d`)·
  `@lat,lng`·`q=lat,lng` 등 URL에 좌표가 그대로 있는 경우는 이미 조회
  없이 뽑아내고 있었다(기존 `fmCoordFromUrl`, 이번에 회귀 테스트로
  재확인).
- **소비자에게 API 키를 입력하게 하지 않는다.** "추가 조회 필요" 항목은
  자동으로 조회하지 않고, Google 지도에서 직접 열어 확인하도록 안내만
  한다. 화면 어디에도 API 키 입력창이 없음을 실제 Chromium으로 확인했다.

**참고 — 기존 앱의 선택적 기능**: `private/personal.html`(기존 앱)에는
사용자가 **자기 소유의** Places/YouTube API 키를 직접 넣는 선택적 보강
기능이 이미 있다("목록·거리·검색 링크는 API 키 없이 작동합니다. 키는
이 기기에만 저장되며 내보내는 파일에는 포함되지 않습니다"로 이미
고지돼 있다). 이번 로드맵은 새 화면(`src/design`) 기준이라 이 기존
기능은 건드리지 않았다 — **새 화면이 판매 화면 자리를 대체하기 전에
이 기존 기능을 유지할지 재검토가 필요하다.**

## 6. 유형 분류 — 확인된 유형 우선, 사용자 수정 보존 (로드맵 ③)

`fmInfer`/`daInfer`(이름·메모·주소를 여러 언어로 보는 다국어 규칙 —
한국어·일본어·영어·프랑스어·터키어·베트남어 등을 같이 봐서 애초에
특정 여행지 전용이 아니었다)를 실제 병합 경로에 연결했다.

- 원본에 확인된 유형(`cat`, 예: Places API 보강 결과)이 있으면 이름
  기반 추정보다 우선 사용한다.
- 이름으로 짐작한 값은 `catConfirmed=false`로 남겨 "짐작"임을 화면에
  구분해 보여준다.
- `fmSetCat`/`daSetCat` 신설 — 사용자가 화면에서 직접 유형을 고르면
  `catConfirmed=true`로 남아 재수입해도 절대 안 덮인다.
- `personal.html` 장소 목록에 유형 선택 드롭다운(짐작이면 배지 표시),
  `design` 화면 상세 시트에 "유형이 맞나요? 수정" 버튼 + 유형 지정 시트.
- 유형 목록은 기존 그대로(맛집·식당·바·이자카야·카페·디저트·숙소·교통·
  사우나·온천·마사지·스파·약국·병원·관광·명소·쇼핑·기타).

실제 Chromium에서 화면에서 유형을 직접 고르고 재수입해도 유지되는지까지
확인했다.

## 7. 실제 코스 생성 (로드맵 ④, 2026-09-10 수정분은 1-B-2·1-B-3 참고)

"오늘 동선"에 담아 둔 곳을 실제 방문 순서·이동시간으로 바꾸는 기능을
새로 붙였다. **직선거리 정렬을 실제 최단 동선처럼 보여주지 않는다.**

- 도보는 OSRM 공개 라우팅 서버(`router.project-osrm.org`, 계정·API 키
  불필요)의 `/trip/` 엔드포인트로 실제 방문 순서 최적화 + 구간별 실제
  거리·시간을 계산한다. **(2026-09-10 수정: 파라미터 조합을
  `roundtrip=true&source=first`로 바꾸고 속도 타당성 검사를 추가했다
  — 1-B-2 참고. 아래 항목들은 그 수정이 반영된 현재 동작이다.)**
- 연결이 안 되거나(네트워크 문제 등) 응답 속도가 도보로 보기엔
  말이 안 되면(프로필 오응답 의심), 가까운 순 정렬 + 직선거리×1.3
  보정 + 시속 4.5km 추정으로 넘어가되, `routedReal` 플래그로 어느
  쪽인지 구분해 화면에 **정직하게 다르게 표시**한다("실제 도보 경로
  기준" vs "직선거리 기준으로 추정 — 실제 경로 연결 실패").
- 좌표 없는 장소는 계산에서 조용히 빼지 않고 "빠진 곳" 목록과 이유를
  결과 화면에 그대로 보여준다. 가용 시간(분)을 넘어 못 들르는 곳도
  **(2026-09-10 수정: 이제 실제로 계산에 반영됨 — 1-B-3)** 별도
  이유("가용 시간 안에 다 못 들름")로 구분해 보여준다.
- 출발 시각은 **여행지 현지 시각의 지금 시각**을 쓴다(2026-09-10
  수정 전에는 오전 9시로 고정돼 있었다 — 1-B-3).
- 출발지는 API 키가 필요 없는 두 가지만 제공: 브라우저 현재 위치(GPS)
  또는 담아 둔 곳 중 하나 선택. 가용 시간(분)은 선택 입력.
- 코스 후보는 지금 보고 있는 도시로 거른다(2026-09-10 수정 전에는
  도시를 바꿔도 이전 도시 장소가 섞여 들어갈 수 있었다 — 1-B-3).
- 대중교통·택시·자전거는 자체 계산을 만들지 않고 구글 지도 길찾기로
  바로 연결한다("연결된 범위만 제공").
- 생성한 코스는 `foodMap.course`에 도시·출발지·이동수단·계산 조건과
  함께 저장돼 **새로고침해도 유지**된다. 저장 실패 시 원상 복구.
  도시를 바꾼 뒤에는 다른 도시에서 저장한 코스를 자동으로 보여주지
  않는다(2026-09-10 수정 — 1-B-3).
- "새로 만들기"는 새 코스가 실제로 완성·저장된 뒤에만 기존 코스를
  교체한다 — 취소하거나 생성이 실패하면 이전 코스가 그대로 남는다
  (2026-09-10 수정 전에는 누르자마자 기존 코스를 먼저 지웠다 — 1-B-3).
- 사진: 실제 사진이 없으면 항상 빈 상태(카테고리 이니셜) 표시 —
  가짜 사진으로 대체 안 함. `loading="lazy"`로 화면 진입을 안 막음.

**검증(실제 Chromium)**: `page.route()`로 OSRM 응답을 실제 모양대로
흉내 내 성공/실패/비정상 속도 세 코드 경로, 좌표 없는 곳 처리, 가용
시간 초과 처리, 새로고침 후 유지, "새로 만들기" 취소 시 보존, GPS
출발지까지 21개 시나리오 확인(`scripts/test-course-generation.mjs`).
**전부 `page.route()` mock 응답 기준 검증이다 — 실제 공개 OSRM 서버
연결 자체는 아래 "확인한 한계"대로 이 환경에서 검증하지 못했다.**

**확인한 한계**: 이 샌드박스는 조직 정책으로 외부 네트워크(OSRM 서버
포함)가 막혀 있어, 실제 공개 서버 연결 자체는 여기서 확인하지 못했다.
실제 사용자 브라우저는 이 프록시를 거치지 않지만, 별도 한계로 남긴다.
또한 OSRM 공개 데모 서버는 평가·소규모 용도로 운영진이 공개한 무료
서비스라, 트래픽이 늘면 자체 라우팅 서버로 옮기는 걸 출시 전 계획에
넣어야 한다(아래 8절).
`private/personal.html`의 기존 다중 날짜 여행 계획 기능(`csGenerate`/
`plToCourse`, 구역 기반)은 이번에 손대지 않았다 — 이번 로드맵은 새
화면의 단일 코스 생성이 대상이었고, 기존 다중 날짜 플래너에 실제
라우팅을 붙이는 건 더 큰 별도 작업이라 범위 밖으로 뒀다.

## 8. 유료 출시 준비 — 계획 (아직 구현 안 함)

**이 절은 코드가 아니라 계획이다.** 이 앱은 서버가 없는 정적 HTML +
localStorage 구조다. 무료체험 1회 제한·결제 웹훅·환불 등을 실제로
안전하게 처리하려면 **서버(백엔드)가 새로 필요하다** — 클라이언트
자바스크립트만으로는 "동시 요청·재시도에서 중복 사용되지 않게" 막을
방법이 원리적으로 없다(클라이언트 값은 사용자가 항상 조작할 수 있다).
그래서 여기서는 실제로 동작하지 않는 "가짜 서버 코드"를 만들어 넣지
않았다 — 대신 필요한 것을 구체적으로 정리한다.

### 8-1. 필요한 것(설계)

- **가격**: 코드에 숫자를 박지 않고 서버(또는 최소한 서버가 서명한
  설정값)에서 읽어오게 한다. 지금은 확정하지 않는다.
- **무료체험**: "계정당 개인화 코스 생성 성공 1회". 판정은 반드시
  서버에서 한다 — 서버가 사용자 계정별로 "성공한 생성 횟수"를 저장하고,
  요청이 올 때마다 서버가 잔여 횟수를 확인한 뒤 잠그고(락) 처리하고
  풀어야 동시 요청·재시도로 두 번 차감되지 않는다. 실패(네트워크 오류,
  OSRM 실패 등)는 차감하지 않는다 — "성공"의 정의를 서버가 판단한다.
  생성 결과는 서버에 저장해 두고 계속 열람 가능해야 한다(브라우저를
  지워도 다시 볼 수 있게).
- **결제**: 결제대행사(PG)의 웹훅을 서버가 받아서 결제 성공·취소·만료를
  처리한다. 클라이언트가 "결제했다"고 스스로 신고하는 방식은 조작
  가능해서 안 된다.
- **추가 일정 생성·재계산 등 유료 범위**: 이용 기간·횟수를 서버가
  검증한다(클라이언트는 참고용 표시만).

### 8-2. 이걸 만들려면 실제로 필요한 계정·비용·설정

- **서버 호스팅**: 지금 있는 GitHub Pages는 정적 파일만 서빙한다 —
  로그인·결제·DB가 필요한 순간 별도 백엔드가 필요하다. 예:
  Cloudflare Workers/Pages Functions, Vercel, 또는 작은 VPS. 대부분
  무료 등급이 있지만 트래픽이 늘면 비용이 발생한다.
- **데이터베이스**: 사용자별 무료체험 사용 여부·결제 상태를 저장할
  곳(예: Cloudflare D1, Supabase, PlanetScale 등). 무료 등급 존재,
  규모가 커지면 유료.
- **결제대행사(PG) 계정**: 국내 카드 결제라면 토스페이먼츠·포트원
  (아임포트) 등, 해외/PayPal 결제도 고려한다면 별도 가입. **사업자
  등록** 여부에 따라 심사 조건이 달라진다(개인사업자 등록이 보통
  필요하다) — 이건 사용자(발주자)가 직접 결정·진행해야 하는 부분이다.
- **통신판매업 신고**: 한국에서 온라인으로 유료 상품을 판매하려면
  일반적으로 통신판매업 신고가 필요하다(면제 요건도 있으니 실제
  적용 여부는 확인 필요) — 이것도 법적 판단이 필요한 부분이라 별도
  확인을 권한다.
- **OSRM 라우팅 서버**: 무료 공개 데모 서버는 평가용이다. 실제 트래픽이
  생기면 자체 OSRM 서버를 띄우거나(오픈소스, 서버 비용만 발생) 유료
  라우팅 API(Google Directions 등, 사용량 기반 과금)로 옮기는 걸
  계획해야 한다.
- **개인정보처리방침·이용약관**: 계정·결제 정보를 다루기 시작하면
  법적으로 필요하다.

**이 중 실제 계정 생성·사업자 등록·서버 구축 여부는 사용자가 결정할
사안이다.** 결정되면 그에 맞춰 실제 백엔드 코드를 붙이는 걸 다음
단계로 진행할 수 있다. 이번 라운드는 핵심 기능(가져오기·분류·위치
확인·코스 생성)을 먼저 검증하는 데 집중했다.

## 11. 과거 기록(이미 커밋된 것) 개인정보 — 별도 보고 (재확인, 아직 미결정)

3차 보고에서 이미 보고했던 항목이 그대로 남아 있다:

- `docs/HANDOFF.md`, `scripts/test/t2.mjs`, `scripts/test/t48.mjs`의
  **과거 커밋(git 히스토리)**에는 이전 세션에서 실제 호텔 이름 하나와
  실제 터미널 이름 하나가 이미 들어간 채로 커밋돼 있다. 이번 라운드에서
  이 3개 파일의 **현재 버전**은 지어낸 값으로 고쳐서 커밋했다(3절) —
  하지만 과거 커밋 자체에는 여전히 남아 있다.
- 과거 기록까지 지우려면 git 히스토리 재작성(rebase/filter-branch 등)이
  필요한데, "master 병합·공개 배포·git 히스토리 재작성은 하지 마세요"
  지시에 따라 이번에도 손대지 않았다.
- **결정이 필요한 부분**: (a) 지금처럼 현재 파일만 고치고 과거 커밋은
  그대로 둘지, (b) 필요하면 별도로 히스토리 재작성을 허락하실지.
  결정해 주시면 그에 맞게 진행하겠다.
