# 디자인 통합 결과 (2026-09-09, 2차 갱신)

1차 보고(같은 날 오전) 이후 제품 방향을 확정받아 이어서 작업했다. 이 문서는
전체를 대체한다. 브랜치: `design-integration` (origin 에 푸시함, `master`는
안 건드림, 공개 배포 안 함).

## 0. 확정된 제품 방향

> 장소 보관과 여행 일정을 분리한다. 담아 둔 장소는 여러 도시를 포함해 계속
> 보관한다. 여행지를 바꿔도 지우지 않는다. 여행지 선택은 필터다.

이번 단계 범위: 여러 여행 **일정**(숙소·날짜·코스)을 동시에 편집하는 기능까지는
안 만든다. 장소 **보관함**만 여러 도시를 유지하게 바꿨다.

## 1. 요청하신 네 가지 확인

### ① 161+3+15=179인데 왜 최종 178(→ 지금은 170)인가

**1차 보고 때는 178이라고 했는데, 다시 정확히 재보니 진짜 정답은 170이었다.**
1차 보고 시점엔 못 잡은 문제가 있었다 — 아래에 그대로 적는다.

- 179건 중 **정확히 1건**은 두 CSV 목록에 글자 그대로 같은 이름(가게 하나가
  기본 목록과 커스텀 목록 둘 다에 저장돼 있었다)이 있었다. 이건 처음부터
  정상적으로 병합됐다. → 179 − 1 = 178.
- 그런데 **`저장한 장소.json`(GeoJSON, 좌표 있음)의 15곳 중 8곳이 이미
  CSV 두 목록에 똑같은 이름으로 들어 있었다**(호텔 몇 곳과 식당 몇 곳).
  CSV 쪽은 좌표가 없고 URL 형식도 GeoJSON 쪽과
  전혀 달라서(`!1s0x...` vs `?cid=...`), **예전 중복 판정 키(URL 또는
  이름+좌표)로는 이 여덟 곳을 "새 장소"로 잘못 셌다.** 1차 보고의 178은
  이 오류가 반영된 숫자였다.
- **고친 것**: 병합 규칙에 "URL·좌표가 달라도 이름이 같으면 겹친 것으로
  본다"는 규칙을 추가했다(`fmMerge`, `private/personal.html`). 대신
  정보를 잃지 않게 **어느 목록들에 있었는지(`sourceLists`) 다 남긴다** —
  화면 상세에도 "여러 목록(기본 목록 · 가고 싶은 장소)에 저장돼 있어
  하나로 합쳤습니다"로 보여준다.
- **정정된 진짜 숫자**: 179건 → 1건(이름 완전 일치) + 8건(이름은 같은데
  형식이 달라 놓치던 것) = 9건 중복 → **170곳**이 진짜 서로 다른 장소.

회귀 테스트 `t49`에 이 정확한 시나리오(CSV 두 곳 이름 겹침 + CSV/GeoJSON
간 이름만 같은 겹침)를 실제 데이터 모양 그대로 넣어서 고정해 뒀다.

### ② 좌표 없다고 숨기지 않되, 좌표 없다고 후쿠오카로 확정하지도 않기

`fmCityGuess()`를 새로 만들었다(`private/personal.html`, `src/design/import-adapter.js`
양쪽에 동일 로직). 규칙:

1. **주소**에 아는 도시 이름이 정확히 하나만 걸리면 그 도시로 확정.
2. 두 도시 이름이 동시에 걸리면(주소가 애매하거나 여러 지명이 섞여 있으면)
   확정하지 않음(`null`).
3. 주소로 못 찾았는데 좌표가 있으면, **지금 정확한 범위를 아는 후쿠오카에
   한해서만** 좌표로 교차검증(그 외 29개 도시는 아직 좌표 범위 데이터가
   없어서 좌표만으로는 못 정한다 — 정직하게 다음 단계로 남겨 둠).
4. 그래도 없으면 `null` → 화면에 **"지역 확인 필요"**로 별도 묶음 표시.
   장소 자체는 절대 안 숨긴다.

**메모(note)는 도시 추측에 안 쓴다.** 실제로 이 규칙 없이 짰다가 진짜
버그를 하나 만들었다 — 후쿠오카의 한 가게 메모가 다른 도시와 비교하는
개인 코멘트(예: "예전에 가 본 ○○ 가게가 더 좋았다")였는데, 메모까지
보게 했더니 이 가게를 그 도시로 잘못 확정했다. 실제 데이터로 검증하다가
발견해서 바로 주소만 쓰도록 고쳤다. 이 케이스도 `t49`에 회귀 테스트로
남겨 뒀다(실제 가게 이름·메모 문구는 개인정보라 테스트에는 지어낸 값을 씀).

**실제 결과(사용자 파일 170곳)**: 후쿠오카 13곳(주소로 확인), 다른 나라
1곳(주소로 확인), **지역 확인 필요 156곳**. 156곳이 많아 보이지만
이건 정직한 숫자다 — 구글 Takeout 기본 CSV 내보내기 자체가 주소를 안 주기
때문이고, 거짓으로 후쿠오카라고 우기지 않은 결과다.

### ③ `private/personal.html` 수정과 `src/index.html`의 관계 · 빌드 반영 확인

**관계**: `private/personal.html`이 유일한 원본이다. `npm run build`
(`scripts/build-sales.mjs`)가 이 파일을 읽어 6곳을 문자열 치환(판매자 개인
신상 제거)해서 `src/index.html`을 **통째로 다시 생성**한다. 부분 패치가
아니라 전체를 다시 쓰는 방식이라, 원본을 고치고 빌드를 돌리면 **원리적으로
빠짐없이 반영된다** — 손으로 옮겨 적는 단계가 없다.

**이번에 확인한 방법**: 오늘 `fmCityGuess`, `fmMerge`, `tripReset`,
`fmSetCountry`를 personal.html에서 고친 뒤 `npm run build`를 돌리고,
이 네 가지를 검증하는 새·수정 테스트(`t46`, `t48`, `t49`)를
**`private/personal.html`과 생성된 `src/index.html` 양쪽에 각각** 실제로
실행해서 **둘 다 통과함을 직접 확인했다.** 코드가 있는지 grep으로 확인한
게 아니라, 그 코드가 실제로 그 파일에서 동작하는지를 실행해서 봤다.

```
node scripts/test/t46.mjs private/personal.html  → 전체 통과
node scripts/test/t46.mjs src/index.html         → 전체 통과
node scripts/test/t48.mjs private/personal.html  → 전체 통과
node scripts/test/t48.mjs src/index.html         → 전체 통과
node scripts/test/t49.mjs private/personal.html  → 전체 통과
node scripts/test/t49.mjs src/index.html         → 전체 통과
```

**현재 변경 목록과 보고 일치 확인**: 아래 4절 "변경 파일"이 `git status`
결과와 완전히 일치한다(직접 대조함). `src/design/`은 personal.html과 별개
파일이라 빌드 대상이 아니다 — 여기 수정은 위 빌드 확인과 무관하게 파일
자체를 커밋해서 검증한다(design-integration-check.mjs로 별도 확인, 아래 5절).

### ④ 로케일 문제 — 확인한 범위만

이 검증 샌드박스(컨테이너)는 기본 로케일이 `POSIX`(비UTF-8)였다. 이 상태에서
Playwright로 **한글 파일명**(예: "기본 목록.csv")을 자동으로 골라 넣으면
`change` 이벤트가 아예 안 왔다 — 파일 내용이 아니라 **파일명**이 문제였다
(ASCII 파일명은 같은 조건에서 정상 동작했다). `LC_ALL=C.utf8 LANG=C.utf8`로
로케일을 맞추자 한글 파일명도 정상 동작했다. 즉 **이 문제는 "이 테스트
샌드박스에 UTF-8 로케일이 기본으로 없었다"는 환경 설정 문제였고, 앱 코드나
브라우저 자체의 결함은 아니었다** — 로케일만 맞추면 재현되지 않았다.

**여기서 확정할 수 있는 것은 이만큼이다.** 이게 실제 아이폰 Safari에서도
항상 괜찮다는 보장은 아니다 — **실제 기기(아이폰 Safari 등)에서 한글
파일명으로 된 실제 다운로드 파일을 고르는 것은 아직 검증하지 않았다.**
이 항목은 계속 "실기기 미검증"으로 남겨 둔다(3절 원래 보고에도 이미
그렇게 적어 뒀던 항목이다).

## 2. 데이터 구조 변경 — ① 여러 도시 보존 (요청하신 다음 구현 순서 ①)

`private/personal.html`:

- **`tripReset()`/`fmSetCountry()` 재작성** — 나라(목적지)를 바꿔도
  `foodMap.places`를 절대 지우지 않는다. 지우는 건 "지금 편집 중인 일정"
  (숙소·날짜·코스·예산)뿐이고, 그마저도 확인창을 띄우고 백업 파일을 먼저
  내려받는다. 확인창 문구도 "N곳을 비웁니다" → "숙소·날짜·코스·예산을
  비웁니다. 담아 둔 장소(N곳)는 지워지지 않고 그대로 보관됩니다"로 바꿨다.
- **`fmCityGuess(p)` 신설** — 위 1절 ②.
- **`fmMerge()` 재작성** — 이름 기반 교차 병합 + `sourceLists`(목록 소속)
  보존 + 새·갱신 장소에 `city` 자동 채움.
- **마이그레이션 `fmMigrateCityTags()`** — 기존 사용자의 옛 장소(도시 태그가
  없는)에 한 번만 도시를 채워 넣는다. 실행 전 백업 파일을 자동으로
  내려받고, 실패하면 `schemaV`를 안 올려서 **다음 실행 때 자동 재시도**한다
  (요청하신 "백업·실패 복구 가능" 그대로 구현).

`src/design/` (승인 디자인 화면):

- **여러 도시 필터가 실제로 동작** — `cities[]`가 이제 실제 저장된
  장소들의 `city` 값 분포에서 만들어진다(고정된 1개짜리 배열이 아니다).
  "지역 확인 필요"는 별도 묶음으로 항상 마지막에 보여준다.
- 새로 아는 도시가 확인되면 자동으로 그 도시를 먼저 보여주되(더 쓸모
  있는 기본 화면), 사용자가 다른 도시를 보고 있었으면 그건 유지한다.
- 상세 시트에 도시 미확인 안내 + 여러 목록 소속 안내를 추가했다(1절 참고).
- 가져오기 병합 로직 자체를 `import-adapter.js`의 `A.merge()`로
  일원화했다(이전엔 spots.js 안에 따로 임시 병합 로직이 있었다 — 지웠다.
  판정 기준이 두 곳에서 갈리는 사고를 막는다).

## 3. 아직 안 한 것 (요청하신 다음 구현 순서 ②③④)

이번 턴은 ①(데이터 구조 + 도시 필터)에 집중했다. 나머지는 각각 크기가
있어서 순서대로 따로 진행하는 게 안전하다고 판단했다 — 특히 ZIP은 실패
시나리오가 많아 서두르면 "일부 실패해도 성공한 건 먼저 쓸 수 있어야
한다"는 요구를 제대로 못 지킬 위험이 있다.

- **② Takeout ZIP 직접 가져오기** — 아직. 지금은 사람이 zip을 먼저 풀어서
  csv/json을 골라야 한다(화면 문구에도 정직하게 그렇게 적혀 있다). 브라우저
  안에서 zip을 푸는 방법 검토 필요(외부 라이브러리 도입 여부 — 02_DESIGN_CONTRACT
  "외부 CSS @import를 재도입하지 않기"에 준해 신중히 접근).
- **③ 검증된 정보 기반 유형 분류 + 사용자 수정** — 아직. 지금은 원본 CSV에
  분류 정보가 없으면 전부 "기타"로만 뜬다. `personal.html`에 이미 있는
  `fmInfer()`(51개 실제 상호명으로 검증된 순서 규칙)를 연결하고, 사용자가
  카드에서 직접 분류를 고칠 수 있는 UI를 붙여야 한다.
- **④ 실제 장소 선택 → 코스 생성·저장** — 아직. "오늘 동선"은 목록 담기까지만
  되고, 최단 동선·이동수단 계산은 승인 디자인 원래 문구 그대로 "아직 연결
  안 됨"으로 뒀다.
