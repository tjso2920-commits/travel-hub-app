순서대로 정리한다. 개발 담당(이 세션)은 outbound 네트워크가 막혀 있어
(`docs/RELEASE_STATUS.md` 2절) 아래 순서를 실제로 밟아본 적이
없다 — 이 문서는 "코드가 무엇을 기대하는지"를 정확히 옮긴 것이지,
실제로 이 순서대로 켰을 때 문제가 없다고 보장하는 게 아니다.

**핵심 원칙 하나**: `/api/health`가 "키가 설정돼 있다"고 보여주는 것과
"그 키로 실제 연결에 성공했다"는 것은 다른 이야기다. 이 문서의 순서를
전부 따라도, **각 서비스로 실제 요청을 한 번 이상 보내서 성공 응답을
받아보기 전까지는 "연결됐다"고 말할 수 없다.** 아래 3단계에 그
확인 방법을 서비스별로 따로 적어 뒀다.

## 0-0. 지금 실제로 쓸 수 있는 서버·호스팅이 있는가 — 없다(15차 신규)

**결론부터: 이 저장소 어디에도 실제 호스팅·배포 설정이 없다.** 이번에
저장소 전체를 다시 훑어 Dockerfile, docker-compose, Procfile, systemd
서비스 파일, render.yaml, fly.toml, vercel.json, netlify.toml,
Caddyfile, nginx 설정 등을 찾아봤지만 전부 없었다 — 15차에 걸친 모든
작업이 지금까지 `node server/index.mjs`를 사람이 로컬에서 직접 실행해
온 것 하나뿐이었다는 뜻이다.

**따라서 "이미 확보된 호스팅 계정이나 계약이 있다"고 가정하지 않는다.**
아래는 어떤 특정 호스팅 서비스도 지정하지 않은, 사용자가 이미 갖고
있을 법한 환경(예: 회사 사무실 PC, 집 서버, 이미 쓰는 VPS 등) 위에서
그대로 따라 할 수 있는 절차다 — 새 유료 계약이나 공개 배포를 요구하지
않는다.

정적 페이지 하나만 인터넷에 떠 있는 상태를 "로그인·결제·동기화까지
되는 테스트 주소"라고 부르지 않는다 — 아래 0-3절의 구성(프런트+API
중계)을 실제로 띄우고, 3절의 화면 조작 확인을 실제로 통과해야만
"테스트 주소가 준비됐다"고 말할 수 있다.

아래 네 공급자의 계정을 먼저 만들어 둔다(계정 생성 자체는 무료):

있다 — 서비스별로 독립적으로 켜지는 구조다(`server/config.mjs`).

## 0-1. 서버 런타임 / 영속 저장소 / 백업·복원(14차 신규)

이 앱의 서버는 `node server/index.mjs` 하나만 실행하면 되는 단일
프로세스다(별도 워커·큐 없음). 데이터는 전부 `DB_PATH`가 가리키는
SQLite 파일 하나(`node:sqlite`)에 들어간다 — 이 파일이 곧 계정·
장소·코스·결제기록·비용원장 전체다. **이 파일을 잃으면 전체 서비스
데이터를 잃는다**는 뜻이므로, 실제 손님을 받기 전에 아래를 반드시
확인한다:

1. **지속 저장소**: `DB_PATH` 경로가 컨테이너/서버 재시작·재배포에도
   내용이 남는 볼륨(디스크)을 가리켜야 한다. 컨테이너 이미지 안
   임시 레이어에 두면 재배포마다 데이터가 사라진다.
2. **정기 백업**: SQLite는 파일 하나이므로 백업은 그 파일을 복사하는
   것만으로 충분하다 — 단, 서버가 쓰기 중일 때 그냥 `cp`로 복사하면
   일관성이 깨질 수 있으니 `sqlite3 $DB_PATH ".backup /백업경로/파일명"`
   (SQLite 자체 온라인 백업 명령, 쓰는 중에도 안전)을 쓰거나, 짧은
   점검 시간에 서버를 잠깐 멈추고 복사한다. 최소 하루 1회, 결제
   연결 이후에는 더 자주(예: 몇 시간 단위) 권장한다.
3. **복원 절차**: 문제가 생기면 서버 프로세스를 멈추고, 백업 파일을
   `DB_PATH` 경로에 덮어쓴 뒤 서버를 다시 시작한다. 서버가 다시
   뜨면 `migrate()`(`server/db.mjs`)가 스키마 마이그레이션을
   자동으로 다시 확인한다(이미 적용된 마이그레이션은
   `schema_migrations` 테이블 덕분에 중복 실행되지 않는다).
4. **이 세션이 실제로 해본 것과 안 해본 것**: 위 절차는 SQLite의
   표준 동작 방식을 그대로 옮긴 것이지, 이 세션이 실제 운영 서버에서
   백업→장애→복원을 실제로 실행해 검증한 적은 없다(네트워크·실
   서버 환경이 없어서다) — 실제로 한 번은 백업 파일로 복원이 되는지
   운영 환경에서 미리 리허설해 볼 것을 권장한다.

## 0-2. 코드 준비 완료 vs 사용자 설정 필요 — 한눈에 보기(14차 신규)

아래 구분은 "코드가 이미 그 공급자를 실제로 부를 수 있게 짜여 있는가"
와 "그걸 실제로 켜려면 사람이 계정을 만들고 키를 넣어야 하는가"를
분리한 것이다. **코드 준비 완료라고 해서 지금 당장 실제로 연결돼
있다는 뜻은 아니다** — 아래 오른쪽 칸의 설정을 마쳐야 실제로 켜진다.

| 공급자/기능 | 코드 상태 | 사용자가 할 일 |
|---|---|---|
| 이메일 로그인(Resend) | 준비 완료(실제 어댑터 구현·테스트됨) | 1-2절의 3개 환경변수 입력 |
| 결제(토스페이먼츠) | 준비 완료(실제 어댑터 구현·테스트됨) | 1-3절의 4개 환경변수 입력 + 소액 실결제 1건으로 확인(3절 4번) |
| 장소 조회(Google Places) | 준비 완료 | 1-4절 키 입력 + 결제 수단 등록(0절) |
| 경로 계산(Google Routes) | 준비 완료 | 1-5절 키 입력 |
| 날씨(WeatherAPI) | 준비 완료 | 1-5b절 키 입력(부가 기능 — 없어도 서비스는 동작) |
| Google 로그인 | 준비 완료(14차 — 계정 탈취 취약점 수정 반영, sub 기준 연결 재설계) | 1-5c절 OAuth 클라이언트 ID 발급(선택 — 없어도 이메일 코드 로그인으로 서비스 전체가 동작함) |
| 지도 링크로 장소 추가 | 준비 완료 | 없음(Places API를 안 부르므로 별도 키 불필요) |
| 일본어 실전 회화 | 준비 완료(문장 자체는 원어민 감수 전) | 없음(기기 TTS만 사용) |
| AI 보조 자동분류(Anthropic) | 준비 완료(14차 — usage 기반 실비용 정산까지 구현), **기본은 계속 비활성** | 1-6c절 이중 게이트 설정(선택 — 안 켜도 규칙 기반 분류로 서비스 전체가 동작함) |

**`GET /api/health`가 위 항목을 전부 "configured"로 보여줘도, 그
자체는 "코드가 그 공급자를 부를 준비가 됐다"는 뜻일 뿐 "실제로 그
공급자에 연결해 성공 응답을 받았다"는 뜻이 아니다** — 3절의 실제
화면 조작 확인을 반드시 거쳐야 한다(3-2절 참고).

## 0-3. 프런트엔드와 API를 폰에서 한 주소로 함께 쓰는 구성(15차 신규)

**이번에 확인된 실제 문제**: `server/index.mjs`는 API 전용이다 — 어떤
경로로 요청을 보내도 `/api/...`가 아니면 그냥 404를 준다(정적 파일을
서빙하는 코드가 원래 없었다). 그리고 `npm run preview`가 실행하는
`scripts/serve.mjs`는 이 프로젝트가 다른 개인 프로젝트였던 시절
파일(`01_SOURCE/커팅트래커_개인용.html` 등, 지금은 존재하지 않음)을
가리키고 있어서 **실행해도 항상 404만 나는 죽은 명령이었다** — 즉
지금까지 이 저장소에는 실제 프런트엔드(`src/design/index.html`)를
폰에서 열어볼 방법 자체가 준비돼 있지 않았다(지금까지의 모든 브라우저
테스트는 Playwright가 `file://` 경로로 직접 여는 방식이었는데, 이건
폰에서는 쓸 수 없다).

**이번에 고친 것**: `scripts/serve.mjs`를 실제 프런트엔드
(`src/design/`, `src/`)를 서빙하도록 고치고, `/api/`로 시작하는
요청은 그대로 API 서버로 중계(proxy)하도록 만들었다 — 폰이 주소
하나만 열면 프런트와 API가 같은 origin으로 보인다(프런트 JS들은
`window.API_BASE`가 안 정해져 있으면 상대 경로 `/api/...`로 요청을
보내므로, 이 구성에서는 프런트 코드를 하나도 안 건드려도 그대로
맞아떨어진다).

**로컬(또는 이미 갖고 있는 서버)에서 띄우는 순서**:

```bash
# 터미널 1 — API 서버 (기본 포트 8787)
DB_PATH=/data/travelhub.db APP_ENV=development node server/index.mjs

# 터미널 2 — 프런트+API 중계 서버 (기본 포트 4173)
node scripts/serve.mjs
```

이제 같은 기기의 브라우저에서 `http://localhost:4173/`을 열면
실제 프런트엔드가 뜨고, 그 화면이 부르는 `/api/...` 요청은 전부
8787번 API 서버로 중계된다(`GET /api/health`를
`http://localhost:4173/api/health`로 열어서 확인할 수 있다).

**폰에서 열려면** — 아래 중 하나가 필요하다(어느 쪽도 이 세션이 대신
설정해 줄 수 없다 — 실제 네트워크·계정이 있어야 하는 단계다):

1. **같은 와이파이 안에서 사설 IP로 열기(가장 간단, 임시 확인용)**:
   `HOST=0.0.0.0 node scripts/serve.mjs`로 띄운 뒤, PC의 사설 IP
   주소(예: `192.168.0.5`)로 폰 브라우저에서
   `http://192.168.0.5:4173/`을 연다. **HTTPS가 아니므로** Google
   로그인 버튼이 origin 오류로 안 뜰 수 있고, 카메라·정밀위치 같은
   일부 브라우저 기능이 제한될 수 있다 — 어디까지나 "화면이 뜨는지,
   기본 흐름이 도는지"를 빠르게 볼 때만 쓴다.
2. **HTTPS 테스트 주소가 필요한 단계(Google 로그인, 결제 등)** —
   이미 갖고 있는 도메인·서버가 있다면 그 서버에서
   `node server/index.mjs`와 `node scripts/serve.mjs`를 계속 떠 있는
   프로세스로 실행하고(예: `pm2`, `systemd`, 또는 그냥 `nohup` — 이
   저장소에는 이런 프로세스 관리 설정이 없으므로 사용자가 이미 쓰는
   방식을 그대로 쓴다), 그 앞에 HTTPS를 종단하는 리버스 프록시(예:
   기존에 쓰던 nginx·Caddy, 또는 클라우드 제공업체의 로드밸런서)를
   하나 두어 `443`(HTTPS) → `4173`(이 서버)으로 넘겨준다. **이
   세션은 특정 호스팅 업체나 도메인을 새로 계약하라고 지시하지
   않는다** — 이미 있는 서버·도메인이 있다면 그 위에 위 두 프로세스만
   추가로 띄우면 된다는 뜻이다. 아무 서버도 없다면, 그 자체가 "지금
   당장 해야 할 일"의 첫 항목이다(맨 아래 6절 우선순위 참고).

**하지 말아야 할 것**: 정적 파일 호스팅(예: 그냥 HTML 파일 하나만
올리는 서비스)에만 `src/design/`을 올려두고 "테스트 주소가 준비됐다"고
부르지 않는다 — API 서버가 없으면 로그인도 코스 생성도 결제도 전혀
동작하지 않는 빈 화면일 뿐이다. 위 구성대로 **API 서버와 중계 서버
둘 다** 떠 있어야 한다.

---

## 1. 환경변수 입력 순서

**서버(`node server/index.mjs`)는 시작될 때 한 번만 환경변수를 읽는다
— 값을 바꾸면 서버를 재시작해야 반영된다.** 아래 순서로 하나씩
채운다(위에서부터 순서대로 해도 되고, 이미 갖고 있는 키부터 먼저
넣어도 된다 — 순서 자체가 서로를 막지는 않는다. 단, **6번(운영
모드 전환)은 항상 맨 마지막에 한다** — 그 전까지는 테스트 기능이
실수로 운영에 노출되는 걸 막아 주는 안전판 역할을 한다).

### 1-1. 필수 — 서버가 아예 못 뜨는 값

| 환경변수 | 값 | 확인 방법 |
|---|---|---|
| `DB_PATH` | 실제 서버가 쓸 SQLite 파일 경로(예: `/data/travelhub.db`) | 이 경로가 있는 디스크에 **지속 저장소**가 붙어 있어야 한다(컨테이너 재시작 시 파일이 사라지면 전체 계정 데이터가 날아간다) |
| `PORT` | 서버가 들을 포트(예: `3000`) | 리버스 프록시(nginx 등)가 이 포트로 연결하는지 확인 |

### 1-2. 이메일 로그인(Resend)

| 환경변수 | 값 |
|---|---|
| `EMAIL_ADAPTER` | `resend` |
| `EMAIL_API_KEY` | Resend 대시보드 → API Keys에서 발급한 키(`re_`로 시작) |
| `EMAIL_FROM` | 실제 보낼 발신 주소(Resend에 도메인 인증을 마친 주소여야 함 — 인증 안 된 도메인은 발송 자체가 거부될 수 있다) |

### 1-3. 결제(토스페이먼츠)

| 환경변수 | 값 |
|---|---|
| `PAYMENT_ADAPTER` | `toss` |
| `TOSS_CLIENT_KEY` | 토스페이먼츠 개발자센터의 **클라이언트 키**(결제창에 쓰임, `live_ck_`로 시작) |
| `PAYMENT_PG_SECRET` | 토스페이먼츠의 **시크릿 키**(서버 승인 API 호출용, `live_sk_`로 시작 — **절대 클라이언트에 노출되면 안 됨**, 이 값은 서버 프로세스 환경에만 넣는다) |
| `PAYMENT_WEBHOOK_SECRET` | 토스페이먼츠 웹훅 설정 화면에서 발급한 서명 검증용 시크릿 |
| `PAYMENT_EXPECTED_CURRENCY` | `KRW`(기본값, 보통 안 바꿔도 됨) |

### 1-4. 장소 조회(Google Places API New)

| 환경변수 | 값 |
|---|---|
| `PLACE_LOOKUP_ADAPTER` | `google` |
| `GOOGLE_PLACES_API_KEY` | Google Cloud Console에서 발급한 키 — **반드시 Places API(New)가 활성화된 프로젝트의 키**(Legacy Places API 전용 키는 이 코드가 요구하는 필드마스크를 못 준다) |

### 1-5. 경로 계산(Google Routes)

| 환경변수 | 값 |
|---|---|
| `ROUTING_ADAPTER` | `google` |
| `GOOGLE_ROUTES_API_KEY` | Google Cloud Console에서 발급한 키(Places 키와 같은 프로젝트여도 되고 달라도 됨 — Routes API가 활성화돼 있어야 함) |

### 1-5b. 착장 판단용 날씨(WeatherAPI.com) — 7차 신규

| 환경변수 | 값 |
|---|---|
| `WEATHER_API_KEY` | WeatherAPI.com에서 발급한 키(무료 등급으로 충분 — 공식 가격표
  https://www.weatherapi.com/pricing.aspx 확인: 상업적 사용 허용, 월
  100,000회, 현재 날씨+3일 예보 포함, https://www.weatherapi.com/docs/) |

이 키가 없어도 서버는 정상 시작된다(결제·이메일과 달리 **부팅을 막는
필수값이 아니다** — 날씨는 코스·동선 기능에 얹는 부가 기능이라, 키가
없으면 그냥 날씨 카드만 "일시적으로 이용할 수 없어요"로 뜬다). 다만
소비자에게 날씨 카드를 실제로 보여주려면 이 키를 넣어야 한다.

**소비자에게 절대 이 키를 입력하라고 요구하지 않는다** — 서버가 키를
들고 있고, 클라이언트(`src/design/weather-card.js`)는 좌표만 서버에
보낸다(Google Places/Routes 키와 같은 원칙). 이 공급자와 유료 계약을
새로 맺지 않는다 — 무료 등급 그대로 쓴다.

### 1-5c. Google 로그인(Google Identity Services) — 13차 신규, 선택이지만 권장

**이 값이 없어도 서버는 정상 시작되고 이메일 코드 로그인만으로도
서비스는 완전히 동작한다** — Google 로그인은 "기본으로 보여줄
편의 진입점"이지 필수 크리덴셜이 아니다(결제·이메일과 다름).

**14차 갱신 — 계정 탈취 취약점 수정**: 13차 코드는 같은 이메일이면
로그인 방식과 무관하게 같은 계정으로 이어지도록 이메일 하나만 보고
계정을 연결했는데, ChatGPT가 "이메일 검증만으로는 그 계정에 이미
가입한 사람과 방금 그 이메일로 Google 로그인한 사람이 같은 사람이란
보장이 없다"는 계정 탈취 경로를 재현했다. 이제는 Google의 안정
식별자(`sub`)를 기준으로 연결하고, 이미 다른 방식으로 가입된 계정에
새로 연결하려면 그 계정의 로그인 세션이나 이메일 인증 코드로 소유
확인을 거치게 바뀌었다(코드는 이미 반영·테스트됨) — **그래도
`GOOGLE_CLIENT_ID`를 아직 안 넣었다면 이 기능 자체가 꺼져 있으므로
당장 체감되는 변화는 없다.**

| 환경변수 | 값 | 확인 방법 |
|---|---|---|
| `GOOGLE_CLIENT_ID` | Google Cloud Console → API 및 서비스 → 사용자 인증 정보에서 만드는 **OAuth 2.0 클라이언트 ID**(유형: 웹 애플리케이션) | 이 값은 공개 식별자다(비밀 아님) — 화면에 그대로 내려줘도 안전하다. **클라이언트 시크릿은 이 서버 구조에서 아예 쓰지 않는다**(발급하더라도 서버에 넣지 않는다 — ID 토큰을 서버가 Google 공개키로 직접 서명 검증하는 방식만 씀) |

설정 순서:
1. https://console.cloud.google.com 에서 프로젝트 선택(Places/Routes와
   같은 프로젝트를 써도 되고 달라도 된다).
2. "API 및 서비스 → OAuth 동의 화면"에서 앱 이름·지원 이메일 등 기본
   정보를 채운다(외부 사용자 대상이면 "외부"로 설정).
3. "사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID"
   → 애플리케이션 유형 **웹 애플리케이션**을 고른다.
4. **승인된 자바스크립트 원본**에 실제 서비스 도메인(예:
   `https://travelhub.example.com`)을 추가한다 — 이 값이 정확히
   안 맞으면 버튼을 눌러도 브라우저 콘솔에 origin 오류가 뜬다(이
   세션은 실제 도메인이 없어 이 단계를 실제로 밟아보지 못했다).
5. 발급된 클라이언트 ID를 `GOOGLE_CLIENT_ID`에 넣고 서버를 재시작한다.
6. 화면에서 로그인 시트를 열어 "Google로 계속하기" 버튼이 실제로
   그려지는지, 눌렀을 때 실제 Google 계정 선택 화면이 뜨는지 확인한다
   (버튼 자체가 안 뜨면 `GET /api/auth/google/config` 응답을 직접
   열어 `ok:true`인지 먼저 확인 — `clientId`가 비어 있으면 환경변수가
   서버에 실제로 전달 안 된 것이다).

### 1-6. 운영 모드 전환(항상 맨 마지막)

| 환경변수 | 값 | 주의 |
|---|---|---|
| `APP_ENV` | `production` | **이 값을 넣기 전까지는 개발용 결제 시뮬레이션(`/api/dev/simulate-payment`) 같은 테스트 전용 경로가 그대로 열려 있다.** `production`으로 두면 그 경로들이 서버 자체에 아예 등록되지 않는다(`server/test/production-boot.test.mjs`로 확인된 동작) — 실제 손님을 받기 전 반드시 이 값을 넣는다 |
| `FORCE_TEST_MODE` | (설정 안 함 — 비워 둠) | 이 값이 `true`이면 장소 조회·경로 계산이 전부 가짜 테스트 어댑터로 동작한다. **운영 서버에는 이 변수 자체를 아예 넣지 않는다** |

### 1-6b. 특정 계정에 테스트 위치 허용(10차 변경 — 반드시 새로 읽을 것)

**9차까지는 브라우저 주소창에 `?testmode=1`만 붙이면 아무나 영구적으로
테스트 위치 기능을 켤 수 있었다 — 이건 보안 결함이었고 10차에서
막았다.** 이제는 서버 DB의 `accounts.test_access` 값이 `1`인 계정만
로그인마다 서버 재확인을 거쳐 테스트 위치 기능을 쓸 수 있다. 이 값은
운영자가 아래처럼 관리자 전용 API로만 켜고 끌 수 있다(환경변수 아님,
DB 값):

```bash
curl -X POST https://your-domain/api/admin/test-access \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"email":"tester@example.com","enabled":true}'
```

`ADMIN_TOKEN`은 기존 관리자 인증 방식을 그대로 쓴다(별도 신규 환경변수
없음). QA·데모용 계정에만 켜 두고, 실제 손님 계정에는 절대 켜지
않는다. 끌 때는 `"enabled":false`로 같은 요청을 다시 보낸다 —
로그아웃·재로그인 없이도 다음 화면 전환부터 바로 반영된다(클라이언트가
매 로그인/화면마다 서버에 재확인하기 때문).

### 1-6c. AI 보조 자동분류 — 13차: 실제 공급자 연결 코드는 생겼지만 기본은 여전히 비활성

**13차 갱신**: `server/adapters/ai-classify.mjs`에 실제 공급자(Anthropic
Claude Haiku 4.5) 연결 코드가 추가됐다 — 선정 근거는 그 파일 상단
주석과 `docs/BUSINESS_DECISIONS.md` 3-3-9절 참고. **14차 갱신**:
그때까지는 실제 청구서와 무관한 자리표시자 단가(3원/건)로 예산만
확인·기록했는데, 이제는 호출 전 보수적 견적으로 예산을 확인하고
응답이 돌아오면 Anthropic이 실제로 알려준 토큰 사용량(usage)으로
정확한 비용을 계산해 기록한다 — 아래 확인 절차의 "1번, 소량 켜서
실제 청구를 지켜본다"가 이제 원장(cost_ledger)의 숫자와 더 가깝게
맞아떨어질 것으로 기대되지만, **실제 청구서와 대조 검증까지 마친
건 아니다**(실제 API 키로 호출해 본 적 자체가 없어서다). 여전히
**운영 기본값은 비활성**이고, 아래 두 값을 **둘 다** 명시적으로
넣어야만 실제로 켜진다(이중 게이트 — 키가 있다는 사실만으로는
절대 안 켜짐):

| 환경변수 | 값 | 주의 |
|---|---|---|
| `ANTHROPIC_API_KEY` | Anthropic 콘솔(https://console.anthropic.com)에서 발급한 API 키 | **절대 클라이언트 코드·저장소·로그에 남기지 않는다** — `PAYMENT_PG_SECRET`과 같은 등급의 비밀값이다 |
| `AI_CLASSIFY_ENABLE_REAL` | `true` | 이 값을 안 넣으면(기본) 위 키가 있어도 계속 `disabled`(운영) 또는 `mock`(개발, `AI_CLASSIFY_ADAPTER=mock`일 때만)으로 동작한다 |

**이 세션은 이 두 값을 실제로 설정해 본 적이 없다** — 즉 실제 API
키로 검증된 게 아니라 가짜 응답을 주입한 모의 검증까지만 끝난
상태다(`server/test/ai-classify-real-adapter.test.mjs`). 실제로 켜기
전에 확인할 것:
1. 소량(예: 장소 2~3곳)으로 먼저 켜서 실제 분류 결과가 그럴듯한지
   직접 눈으로 확인한다.
2. Anthropic 콘솔의 사용량·청구 화면에서 실제로 청구가 얼마나
   나오는지 하루 이틀 지켜본 뒤에 전체 사용자에게 켤지 결정한다
   (BUSINESS_DECISIONS.md 3-3-9절의 원가 추정은 검증된 청구서가
   아니라 계산 근거일 뿐이다).
3. 언제든 `AI_CLASSIFY_ENABLE_REAL`을 빼거나 `false`로 두면(값 자체를
   지우는 게 더 확실) 즉시 다시 비활성으로 돌아간다 — 별도 배포 없이
   환경변수만 바꾸고 재시작하면 된다.

개발 환경에서는 여전히 `AI_CLASSIFY_ADAPTER=mock`으로 결정론적 가짜
어댑터만 켤 수 있다(비용 없음, 계약 테스트 전용 — 운영에는 영향 없음).

**11차 신규(마찬가지로 운영자가 지금 손댈 값 아님, 참고용)**:
`AI_CLASSIFY_GLOBAL_DAILY_BATCH_LIMIT`(기본 2,000)이 새로 추가됐다 —
실제 AI 공급자가 없는 지금은 아무 효과가 없는 한도 계산용 값이다.
공급자를 선정한 뒤 실제 사용량을 보고서야 조정할 값이므로 지금
바꾸지 않는다.

**12차 변경**: 11차에 있던 `AI_CLASSIFY_RESERVED_ROUTE_SEGMENTS_PER_COURSE`
값은 제거됐다 — "남은 코스 횟수마다 몇 세그먼트를 예약할지"를 조정용
상수로 두는 대신, 이제 `MAX_PLACES_PER_GENERATION`(코스 하나에 담을
수 있는 최대 장소 수, 기본 60)에서 실제 세그먼트·SKU 수를 그대로
계산해 자동으로 예약한다(`server/route-segments.mjs`). 즉
`MAX_PLACES_PER_GENERATION`을 바꾸면 AI 분류 예산 예약도 자동으로
그에 맞게 다시 계산된다 — 별도로 손댈 AI 전용 값이 하나 줄었다.

### 1-7. 선택 — 값 조정용(기본값 그대로 써도 된다)

가격·이용권 한도·비용 한도는 전부 기본값이 코드에 들어 있고, 아래
변수로만 바꿀 수 있다(코드 수정 불필요):

- `PRICE_AMOUNT_KRW`(기본 9900), `PRICE_PERIOD_DAYS`(기본 30),
  `PRICE_AUTO_RENEW`(기본 false)
- `ENTITLEMENT_FREE_PLACE_LOOKUP_LIMIT`(기본 10),
  `ENTITLEMENT_FREE_COURSE_LIMIT`(기본 1),
  `ENTITLEMENT_PAID_PLACE_LOOKUP_LIMIT`(기본 50),
  `ENTITLEMENT_PAID_COURSE_LIMIT`(기본 30) — **6차 신규, 이 문서
  작성 시점 기준 "초기 테스트 상품" 스펙이다(`docs/BUSINESS_DECISIONS.md`
  1절·3-3-1절) — 시장 검증된 확정값이 아니므로, 실제 손님 반응을 보고
  바꿀 수 있다는 걸 전제로 둔 값이다.**
- `COST_SAFETY_CAP_FREE_KRW_MICROS`(기본 700원 단위 micros),
  `COST_SAFETY_CAP_PAID_KRW_MICROS`(기본 3,500원 단위 micros) —
  6차 신규 내부 안전상한. **고객에게 보여주는 숫자가 아니다** — 회사가
  실제로 감당할 실비용의 절대 상한이다.
- `COST_GLOBAL_MONTHLY_KRW_MICROS` 등 나머지 비용 한도는
  `docs/BUSINESS_DECISIONS.md` 3-4절 참고.

## 3. 시작 후 반드시 할 것 — "키가 있다"와 "연결됐다"는 다르다

### 3-0. 실제 연결 확인 순서 — 7단계(15차 신규)

아래는 처음부터 끝까지 **이 순서로만** 진행할 것을 권장한다 — 뒷
단계는 앞 단계가 실제로 연결된 상태를 전제로 하기 때문이다(예:
③Google 로그인 확인은 ①의 영구 DB가 없으면 "연결은 됐는데 재시작하니
계정이 사라졌다"는 식으로 헛되이 반복하게 된다). 각 단계마다 **어디서
무엇을 설정하는지**와 **무엇을 봐야 "됐다"고 판단할 수 있는지**를
같이 적는다. 공통 원칙 두 가지는 모든 단계에 그대로 적용된다:

- **`/api/health`에 키가 "configured"로 뜨는 것과 `verified`가
  채워지는 것만으로는 절대 "연결 성공"으로 기록하지 않는다** — 아래
  각 단계가 지정하는 실제 화면 조작 결과를 직접 봐야 한다.
- **비밀키(시크릿·API 키·웹훅 시크릿 등)는 채팅·문서·ZIP·저장소
  어디에도 넣지 않는다** — 전부 운영 서버 프로세스의 환경변수로만
  들어간다(5절 참고).

**① 테스트 서버·영구 DB 준비**
어디서: 0-0절(현재 호스팅 없음 확인)·0-1절(영구 저장소·백업)·0-3절
(프런트+API를 폰에서 한 주소로 띄우는 구성) 그대로 따라간다.
성공 기준: `node server/index.mjs`와 `node scripts/serve.mjs`를 둘 다
띄운 뒤, 서버 프로세스를 **한 번 재시작**해도(`Ctrl+C` 후 다시 실행)
전에 만든 테스트 계정·장소가 그대로 남아 있어야 한다(재시작 후
사라지면 `DB_PATH`가 지속 저장소를 가리키지 않는다는 뜻 — 아직
①이 안 끝난 것).

**② 이메일 로그인**
어디서: 1-2절(`EMAIL_ADAPTER=resend` 등 3개 환경변수).
성공 기준: 3-2절 1번 — 실제 화면에서 이메일을 넣고 "코드 받기"를
눌러, 그 이메일함에 실제로 6자리 코드가 도착하고 그 코드로 로그인이
끝까지 된다.

**③ Google 로그인과 기존 계정 연결**
어디서: 1-5c절(`GOOGLE_CLIENT_ID` 발급). 15차에서 완성한 기존 계정
연결 화면(소유확인)은 별도 서버 설정이 필요 없다 — 클라이언트
코드로 이미 들어가 있다.
성공 기준: (a) ②에서 만든 이메일 계정으로 로그아웃한 뒤 **같은
이메일의 Google 계정**으로 "Google로 계속하기"를 누르면 "이미 가입된
계정이 있어요" 화면이 뜬다, (b) 그 화면에서 이메일 코드로 소유
확인을 마치면 새 계정이 아니라 **기존에 저장해 둔 장소·이용권
상태 그대로** 들어가진다, (c) 그 뒤 같은 Google 계정으로 다시
로그인하면 소유확인 화면 없이 바로 들어가진다. 이 세 가지를 실제
화면에서 순서대로 확인해야 "연결됐다"고 말할 수 있다 — 서버가 한 번
켜져 있다는 것과는 다른 이야기다.

**④ Google Places/Routes 실제 장소·코스 확인**
어디서: 1-4절(`GOOGLE_PLACES_API_KEY`)·1-5절(`GOOGLE_ROUTES_API_KEY`),
둘 다 결제 수단이 등록된 Google Cloud 프로젝트가 있어야 한다(0절).
성공 기준: 3-2절 2·3번 — 좌표 없는 장소 하나를 실제 위도·경도·주소로
찾아내고, 장소 2곳 이상으로 코스를 만들었을 때 결과 화면에 "실제
도보 경로 기준으로 계산했습니다"라고 뜬다(직선거리 추정이면 아직
안 된 것).

**⑤ WeatherAPI와 일본어 기기 음성 확인**
어디서: 1-5b절(`WEATHER_API_KEY`, 없어도 부팅은 됨). 일본어 음성은
별도 서버 키가 필요 없다 — 기기 자체의 TTS(음성 합성)를 쓰므로 **실제
아이폰/안드로이드 기기**에서 직접 소리가 나는지 들어봐야 한다(에뮬레이터
음소거·오디오 미지원으로 오판하기 쉬운 지점).
성공 기준: 오늘 동선 화면 날씨 카드가 "테스트 데이터(예시)"가 아니라
"WeatherAPI.com 제공"으로 실제 그 도시 기온을 보여준다(3-2절 5번),
그리고 일본 목적지의 "여기서 쓸 말" 🔊 듣기를 실제 기기에서 눌렀을 때
소리가 실제로 난다.

**⑥ Toss 테스트 결제와 이용권 반영**
어디서: 1-3절(`PAYMENT_ADAPTER=toss` 등 4개 환경변수, 토스페이먼츠
가맹점 가입 필요 — 0절).
성공 기준: 3-2절 4번 — 소액(9,900원) 결제를 실제로 진행해 토스
대시보드에 그 거래가 찍히고, 이 계정이 실제로 유료로 바뀌어 이용권
한도(1-7절 `ENTITLEMENT_PAID_*`)가 화면에 반영된다. **테스트 결제였다면
반드시 토스 쪽에서 취소 처리한다.**

**⑦ 실제 AI는 예산·사용량 기록 확인 후 제한적 검증**
가장 마지막에, 그리고 가장 조심스럽게 확인한다 — 실제 청구가 발생하는
유일한 항목이기 때문이다. 어디서: 1-6c절(`ANTHROPIC_API_KEY` +
`AI_CLASSIFY_ENABLE_REAL=true`, 이중 게이트 — **둘 다 넣기 전까지는
기본 비활성 상태 그대로 두고, 이 상태를 임의로 켜지 않는다**).
켜기 전에 반드시 확인:
- 호출 전 **예상(견적) 비용**이 실제로 예산 원장에 기록되는지
  (`server/test/reliability-and-cost.test.mjs` 등 기존 테스트가 이
  경로를 재현 검증했지만, 실제 청구서와 대조된 적은 없다).
- 응답이 돌아온 뒤 Anthropic이 알려준 실제 **usage(토큰 사용량)**로
  정정된 확정 비용이 원장에 남는지.
- 위 견적·usage·확정 비용·남은 예산 네 숫자가 서로 말이 되는
  범위인지(견적이 확정보다 지나치게 낮거나 예산이 이상하게 소진되면
  중단).
- 실패·응답 잘림(truncated)·usage 필드 자체가 없는 경우에도 서버가
  죽거나 잘못 과금하지 않고 기존에 설계된 처리(비활성/규칙 기반
  분류로 대체)를 그대로 유지하는지.
성공 기준: 소량(장소 2~3곳)만 실제로 켜서 위 네 가지를 전부 눈으로
확인한 뒤에도, 전체 사용자에게 켤지는 **하루 이틀 Anthropic 콘솔의
실제 청구 화면을 지켜본 뒤** 별도로 결정한다(1-6c절 그대로) — 이
단계 하나의 성공이 "전체 오픈"을 자동으로 의미하지 않는다.

### 3-1. 폰에서 확인할 순서(14차 신규)

서비스별로 하나씩 따로 확인하기 전에, **실제 사용자가 폰에서 겪는
순서 그대로** 한 번은 끝까지 이어서 확인하는 걸 권장한다 — 각
서비스가 개별로는 동작해도 앞뒤로 이어지는 흐름에서 막히는 지점은
따로 확인해야 보인다:

1. **ZIP/CSV 가져오기** — 저장 목록 파일을 실제로 골라 가져와서
   장소가 화면에 실제로 담기는지.
2. **분류·검색** — 가져온 장소들이 유형별로 분류되고, 검색·필터가
   실제로 걸리는지(AI 보조 분류를 켰다면 백그라운드 분류 결과도
   함께).
3. **실제 코스 생성** — 오늘 갈 곳을 몇 곳 담아 "코스 만들기"를
   실제로 눌러, 실제 도보 경로 기준 결과가 나오는지.
4. **저장 → 로그아웃 → 재로그인** — 만든 코스·담은 장소가 로그아웃
   후 다시 로그인해도 그대로 남아 있는지.
5. **일본어 회화 듣기**(일본 목적지가 있을 때만) — "여기서 쓸 말"을
   열어 🔊 듣기가 실제로 소리를 내는지.
6. **테스트 결제** — 소액 결제를 진행해 유료 전환이 실제로 되는지
   (완료 후 반드시 토스페이먼츠 쪽에서 취소 처리).

**우선순위**: 운영자 본인의 iPhone Safari에서 먼저 전체 순서를 한
번 확인한 뒤, 소수 베타 참가자에게 배분할 때는 참가자들이 실제로
쓰는 **Android Chrome·삼성 인터넷(Samsung Internet)**에서도 같은
순서를 확인해 달라고 요청한다 — 이 세션은 iPhone·Android 실기기
어느 쪽도 직접 확인한 적이 없으므로(`docs/RELEASE_STATUS.md`
"실기기 미검증" 표기 참고), 이 두 축(iPhone Safari + 베타 참가자의
Android)에서 처음 실제로 드러나는 문제가 있을 수 있다. Instagram·
Threads 같은 인앱 브라우저로 링크를 열었을 때 특정 단계(로그인·
결제 등)가 막히면, 화면이 "외부 브라우저로 열기" 안내를 실제로
보여주고 그 안내를 따라가면 막힌 단계를 계속할 수 있는지도 함께
확인한다(막다른 화면으로 끝나면 안 됨).

### 3-2. 서비스별로 하나씩 확인

서버가 뜨면 `GET /api/health`를 열어 본다. 이 응답은 **"각 서비스에
키가 설정돼 있는지"만 보여준다** — `services.places: "configured"`가
"실제로 Google에 요청을 보내 성공 응답을 받았다"는 뜻이 아니다.
`verified` 필드가 있다면 그건 **이 세션이 코드로 미리 짐작한 값**이지
사람이 실제로 확인한 기록이 아니다. **아래 네 가지를 실제 화면에서
직접 눌러 봐야 "연결됐다"고 말할 수 있다**:

1. **이메일 로그인** — 실제 화면에서 이메일 주소를 넣고 "코드 받기"를
   누른 뒤, 그 이메일함에 실제로 6자리 코드가 도착하는지 확인한다.
2. **장소 조회** — 좌표가 없는 장소 하나를 실제로 가져온 뒤, 상세
   화면에서 "서버로 위치 후보 찾아보기"를 눌러 실제 후보(위도·경도·
   주소)가 나오는지 확인한다.
3. **경로 계산** — 좌표가 있는 장소 2곳 이상을 오늘 동선에 담고
   "코스 만들기"를 실제로 눌러, 결과 화면에 "실제 도보 경로 기준으로
   계산했습니다"라고 뜨는지 확인한다(직선거리 추정으로 뜨면 경로 키
   연결에 문제가 있다는 뜻).
4. **결제** — 실제로 소액(9,900원) 결제를 한 번 진행해, 토스페이먼츠
   대시보드에 그 거래가 실제로 찍히는지, 이 계정이 실제로
   `paid`(유료)로 바뀌는지 확인한다. 그 뒤 **테스트 결제라면 반드시
   토스페이먼츠 쪽에서 취소 처리**한다(실제 돈이 오갔다면).
5. **날씨(7차 신규)** — "오늘 동선" 화면을 열어 맨 위 날씨 카드가
   "테스트 데이터(예시)"가 아니라 "WeatherAPI.com 제공"으로 뜨는지,
   실제 그 도시의 실제 기온·날씨로 보이는지 확인한다. 카드 하단의
   "몇 시 기준" 표시가 실제 현재 시각과 크게 어긋나지 않는지도 함께
   본다(너무 오래된 값이면 `stale` 문구가 같이 뜬다).
6. **Google 로그인(13차 신규, `GOOGLE_CLIENT_ID`를 넣었을 때만)** —
   로그인 시트에서 "Google로 계속하기"를 실제로 눌러 실제 Google
   계정으로 로그인이 끝까지 되는지, 이미 이메일 코드로 가입했던 계정과
   같은 이메일로 Google 로그인했을 때 새 계정이 아니라 기존 계정(같은
   저장 장소·이용권 상태)으로 들어가는지 확인한다. Instagram·Threads
   인앱 브라우저에서 열었을 때도 버튼을 누르면 실제로 로그인이 되는지,
   안 되면 이메일 코드 로그인으로 자연스럽게 대체되는지(깨진 화면
   없이) 확인한다.

이 여섯 가지를 실제 아이폰(Safari)에서도 한 번씩 해 보는 걸 권장한다 —
이 세션은 실제 iPhone 기기에서 확인한 적이 없다(`docs/RELEASE_STATUS.md`
2-3절).

## 4. 이미 마이그레이션된 계정이 있다면

서버가 처음 켜질 때 기존 `account_courses`(여행 분리 이전 데이터)를
`trips`/`trip_courses`로 자동 옮기는 마이그레이션이 **딱 한 번만**
실행된다(`server/db.mjs`의 `migrateLegacyCoursesIntoTrips`,
`schema_migrations` 테이블로 중복 실행을 막는다). 운영 DB에 처음
배포할 때 서버 로그에서 이 마이그레이션이 실제로 한 번 실행됐는지
확인한다 — 실행 안 됐다면 기존 사용자가 재방문 여행자 화면에서
"여행이 하나도 없다"고 보일 수 있다(데이터 자체는 안전하게 남아 있고
서버 재시작 시 다시 시도된다).

## 5. 하지 말아야 할 것

- `FORCE_TEST_MODE=true`를 운영 서버에 넣지 않는다.
- `APP_ENV=production` 없이 실제 손님에게 서버를 공개하지 않는다.
- `PAYMENT_PG_SECRET`·`ANTHROPIC_API_KEY`·`EMAIL_API_KEY` 같은
  비밀값을 클라이언트 코드·저장소(git)·로그에 남기지 않는다. **개발
  담당(이 세션)과 대화로 주고받거나, 전달되는 코드 ZIP·문서 안에
  실제 값을 넣지도 않는다** — 이런 값은 오직 운영 서버 프로세스의
  환경변수로만 들어가야 한다(이 문서의 표에 적힌 값 자체는 전부
  자리표시자(`xxx` 등)이지 실제 키가 아니다).
- `/api/health`의 `services` 값만 보고 "전부 연결 확인 완료"라고
  보고하지 않는다(위 3절을 실제로 다 해봐야 한다).

## 6. 우선순위 체크리스트(13차 신규) — 사용자가 다음에 할 일을 순서대로

시간이 한정돼 있다면 아래 순서를 권장한다(뒤로 갈수록 급하지 않음):

1. **이메일(Resend) + 토스 테스트 결제** — 이 둘이 안 되면 로그인도
   구매도 안 되므로 최우선. 소액 실결제 1건을 직접 진행하고 바로
   취소해 결제 전체 흐름을 실제로 확인한다(3절 4번).
2. **Google Places/Routes 키** — 위치확인·코스생성의 핵심 경로.
   키를 넣은 뒤 실제 장소 1곳으로 위치확인, 실제 코스 1개 생성까지
   확인한다(3절 2·3번).
3. **소수 베타 참가자에게 배분 + "불편함 보내기"로 피드백 받기** —
   RELEASE_STATUS.md의 "실기기 베타 체크리스트"를 그대로 쓴다. 위
   1·2번이 실제로 동작해야 베타를 시작할 수 있다.
4. **Google 로그인(`GOOGLE_CLIENT_ID`)** — 필수는 아니지만, 기본
   진입 방식으로 노출되므로 이왕 켤 거면 이 시점에 함께 설정하는
   게 좋다(1-5c절).
5. **날씨(WeatherAPI)** — 이미 무료 등급으로 켤 수 있고 핵심 흐름을
   막지 않으므로 여유 있을 때 확인.
6. **AI 보조 분류(Anthropic)** — 가장 나중. 실제 청구 비용을 먼저
   소량으로 확인한 뒤에만 전체 사용자에게 켤지 결정한다(1-6c절).
   급하게 켤 이유가 없는 부가 기능이다.

`GET /api/health` 응답만으로는 "연결 완료"를 절대 판단하지 않는다 —
매 단계 실제 화면 조작 결과까지 확인한 뒤에만 다음 단계로 넘어간다.
