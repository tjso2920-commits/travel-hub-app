# 후쿠오카 통합 앱 프로젝트 — 인수인계

## 0. 배경
- 2026년 10월 25일 후쿠오카 여행이 목표 마일스톤 (여행일까지 D-day는 앱에서 별도 카운트다운)
- 일본어 학습 자체는 **90일 프로젝트**로 설계 (여행 D-day와는 별개 트랙)
- 3달 프로젝트 목적: 다이어트 + 일본어 회화(일상대화) 실력 향상
- 기존에 만들어둔 개인용 웹앱들(운동/식단 트래커 등)을 하나로 합치는 방식으로 진행 중 (예전에 한글게임+영어게임처럼 통합웹 만든 전례 있음)

## 1. 기존 운동웹 — 커팅트래커_개인용.html (업로드 파일, 이미 완성됨)
- 단일 HTML 파일, 순수 vanilla JS, localStorage 기반 (서버 없음)
- 다크 테마, CSS 변수: `--wasabi`(포인트 그린), `--ember`(포인트 오렌지), `--bg #16130F` 등
- 구조:
  - **게이트 화면**: D-day 카운트다운 + 오늘 체중/소모 입력 게이트
  - **상단 헤더**: 현재체중→목표체중 표시, D-day 뱃지
  - **nav 탭 구조** (sticky, 버튼형 탭 전환 방식 — `.tab.on`으로 표시/숨김)
  - **캘린더/일별 기록**: 운동 세트, 식단(칼로리/단백질), 체중, 소모량 기록
  - **설정 탭**: Gemini API 키 저장(`ai.key`, `ai.model` — localStorage), 목표 칼로리 AI 계산(`callGemini()` 함수로 Gemini 호출), 데이터 export/import(JSON 백업)
  - localStorage 키 prefix 존재(`PFX`) — 통합 시 일본어 데이터도 같은 prefix 체계 안에서 별도 키로 관리하면 충돌 없음
- **통합 방식**: 이 파일에 tab을 하나 더 추가(예: "일본어" 탭, "맛집지도" 탭)하는 식으로 구조 확장. 완전히 새 앱 아님. 기존 URL/홈스크린 아이콘 유지가 목표.

## 2. 일본어 회화 앱 설계 확정사항

### 목표 성격
- **완전 초보 아님**. 이미 후쿠오카 여러 번 다녀와서 공항/숙소/길찾기 등 생존회화는 불필요.
- 목표는 **일본인들과 일상대화** — 스몰토크, 이자카야에서 사장님이랑 잡담, 취향/의견 얘기, 즉흥 대응까지.
- 유저는 F&B 경력 10년+ (바텐더/오로시/이자카야) — 스시/사시미/조리 관련 업계 용어는 실제 강점이라 커리큘럼에 살릴 것.
- **현재 레벨**: 이자카야/야타이에서 주문·영수증 요청까지는 자연스럽게 가능. 다락원 "일본어 잘하고싶을땐 독학 첫걸음" 완독했지만 오래돼서 까먹은 상태.
  - (분석 결과) 이 책은 총 12과, 히라가나/가타카나부터 시작해 **JLPT N5 수준 문법/표현/어휘**까지 다루는 왕초보 교재.
  - → **N5 재탕 금지가 아니라, 이 책 내용을 토대로 N5를 복습하며 자연스럽게 다시 익히고, 그 위에 N4를 자연스럽게 얹는 방향으로 진행.** (이전에 "N5 재탕 없이 N4부터 시작"이라고 잘못 정리했던 부분 — 유저가 정정함: 다 까먹어서 복습 필요)
  - 책의 정확한 목차/과별 디테일을 알면 리뷰 순서를 실제 학습 순서에 맞출 수 있음 — 유저가 목차/내용 사진 찍어 보내주면 더 정확하게 설계 가능 (필수는 아니고, 없으면 일반적인 N5 커리큘럼 순서로 진행)
- 히라가나/가타카나 공부했지만 자꾸 헷갈림 → 별도 알파벳 암기 세션보다 실제 문장 읽으면서 자연스럽게 굳히는 방식 필요. 기본 한자 들어간 문장도 마찬가지로 자연 노출 방식 선호.
- **프로젝트 기간 90일** (95일 아님 — 유저가 90일로 지정)

### 자투리 시간 학습 — 신규 핵심 요구사항
유저가 명시한 실제 가용 시간대:
- **말하기(회화) 가능**: 주방 근무 중, 퇴근 후 → 여기서만 시뮬레이션 챗봇 음성 연습 가능 (기존처럼 선택/보너스 취급). 주방에서는 말하기 외에도 **이어폰 한쪽으로 듣기(오디오 리스닝)도 가능** — 운동 중 오디오 모드와 같은 리스닝 큐를 여기서도 재생 가능
- **운동(천국의계단·헬스) 중**: 이어폰으로 음성 듣기 가능 (양손 못 씀, 오디오 전용 모드 필요)
- **세트 사이 쉬는 시간**: 짧게 글자 보는 건 가능 (커팅트래커에 이미 있는 세트 간 휴식 타이머 UI 재활용 가능 — 이 타이머 도는 동안 SRS 카드 한 장 노출)
- **헬스장 인포(안내데스크) 근무 중**: 듣기·말하기는 불가, **텍스트(활자)만 가능** — 끊기더라도 볼 수 있고 15분 이상 투자 가능 (세트 사이보다 훨씬 긴 세션)
- **자기 직전**: 짧은 복습 정리 세션

**설계 방향**: 이 시간대별로 다른 학습 모드를 자동 매칭
1. **오디오 전용 모드** (운동 중, 손 못 씀) — 새 표현+복습 표현을 음성으로만 순차 재생 (자막 없이도 되는 리스닝 큐)
2. **쉬는 타임 카드** — 커팅트래커의 세트 간 휴식 타이머가 도는 동안 자동으로 SRS 카드 1장 표시 (기존 운동 기능 위에 얹는 것이라 새 UI 거의 안 만들어도 됨)
3. **인포 모드 (텍스트 전용, 긴 세션)** — 15분 이상 확보되는 대신 손님 응대로 끊길 수 있으니, 짧은 카드 여러 장보다 **끊겨도 이어보기 가능한 텍스트 읽기 콘텐츠**(리딩 지문, 대화문 여러 개 스크롤, 어디까지 읽었는지 자동 저장) 형태가 맞음. 오디오/말하기 요소 없이 순수 읽기.
4. **취침 전 요약 모드** — 오늘 학습한 것 + 내일 나올 것 미리보기 짧게
5. **히라가나/가타카나/한자 자연 노출** — 문장에 후리가나 달아서 보여주다가, 익숙해진 글자부터 후리가나를 점점 빼는 방식(단계적 노출 감소)으로 "따로 외우기" 없이 자연스럽게 굳히기

### 90일 커리큘럼 구조 (주 단위, 1주=7일, 약 12~13주)
- W1~2: 스몰토크 기본
- W3~4: 이자카야 단골 대화 (잡담, 추천 요청, 농담)
- W5~6: 스시/사시미 전문 표현 + 업계인 대화 (오로시 등 유저 전문 지식 연결)
- W7~8: 하카타벤(후쿠오카 사투리)
- W9~10: 의견/취향 표현 (좋아하는 것, 비교해서 말하기)
- W11~12: 즉흥 대응 (예상 못한 질문, 화제 전환)
- W13~ : 시뮬레이션 챗봇 종합 프리토킹
- 매일 그 주 테마 안에서 다른 소주제로 새 표현 5~8개, + 전날/이전 학습 복습이 섞여 나오는 구조(SRS)

### 기능 목록
1. **가게 카테고리별 맞춤 표현 세트** — 라멘/이자카야/스시 등 업종별로 표현 자동 매칭
2. **실전 시뮬레이션 챗봇** — 스크립트 암기 아님, AI가 점원 역할로 랜덤 변수(품절, 예상외 답변 등) 던져서 애드리브 훈련
3. **메뉴판 사진 자동번역** — Gemini 비전으로 필기체/세로쓰기 메뉴도 인식, 요리별 정리 + 발음가이드
4. **메뉴판 → 즉석 시뮬레이션 연결** — 찍은 실제 메뉴로 그 자리에서 회화 연습 시나리오 자동 생성 (핵심 차별점)
5. **한→일 실시간 번역** — 타이핑은 API 텍스트 번역, 음성은 브라우저 음성인식+API 또는 Gemini 오디오 입력
6. **양방향 실시간 자막 모드** (통역기처럼)
7. **F&B 전문 용어 레이어** — 메뉴판에서 조리법/재료 나오면 업계 관점 설명 추가

## 3. 구글맵 저장 장소 연동
- **결론: 실시간 연동 불가능** — 구글맵 개인 저장 리스트는 공식 API 없음
- **방법**: Google Takeout으로 저장 장소 export(KML/JSON) → 앱에 1회 import → 이후 앱 자체 데이터로 관리(실시간 sync 아님, "이식" 방식)
- 저장 개수 1,000건 미만 확인됨 → **Google Places API (Place Details, Pro tier)**로 카테고리/평점/사진 자동 보강 시 월 5,000건 무료 cap 안에 여유 있게 들어감 (사실상 무료)
- 이름만으로 업종 유추는 절반 정도만 가능 (일본 가게명은 오너 이름/언어유희로 짓는 경우 많음) → Places API 보강이 필요한 이유

## 4. 비용/API 정책 (중요 — 유저가 돈 안 쓰고 싶어함)
- **Gemini API는 앱 구독(AI Pro/Ultra)과 완전 별개.** 유저가 이미 Gemini 유료 구독 중이어도 API는 Google AI Studio에서 별도 키 발급, **무료 티어 그대로 존재** (Flash/Flash-Lite 모델, 하루 최대 1,000건 무료 — 2026-04-01부터 Pro 모델만 무료 티어 제외, Flash는 무료 유지)
- 개인 저용량 사용(하루 회화 연습 몇 번 + 가끔 메뉴판 사진)은 **무료 티어로 충분히 커버 가능** — 유료 전환 불필요할 가능성 높음
- **TTS(ElevenLabs 등)는 별도 결제 필요** — 유저가 원하지 않는 방향. 대신 **유튜브 쇼츠/영상 embed 방식 선호** (실제 원어민 발음+표정, 완전 무료). 커스텀 문장(맞춤형)만 텍스트로 처리하고 음성은 최대한 배제하는 방향으로 설계
- Google Places API도 무료 cap 안에서 해결 (위 3번 참고)
- **결론: 이 프로젝트는 사실상 추가 지출 없이 진행 가능한 방향으로 설계 확정**

## 5. 오늘 추가된 신규 요청 (아직 설계 전, 새 채팅방에서 이어서 풀어야 할 것)
> "각주마다 목표 세션이 있을 텐데, 그걸 꼭 안 지키더라도 다 학습이 되는 시스템"
> "자동복습도 되게 (인간 뇌는 까먹게 되어 있으니, 무의식적으로라도 반복학습 되게)"

풀어야 할 설계 문제:
1. **주차별 커리큘럼이 캘린더 날짜에 고정되면, 며칠 빠졌을 때 진도가 밀리거나 압박감으로 이어질 위험** → 날짜 고정이 아니라 "완료 기반 진행" 구조(진도 포인터가 실제 완료한 만큼만 이동)로 갈지 검토 필요
2. **SRS를 진짜 "무의식적으로" 만들려면?** — 일본어 탭을 따로 안 열어도, 운동 탭이든 홈 화면이든 앱을 켤 때마다 복습 문장 1~2개가 자동으로 뜨는 방식(예: 홈 대시보드 상단에 "오늘의 한마디" 위젯) 같은 걸 고려 중이었음 — 다음 세션에서 구체화 필요
3. **밀린 복습량이 한꺼번에 몰릴 때 과부하 안 되게 하는 로직** (하루 최대 복습량 캡, 밀린 것부터 우선순위)도 아직 미설계

## 7. 2026-07-22 구현 완료 현황 — 위의 “아직 설계 전”보다 이 절이 우선

### 산출물
- `커팅트래커_개인용.html`: 기존 개인 데이터와 기본값을 유지하는 실사용본. `SALE_MODE=false`, localStorage prefix `cp1_`.
- `후쿠오카_통합앱_판매용.html`: 사용자 개인정보·개인 프로필 기본값·API 키·호텔·현재 위치를 넣지 않은 배포본. `SALE_MODE=true`, prefix `cs1_`로 개인용과 저장소를 완전히 분리.
- 기존 개인용 파일에 일본어와 후쿠오카 탭을 **추가**했으며, 기존 운동 코드의 삭제·리팩터링은 하지 않았다.

### 반드시 유지할 불변 조건
- 운동 영상의 하드코딩 YouTube 목록, 자동 검색 URL 생성, Gemini 영상 찾기, 영상 그룹 추가/삭제를 수정하거나 단순화하지 말 것.
- 기존 localStorage 키와 데이터 구조를 바꾸거나 마이그레이션하지 말 것.
- `:root`의 기존 색상 변수와 폰트를 바꾸지 말 것. 밝기 개선은 파생 그라데이션·표면·그림자만 사용했다.
- 기존 `.tab.on` 탭 전환, D-day, 운동 달력·기록·칼로리 계산 로직을 유지할 것.
- 사용자가 수정 요청을 할 때마다 먼저 “추가할 것 / 건드리지 않을 것”을 설명하고, 결과는 일부 코드가 아니라 완성 HTML 전체 파일로 전달할 것.

## 8. 2026-07-22 재검수 정정 — 이 절이 위의 “구현 완료” 표현보다 우선

### 검은 화면 원인과 전달 방식 수정
- ChatGPT의 HTML 미리보기 환경이 인라인 JavaScript를 실행하지 않으면, 기존 구조상 빈 `#gateWrap`만 남고 `#app`은 `display:none`이어서 검은 화면만 보였다. 앱 소스의 문법 오류가 원인은 아니었지만, 미리보기에서 쓸 수 없는 HTML을 실행본처럼 전달한 것은 전달 오류다.
- 개인용·판매용의 `#gateWrap` 안에 정적 안내 폴백을 추가했다. JavaScript가 차단된 미리보기에서는 “다운로드 후 Safari 또는 Chrome에서 열기” 안내가 보이고, JavaScript가 실행되는 실제 브라우저에서는 기존 `renderGate`/`renderOnboard`가 이를 교체한다.
- 다운로드 클릭이 HTML 미리보기로 열리지 않도록 각 전체 HTML을 ZIP으로도 제공한다. 권장 실행 절차는 `ZIP 다운로드 → 압축 해제 → HTML을 Safari/Chrome에서 직접 열기`다.
- 이 수정에서는 운동 영상 매핑, 기존 localStorage, D-day, 운동 달력·기록, 기존 탭 전환, 기존 `:root`를 수정하지 않았다.

### 원본 대비 보존 검수
- 최초 첨부 원본을 별도 감사본으로 물질화해 현재 개인용과 줄 단위 비교했다.
- 원본 `:root`, 운동 영상 객체 `V`, `personalDays()`, `PF_PERSONAL`, `PF_GENERIC`는 동일하다.
- 기존 영상 관련 `autoVid`, `editVid`, `addVid`, `aiVidFor`와 하드코딩 YouTube 링크 12개가 유지된다.
- 원본 줄의 교체는 홈 버튼 삽입, `가이드→운동가이드` 표시명, 운동 달력의 일본어 완료 표시 결합 등 요청된 연결 지점에 한정된다. 기존 localStorage 키는 이름·구조를 바꾸지 않고 신규 키만 추가됐다.

### 전수검수에서 새로 확인된 미해결 결함
1. **좌표 판정 치명적 결함**: `fm2HasCoords()`가 `Number.isFinite(+p.lat)` 방식이라 `null`을 숫자 `0`으로 오인한다. 좌표 없는 Takeout 행이 `(0,0)` 좌표 보유로 처리되어 지도·길찾기·“좌표 없음” 필터가 틀릴 수 있다. 실제 CSV 반영 전에 최우선 수정해야 한다.
2. **전체 백업 누락**: 기존 “전체 데이터 내보내기/가져오기”가 신규 `jp_state_v1`, `jp_chat_v1`, `jp_packs_v1`, `foodmap_v1`을 포함하지 않는다. 기존 백업 포맷을 훼손하지 않고 확장 백업/복원 경로를 추가해야 한다.
3. **일본어 목표 대비 정적 콘텐츠 부족**: 90회 세션·90개 문법·13개 연계 회화는 생성되지만, 중복 제거한 기본 회화 문장은 104개다. Gemini 확장을 사용하지 않는 상태에서 N4 및 이자카야 실전 회화를 보장한다고 표현하면 안 된다. N3 보너스 33개도 현재는 라벨 중심이라 N3 턱걸이 목표를 뒷받침하지 못한다.
4. **문법 설명 품질 불균일**: 90개 중 18개만 수기 상세 메타이고 72개는 일반 생성 설명이다. `て형`, `〜前に／〜た後で`, 가능형, `〜間／〜間に` 등은 접속 설명이 부정확하거나 모호하다. 전 항목 수기 교정이 필요하다.
5. **히라가나 요구 미완료**: 읽기 문자열 4개에 가타카나가 남아 있어 “히라가나 줄” 요구를 완전히 충족하지 못한다.
6. **달력 학습 기록 범위 부족**: 현재 달력에는 완료 팩만 기록된다. 복습만 한 날, 오디오 모드, 인포 읽기, 취침 전 복습은 학습 활동으로 기록되지 않는다.
7. **발음 버튼 한계**: `ja-JP` Web Speech API는 기기 내 TTS이며 녹음된 일본인 성우 음성이 아니다. 음성 존재·품질·로딩 시점이 브라우저/기기마다 다르다.
8. **연계 질문 자연스러움**: `何回来たことがありますか`보다 상황상 `福岡は何回目ですか` 또는 `今まで何回来ましたか`가 자연스럽다. 회화 문구 교정이 필요하다.
9. **145개 전체 지도 미완료**: 현재 지도 iframe은 선택한 한 장소를 보여주며, 145개를 한 화면에 모두 핀으로 표시하지 않는다. Places 보강도 선택 장소 단위라 대량 보강이 아니다.
10. **분류·거리·동기화 한계**: 일본어 상호만 있는 좌표 미보유 행은 초기 분류가 `기타`가 되기 쉽다. 빈 시간 코스는 직선거리 근사이며 실제 도보 시간이 아니다. 단축 `maps.app.goo.gl` 호텔 URL은 좌표 추출이 안 될 수 있다. CSV 파일 연결은 로컬 파일 변경 감지일 뿐 Google Maps Saved 실시간 연동이 아니고 Safari/iPhone에서는 수동 재가져오기가 필요하다.
11. **실데이터 검증 미실시**: 사용자 145개 `여행 계획` CSV 원본을 아직 받지 못했으므로 실제 열 이름, 누락 좌표, 중복, 개인정보 포함 여부는 검증하지 못했다.
12. **실브라우저 시각 QA 제한**: 현재 환경에 Chromium/Firefox 실행 파일이 없어 VM/JSDOM의 `file://` 실행과 무스크립트 상태까지만 검증했다. 모바일 6개 탭에서 `운동가이드` 줄바꿈/폭은 실제 Safari·Chrome 확인이 필요하다.

- 투영은 중심 위도의 `cos`로 경도를 보정한 등장방형이다. 도시 규모에서는 왜곡이 무시할 수준이다.

## 26. 2026-07-29 규칙 기반 동선 코스 생성

### 왜 규칙인가

코스 생성을 AI에 맡기지 않았다. 규칙은 키가 없어도 돌고, 오프라인에서 돌고, 즉시 답하고, 같은 조건에 같은 결과를 준다. 판매용에서 구매자가 API 키 없이 쓸 수 있어야 하는 핵심 기능이므로 규칙이 맞다. AI는 이미 만들어진 코스를 설명하거나 변형하는 데만 쓴다.

### 목적·시간대 규칙

- 목적 6종 `식사·술·카페·관광·쇼핑·사우나`. 각각 대응 분류, 체류 시간, 낮·밤 시간창을 가진다.
- 예: 관광은 09~17시만, 술은 17~26시(새벽 2시까지)만, 식사는 11~14시와 17~21시. 시작 시각이 시간창을 벗어난 목적은 칩에 `·시간대밖`으로 표시되고 선정에서 후순위가 된다.
- 시간창을 벗어난 목적만 선택했다면 그대로 진행한다. 사용자의 명시적 선택을 규칙이 무시하지 않는다.

### 후보 선별

- 좌표가 있고, 제외되지 않았고, 영업 중이 아닌 것으로 확인되지 않았고, **아직 방문하지 않은** 장소만 후보다.

## 33. 2026-07-29 실시간 환율·사진 기록

### 환율 자동 갱신

- `fxAuto()` — 앱을 열 때 저장된 기준일이 오늘이 아니면 **한 번만 조용히** 다시 받는다. 세션당 1회로 제한하고, 오프라인이거나 통화가 같으면 건너뛴다.

- `fxFetch(quiet)` 로 수동·자동 호출을 구분한다.

### 사진 기록

**설계 원칙:** 위치와 시각은 파일에 기록된 값을 직접 읽는다. AI 추측이 아니므로 정확하다. 금액은 영수증에서만 읽는다. 음식 사진으로 가격을 추정하면 예산이 통째로 틀어지므로 프롬프트에서 금지한다.

- `phRead(buf)` — 외부 라이브러리 없이 JPEG EXIF 를 직접 파싱한다. APP1 세그먼트 → TIFF 헤더(엔디안) → IFD0 → ExifIFD(0x8769)에서 촬영 시각(0x9003), GPSIFD(0x8825)에서 좌표(0x0001~0x0004).
  - **4바이트 이하 값은 오프셋이 아니라 항목 안에 직접 들어간다.** GPS 방위 문자(N/S/E/W)가 여기 해당한다. 검사용 생성기를 처음 규격과 다르게 만들어 남위·서경 판정이 실패했고, 생성기를 규격에 맞춰 고쳐 해결했다. **파서가 아니라 검사가 틀렸던 사례다.**
  - 좌표는 `fm2Coord` 로 재검증한다.
- `phNearest(lat,lng,300)` — 300m 안의 가장 가까운 저장 장소를 찾는다. **구매자가 넣은 장소든 무엇이든 `foodMap.places` 전체를 대상으로 한다.**
- `phAnalyze('receipt'|'food')` — Gemini 이미지 입력. 영수증은 합계·통화·항목을 JSON 으로, 음식은 이름·칼로리·단백질을 JSON 으로 받는다. 코드블록 표기를 제거한 뒤 파싱하고, 실패하면 사유만 남기고 앱은 계속 동작한다.
- `phSaveSpend()` — 읽어 낸 합계를 지출에 넣는다. **날짜·시각은 EXIF 값을 쓴다.** 사진을 나중에 정리해도 실제 소비 시점으로 기록된다. 장소가 매칭되면 연결하고 방문 처리한다.
- `phSaveVisit()` — 금액 없이 방문만 기록한다. **Gemini 키가 없어도 동작한다.**
- `phSaveFood()` — 추정 칼로리·단백질을 오늘 식단에 추가한다. 화면에 추정치이며 오차가 크다고 명시한다.
- **사진 파일 자체는 저장하지 않는다.** 읽어 낸 정보만 기록에 남긴다. base64 이미지를 localStorage 에 넣으면 용량이 금방 찬다.

### 제품의 핵심 정의

소비자가 Google Maps 등에 직접 저장한 장소는 그 사람의 **관심 데이터**다. 판매자가 후쿠오카 추천 장소 목록을 파는 제품이 아니다.

> 구글맵, 인스타그램, 틱톡, 유튜브 어디서 발견했든 사용자가 직접 저장한 관심 장소를 한곳에 모아, 숙소·여행 날짜·영업시간·휴무·이동거리·예산에 맞는 실제 실행 가능한 일정으로 바꿔준다.

장기적으로는 특정 국가에 종속되지 않게 설계한다. 국가·언어·통화·지도 지역만 바꾸면 같은 로직을 다른 여행지에 적용할 수 있어야 한다.

### SNS 여행 인박스

SNS 계정의 비공개 저장함을 무단으로 통째로 읽는 방식과, 사용자가 게시물을 직접 앱에 공유하는 방식은 완전히 다르다. 초기 제품은 후자를 사용한다.

### 확정된 장기 기능 목표 — 좋아요·저장 항목 가져오기

사용자는 Google Maps만이 아니라 Instagram·TikTok·YouTube에서 자신이 **좋아요를 누르거나 따로 저장한 콘텐츠**도 여행 관심 데이터로 가져오기를 원한다. 이 목표를 정식 제품 로드맵에 포함한다.

다만 UI에서 플랫폼별 차이를 숨기려고 거짓으로 `모든 저장함 자동연동`이라고 표현하면 안 된다. 내부 구현은 아래 3가지 통로를 하나의 `관심 장소 가져오기` 화면으로 묶는다.

1. **계정 동의형 자동 가져오기:** 공식 OAuth/API가 허용하는 데이터. 현재 가장 현실적인 것은 YouTube 좋아요 영상과 일반·비공개 여행 플레이리스트다.
2. **사용자 파일 가져오기:** 플랫폼이 제공하는 `내 정보 내보내기` 파일을 사용자가 직접 받아 업로드하는 방식. Instagram은 실제 내보내기 샘플에서 좋아요·저장 링크가 안정적으로 제공되는지 먼저 검증한 뒤 지원 여부를 확정한다.
3. **개별 공유형 가져오기:** 공식 대량 조회가 막힌 Instagram·TikTok에서 `공유 → 이 앱` 또는 링크 붙여넣기로 수집한다.

#### 가져오기 화면의 권장 표현

- `Google Maps 저장 장소 가져오기`
- `YouTube 좋아요·여행 재생목록 연결`
- `Instagram 저장 게시물 보내기`
- `TikTok 즐겨찾기 영상 보내기`
- `내보내기 파일에서 가져오기(지원 형식만)`

#### 대량 가져오기 때 필요한 필터

좋아요는 저장보다 신호가 약하고 여행과 무관한 콘텐츠가 많이 섞인다. 전부 장소로 등록하지 말고 다음 단계를 둔다.

1. AI가 여행·맛집·숙소·쇼핑·관광 가능성이 있는 콘텐츠만 1차 분류한다.
2. 국가·도시 후보별로 묶어 `일본 84개 / 태국 21개 / 장소 불명 37개`처럼 보여준다.
3. 사용자가 여행지와 가져올 항목을 선택한다.
4. 여러 게시물이 같은 장소를 가리키면 하나의 Place ID로 합치되, 각 게시물의 추천 이유와 원본 링크는 모두 남긴다.
5. `저장`, `좋아요`, `직접 추가`를 서로 다른 관심 강도로 기록한다. 일정 추천 우선순위는 기본적으로 `직접 추가 > 저장 > 좋아요` 순으로 둔다.

#### 동기화 상태를 정직하게 표시

- `자동 동기화`: 공식 API와 사용자 동의로 반복 조회가 가능한 경우
- `한 번 가져옴`: 내보내기 파일처럼 특정 시점의 사본인 경우
- `직접 보냄`: 공유 시트나 링크로 한 건씩 들어온 경우

플랫폼 연동이 끊기거나 권한이 만료돼도 이미 사용자가 확인한 장소·개인 메모·일정이 함께 사라지지 않도록 한다. 단, 원본 게시물이 삭제되면 미리보기는 깨질 수 있음을 안내한다.

### AI가 게시물에서 추출할 정보

단순한 장소 핀만 가져오면 게시물을 저장한 이유가 사라진다. 다음 정보를 구조화해서 저장한다.

- 원본 플랫폼·게시물 URL·작성자
- 장소 후보명·지점·지역
- **저장한 이유 또는 크리에이터의 핵심 팁**
- 추천 메뉴·체험·사진 포인트
- 방문하기 좋은 시간과 요일
- 휴무·웨이팅·예약 필요 여부
- 가격 또는 예산 힌트
- AI 장소 판별 신뢰도
- 사용자가 확인한 Google Place ID 또는 최종 좌표

권장 처리 흐름:

1. 사용자가 링크를 공유하거나 붙여넣는다.
2. 허용된 공개 메타데이터·캡션·설명 등에서 AI가 장소 후보와 핵심 팁을 추출한다.
3. Places/지오코딩 데이터로 실제 장소 후보를 매칭한다.
4. 동명 장소나 지점이 여러 개면 사용자가 최종 확인한다.
5. 확정된 장소와 `왜 저장했는지`를 함께 여행 인박스에 보관한다.
6. 숙소·날짜·영업시간·이동거리·예산을 적용해 일정 후보를 만든다.

AI가 장소를 틀리게 인식할 수 있으므로, 낮은 신뢰도의 결과를 자동 확정하지 않는다. 원본 링크는 사용자가 다시 확인할 수 있게 유지한다.

6. Instagram DM 봇
7. Instagram 내보내기 파일 실물 샘플 검증
8. TikTok Data Portability는 한국 지원이 시작된 뒤 판단

후쿠오카 출발 전 판매에 필요한 것은 1~3단계다. 모든 SNS 계정의 저장함 전체 동기화를 먼저 완성하려다 출시를 늦추지 않는다.

### Plotline과의 관계·차별화

- Plotline iOS 1.0은 2026-03-17 출시된 신생 앱이며, 게시물 공유→장소 추출→AI 일정이라는 방향이 일부 겹친다.
- 방향이 겹친다는 사실만으로 제품을 중단하지 않는다. 사용자가 저장한 콘텐츠를 일정으로 바꾸는 **기능적 아이디어 자체**와, Plotline의 구체적인 화면·문구·그래픽·코드·브랜드는 구분한다.
- Plotline의 기능 목록을 그대로 복제하는 제품이 아니라, 한국 사용자의 일본 여행 실행 문제에 더 깊게 들어간다.
- 우선 차별점:
  - 한국어 우선의 매우 쉬운 온보딩
  - Google Maps 저장 장소를 숙소·영업시간·휴무·거리·예산으로 실제 일정화
  - 일본 현지 회화·통번역·메뉴판 번역
  - 날씨·라이브캠·현장 상황에 따른 일정 재조정
  - 게시물에서 `장소`뿐 아니라 `왜 저장했는지`와 추천 메뉴·시간까지 보존
  - 여행 전 준비 과정 판매 → 현지 실사용 검증 → 귀국 후 V2 판매

### 법적 경계

아래는 개발·출시 단계의 위험 관리 기준이며 정식 법률 자문은 아니다.

1. **아이디어와 표현을 분리한다.** 한국 판례상 독창적인 아이디어라도 그 자체는 저작권 보호 대상이 아니고, 창작적인 표현 형식이 보호된다. 따라서 동일한 문제를 독립적으로 해결하는 것은 가능하지만, Plotline의 고유한 화면 구성·아이콘·색·카피·그래픽·온보딩 순서까지 실질적으로 유사하게 복제하지 않는다.
2. **Plotline 코드를 보거나 추출하지 않는다.** Plotline 약관은 역공학·소스 추출과 자동 스크립트 수집을 금지한다. 앱 분석 도구로 내부 코드·네트워크·데이터를 복제하거나 Plotline의 장소 DB를 수집하지 않는다.
3. **이름과 브랜드를 독립적으로 만든다.** `Plotline`과 혼동될 이름·로고·스토어 설명·광고 문구를 사용하지 않는다. 국내 출시 전 KIPRIS, 글로벌 출시 전 주요 국가 상표 검색을 한다.
4. **공식 API·공유 링크를 기본으로 한다.** Instagram/TikTok/YouTube의 비공개 저장함을 비공식 로그인·세션 탈취·크롤링으로 수집하지 않는다. 공식 API, OAuth, 공유 시트, 사용자가 직접 제공한 URL 범위에서 처리한다.
5. **타인의 콘텐츠를 재판매하지 않는다.** 영상·이미지·전체 캡션을 다운로드해 앱 서버에 복제·재배포하지 않는다. 가급적 원본 링크, 공식 임베드, 장소라는 사실 정보, 사용자가 작성한 메모, 최소한의 AI 요약만 저장한다. 신고·삭제 요청 절차도 둔다.
6. **지도 데이터 약관을 지킨다.** Google Places 데이터는 표시·귀속·캐시 제한이 있으며 Place ID는 예외적으로 장기 저장할 수 있다. 장소 사진·리뷰·영업시간을 자체 영구 DB처럼 무제한 복제하지 않는다.
7. **개인정보와 위치정보를 별도 설계한다.** 계정, 여행 날짜, 숙소, 저장 목록, 실시간 GPS는 개인을 식별하거나 이동을 드러낼 수 있다. 수집 목적·보유기간·제3자 AI 전송·국외 이전·삭제 방법을 고지하고 필요한 동의를 받는다. 실시간 개인위치정보를 서버에서 지속 처리하는 유료 서비스라면 한국 위치정보법상 신고·약관 의무를 출시 전에 전문가에게 확인한다.
8. **특허 위험은 별도다.** 아이디어가 저작권 대상이 아니어도 특정 기술 구현에 유효한 특허가 있으면 문제가 될 수 있다. 국내 유료 출시 전 간단한 선행기술·상표 검색을 하고, 투자 또는 글로벌 확장 전에 변리사를 통해 자유실시(FTO) 검토를 한다.
9. **독자 개발 기록을 남긴다.** Git 커밋, 기획 문서, 테스트 기록, 디자인 시안과 의사결정 날짜를 보관한다. Plotline을 베낀 것이 아니라 사용자 문제에서 독립적으로 설계했다는 근거가 된다.
